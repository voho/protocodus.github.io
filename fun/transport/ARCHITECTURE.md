# Transport module reference

Static ES modules. No build step. `model.js` owns all game state and exports:

- `BIOMES`: object keyed taiga/tundra/desert, each `{name, description}`.
- `INDUSTRIES`: object keyed kind, each `{name, inputs: {cargo:count}, outputs: {cargo:count}, cost, biomes: string[]}`.
- `CARGO`: object keyed cargo, each `{name, color, price, transit}`, where `transit` names its `TRANSIT_CLASSES` entry: express, perishable (shown as Time-sensitive), standard or bulk. `mail` (price 26, express) comes second, after `passengers` (18), so it is second in every cargo list; routes save cargo by key, so the order is save-safe.
- `TOWN_TRAFFIC` (`['passengers', 'mail']`) and `isTownTraffic(cargo)` (`data.js`) name the cargo that travels between two different towns and loads at both ends. Every check that once meant `cargo === 'passengers'` for that reason uses it; checks about people or buses (bus, coach and ferry art, the residents badge, the starter route, the town hall's advertising) stay on passengers.
- `createGame({biome='taiga', seed=1847, size='square512'}={})` returns JSON-serializable state.
- `build(game, tool, x, y)` returns `{ok, message}`; tools `road`, `rail`, `bridge`, `railbridge`, `tunnel`, `railtunnel`, `bus-stop`, `train-stop`, `port`, `airport-x`, `airport-y`, `residential`, `commercial`, `industrial`, `city`, `bulldoze`, or industry kind.
- `buildPath(game, tool, points)` returns `{ok, message}` for array `{x,y}`; safe partial placement is allowed but message must report errors/cost. Deduplicate points.
- `addRoute(game, {name, mode:'road'|'rail'|'water'|'air', stops:[stationId,stationId], cargo:'passengers'|'mail'|cargoKey, fullLoad=false})` returns `{ok,message,route?}`. Requires connected infrastructure and a suitable cargo source/destination. Buys vehicle, exact upfront cost exposed by `VEHICLE_COSTS` export. The route takes `nextRouteNumber`, the fill of `nextLineColor` at its stops and, without a name, `defaultRouteName` (see Route identity). Before spending, a `fullLoad` that is not a boolean is refused (*Choose on or off.*), and so is `true` for passengers or mail (*Full load is for freight routes.*); `true` alone writes `route.fullLoad` (see Full load under Local simulation).
- `FULL_LOAD_MAX_WAIT` (30 days), `waitingForFullLoad(vehicle)` (`typeof vehicle?.fullLoadSince === 'number'`) and `setRouteFullLoad(game, routeId, on)`, which returns `{ok,message,route?}`. It refuses a missing route, an `on` that is not a boolean, town traffic and the current setting (*Nothing to change.*); otherwise it sets `route.fullLoad`, and turning it off ends every wait on the route at once. It bumps `revision`, spends nothing and never notifies.
- `removeRoute(game, routeId)` returns `{ok,message,refund}`; `getRetirementRefund(game, routeId)` quotes that refund, 45% of each vehicle's paid price.
- `editRoute(game, routeId, {stops, cargo})` moves a route to new stops or another freight without selling its vehicles and returns `{ok,message,route?}`. The route keeps its mode. The launch rules come from `planRoute`, which `addRoute` shares, with its messages and the freight reversal that loads at the producer's end. A switch to or from mail is refused (*Mail needs its own route. Launch a new one instead.*), then a switch between passengers and freight (*Passenger and freight vehicles differ. Launch a new route instead.*), and so are the same stops and cargo (*Nothing to change.*); a refusal changes nothing. Otherwise the edit sets the stops, path and `pathRevision` and marks the route running. `snapVehiclesToPath`, which `updateRoutePath` shares, moves each vehicle to the nearest tile of the new path, keeping its direction and load. A cargo change empties the vehicles. The card's accounts restart (`revenueAtAccountingStart = revenue`, `expenses = 0`, `accountingStartDay = day`), while `delivered` stays a lifetime count. A new `game.routes` array retires the cached upkeep shares and fleet index, whose keys include that array. No money moves, no id is spent and nothing new is saved.
- `renameStation(game, stationId, name)` and `renameRoute(game, routeId, name)` trim the name and return `{ok,message}`. They refuse an empty name (*Enter a name.*), one over 36 characters or the current name; otherwise they set it and bump `revision`. Duplicate names are allowed but never generated: `build` numbers a new stop from `stations.length+1` upwards until `${place} Stop|Station|Port ${n}` is unused, so fresh games keep their old names and nothing new is saved.
- `addRouteVehicle(game, routeId)` buys one more vehicle at `getVehiclePurchase` for an active route and returns `{ok,message,vehicle?,cost?}`. `sellRouteVehicle(game, routeId)` sells the lowest generation, then the emptiest, then the last in array order, and refuses the last vehicle; it returns `{ok,message,vehicle?,refund?}`. `getRouteFleet(game, routeId)` returns `{count,capacity,load,minLevel,maxLevel,levels,sellRefund}`. `vehicleNoun(mode, cargo, n)`, re-exported from `copy.js`, names a route's vehicle (bus, truck, train or ship). `addRoute` and `addRouteVehicle` refuse once the fleet holds `MAX_VEHICLES` (10,000), the most `validateGame` accepts.
- `tick(game, days)` advances time, vehicles, economy, growth. Can receive fractional days; sim rate one day per real second at 1x.
- `findPath(game, from:{x,y}, to:{x,y}, mode)` returns tile coordinate array or null.
- `saveGame(game)` / `loadGame()` / `deleteSave()` localStorage with validation/version.
- `drainDeliveryEvents(game)` returns and clears the paid deliveries since the last call, `{x,y,revenue,cargo,amount,routeId,day}` at the receiving stop, at most 64. A module `WeakMap` keyed by the game holds them: never saved, never touching `nextId` or `randomAt`.
- `networkTotals(game)` returns `{owned, structures, upkeep, revision, tiles}`: the road and rail tiles the company built (`rail || road && !publicRoad`) and its bridge and tunnel tiles (`(bridge || tunnel) && (rail || !publicRoad)`). `maintenance()` counts them in the pass that sums network upkeep once per `networkRevision` and keeps the result in a module `WeakMap`; `networkTotals` recounts only when the revision or the tile array has changed. Achievements read it; the simulation never does.
- `routeBreakPoint(game, route)` returns null for a running route or one without a path. For a disconnected route it returns `{x,y,index}`: the first point of its last path, from the start stop, that fails `findPath`'s own tile (`validNetwork`) or edge (`networkEdgeAllowed`) rule, or the path midpoint when the gap lies elsewhere, such as a removed stop.
- Optional additional exports welcome. `model.js` must stay DOM-free for Node tests, apart from guarded localStorage.

`background-jobs.js` wraps creation, restoration and save encoding in cancellable module workers. `world-worker.js` uses the same model and codecs as synchronous callers. `world-transfer.js` transfers a four-byte tile buffer, sparse exact extensions, route-coordinate buffers and the procedural-save baseline rather than cloning millions of tile objects. Main-thread capture/hydration yields in small slices; the transfer format is internal and does not change local save formats. Unsupported/blocked workers fall back to the existing model.

`createGameAsync` and `restoreGameAsync` return hydrated games with a one-shot `preparedSave(game)`. `autosave-storage.js` commits that already validated JSON when a new or loaded company is activated. Its `noteAutosaveTime()`, also called by `app.js` `saveFinished`, records the wall-clock time of each autosave write under `transport-autosave-at` for the start menu's Continue line. Live autosaves hold edits and daily steps only during `captureGame`, resume before `encodeCapturedGame`, coalesce overlapping requests, and reject results from cancelled or replaced worlds. Vehicles keep moving inside the current day: tiles and route paths change only with edits or daily steps, and `captureWorld` clones all other state, including route state, before its first slice. Edits, a day boundary or a replaced route path during capture cause a fresh snapshot attempt. Periodic autosaves start in the first quarter of a day while running; construction strokes debounce their autosave by three seconds. A failed autosave, other than repeated snapshot changes, toasts once, marks `#game-menu-button[data-alert]` and `#save-status.save-failed`, and backs off to 60 seconds until a later save succeeds. Page-leave saves retain synchronous validation/encoding because the browser can stop workers during navigation. Save dialogs opt into cooperative capture with `capturePaused:true`; synchronous snapshot semantics remain available to older `writeSaveSlot` callers. Cancellation and storage failures preserve the previous complete slot.

State shape:
```
{version:1, seed, biome, width:512, height:384, size:'huge', tiles:Tile[],
 money:400000, day:0, totalDelivered:0, totalRevenue:0,
 monthlyIncome:0, monthlyExpenses:0, history:[], notifications:[],
 cities:City[], industries:Industry[], stations:Station[], routes:Route[], vehicles:Vehicle[], zones:Zone[], revision:0, networkRevision:0 }
```
`tiles[y*width+x]` = `{terrain:'grass'|'water'|'forest'|'mountain'|'rock'|'sand'|'snow', elevation:number, variant:number, detail?:string, publicRoad?:boolean, road:false, rail:false, bridge:false, tunnel:false, building:null|{kind: keyof BUILDINGS | 'house'|'apartment'|'shop'|'office'|'factory',level:number}, zone:null|'residential'|'commercial'|'industrial'}`. Roads and rails can coexist for crossings; bridges/tunnels terrain traversal. Coastline water has water neighbors; rivers same water.

City `{id,name,x,y,population,activity,growth}`. Industry `{id,kind,name,x,y,capacity,inventory:{cargo:number},production:number}`. Station `{id,name,x,y,mode:'road'|'rail'|'water'|'air',axis?}`, with `axis:'x'|'y'` on airports only. Zone `{x,y,kind,progress}`. Building and industry anchors carry an explicit `footprint` of 1–3 tiles per side; missing fields preserve legacy one-tile sites. Stops and ports remain one tile (an airport covers 6 × 2, see Airports and flights) and their piers can visually overhang. Terrain-object anchors carry `terrainObject: {kind, detail, variant, footprint:2|3}`. Child cells retain their base terrain and have no duplicate object. Route `{id,name,number?,mode,stops:[id,id],cargo,delivered,revenue,color,path:[{x,y}],active:true}`. Vehicle `{id,routeId,x,y,angle,load,capacity,progress,direction,loadedDay?}` uses tile-coordinate floating x/y, angle in radians; `loadedDay` is the boarding day of the cargo aboard (see Annual economy). A route runs one or more vehicles that reference it by `routeId`; `fleetIndex` groups them per revision. A vehicle's place in the round trip is its phase, `progress` outbound or `2L − progress` on the way back for a path of `L` tiles. `addRouteVehicle` starts the new vehicle at the middle of the widest phase gap (ties take the lowest start); within half a tile of a stop it starts there, loaded and departing. It needs no new saved field. Renderer must tolerate optional/missing stats.

Every city carries `mail`, the bags waiting for a mail route (see Mail between towns). `createGame`, a founded town and `restoreGame` start it at 0; validation accepts `undefined` or a finite number in [0, 1e9].

A city may also carry the four optional town-authority fields: `serviceMonths` (an integer 0–10, the reliability meter), `disturbance` (0–60, recent demolition), and `advertisedUntil` and `fundedUntil` (integers, the first day a town-hall action is over, at most 180 and 365 days after today). `createGame` and `restoreGame` never add them; readers treat a missing field as 0 or none. A city may also carry `market` (see `town-market.js` under Local simulation): `{wants, supplied, met, demand, shops, works, visitors, visitorsNow, bonus, bonusLast}`, written at the first month close or a served town's first arrival. A route may carry `marketBonus`, a history entry `marketBonus` and the game `monthlyMarketBonus`, each written only when a bonus was paid.

`createGame` starts with at least 3 cities, environment-specific industries, visible terrain varieties, an already working two-stop passenger road route and initial bus, plus an unconnected production opportunity. The starter city is centered near 43% of world width and 47% of height (recipe 8 takes the nearest dry, low and even site), with a second town 24 tiles to its east. Name taiga initial city Alderbrook. Starting roads avoid obstacles. Industry growth and zoning service depend on activity; connected routes earn income only by actual loading/delivery. Starting game economy net positive at 1x. Seed deterministically changes generated terrain.

## Freedom rules

Every system stays optional and safe to ignore. `tests/idle-company.test.mjs` leaves the regional taiga 1847 company alone for 30 years: money never falls from one year end to the next, the starter service reads *Running* every year with nothing to fix, no warning or error notice appears and the next goal never speaks of deadlines. Every new mechanic must keep this test green. A reward for engaging is fine; a loss or a warning for not engaging is not. Opportunities, such as room for another vehicle or a factory's other input, stay quiet hints where the player already looks; they never become warnings, attention counts or orange calls to action.

1. No mechanic may reduce what an unattended network earns, or make an asset decline over time. A factory takes and pays for every delivery of a cargo it lists, even once its store is full, so a route into a factory never stalls on an input the player has not supplied.
2. Transport Tycoon systems arrive only in reward-only form: yearly new models with an optional Upgrade, as today; subsidies as contracts without expiry nags; town growth from service; industry growth from service. Town needs follow this: missing cargo slows the next housing tier, and never stops or reverses it.
3. Never add breakdowns, aging or servicing; station-rating cargo loss; industry closures (idle sites never shrink below half capacity and are never removed); construction bans; bankruptcy or game over; AI competitors.
4. A new warning notice must come from a player action, such as bulldozing or disconnecting, or appear at most once per streak.

## Isometric presentation

`isometric.js` is a DOM-free projection shared by the renderer and new-world previews. World pixel positions project to `(x − y, (x + y) / 2)`, giving a 64×32 diamond for a 32×32 logical tile. The inverse is `(screenY + screenX / 2, screenY − screenX / 2)`. Camera coordinates remain unprojected world pixels. Pointer picking, screen-space pan deltas and zoom anchors use the inverse; game state, generation recipes, paths, distances and save data keep their existing square grid.

Ground, water and continuous networks occupy the projected plane. Upright artwork is positioned by projected anchors and sorted from back to front; interface labels stay in screen space. `projectAngle` projects each vehicle direction vector, so eight-direction artwork and load overlays follow the visible track. The flat overhead minimap continues to use world coordinates. New-world biome cards show miniature isometric landscapes using the same projection. `tests/isometric.test.mjs` covers corner geometry, inverse picking through 2048-tile maps, all eight vehicle headings and pointer zoom anchors.

All 27 houses and 51 civic/commercial climate variants were regenerated for the fixed camera; `assets/world/isometric-architecture-prompts.json` records the built-in imagegen prompts. `prepare-building-atlas.py` preserves disconnected source RGBA silhouettes in padded cells, then existing house/world packers create 256px masters and display densities. House atlas input can use `--normalize-atlas` for tier-specific widths and a common foundation line.

Town features added with recipe 8 (park, playground, swimming pool, sports field, tennis courts, ballpark, sports hall, town hall, café, pharmacy, bookshop) have no painted art yet. `town-feature-sprites.js` draws them in code on the painted buildings' plate, a 2:1 diamond centred at (16, 24) of the 32-unit sprite box; `tools/render-town-features.mjs` renders those drawings into the `buildings-town-features` 4 × 3 atlases, which `raster-buildings.js` loads like the painted families, so improved art replaces the PNGs alone. The code drawing is the fallback while an atlas loads. Their catalogue entries carry `since: 8`: `LEGACY_BUILDING_KINDS` and `LEGACY_COMMUNITY_KINDS` keep recipes 1–7 regenerating exactly the towns their saves were made from.

Streets are painted into the ground chunks by `renderer.js` `network()`. A public road beside a building or a zone (`townStreet`) gets sidewalks, and the scene adds a lamp on every other such tile and a bin on about one in five, on the side away from its road arms, skipped at Region zoom. A road tile in any all-road 2 × 2 square (`pavedSquare`) is painted as one asphalt surface without lanes, with a kerb and parking bays where it meets land; it remains an ordinary road for routes.

The later camera audit is recorded in `assets/world/camera-audit.md`. Active commerce atlases use `buildings-commerce-camera-v2`, replacing only bank, garage and hardware-store cells in all climates. Stops/ports and portals use their `-v2` siblings; stops and port art use square runtime bounds. These corrections preserve original source directories. Generated edges retain small painterly variations around the exact terrain projection. Small stone details are upright objects, like other authored nature art; they must not be baked into ground textures and projected a second time.

## Multi-tile terrain objects

`terrain-objects.js` resolves anchors from any covered cell with a bounded 3×3 lookup. A 2×2 or 3×3 site requires matching base terrain, an equal rounded elevation level throughout, continuous height variation of at most 0.3 levels, and at most 0.6 levels across its complete one-tile collar. Water, buildings, networks, zones and other objects exclude placement. The allocator does not flatten or change the original terrain.

`world-terrain-objects.js` uses sparse seeded candidates and a temporary byte occupancy mask to add occasional large groves, rock outcrops and mountain formations. Mountain anchors are retained for save compatibility but no longer rendered as scenery: their saved elevations produce the mountain geometry. A large forest/rock parcel is rendered only when every displayed grid vertex across its full footprint has the same height. Invalid parcels can use small scenery only on individually flat child cells, without changing save occupancy. Recipe 6 runs this after recipe 5's building allocation; recipes 1–5 remain available unchanged for procedural saves. Restoring a company without `terrainObjectVersion:1` safely allocates eligible objects once. Explicit anchors round-trip through existing sparse tile extras.

Successful construction dissolves intersected terrain objects into their remaining single-tile scenery. Forest and rock demolition clears the complete parcel for one charge, preserving elevation. Mountain formations retain the ordinary terrain/tunnel rules. Earthworks also dissolve objects whose smoothing collar was changed; ecological succession releases a parcel before changing one of its constituents. Rejected construction never alters a parcel. Validation checks shape, overlap, terrain and flatness before accepting a save.

The renderer suppresses small scenery over covered parcels, positions each large object on its full ground diamond and sorts by its front corner. Groves distribute separately sized trees across the parcel. Inspection and clearing highlight the whole footprint; parcel and opaque sprite picks resolve to the anchor. Terrain lookups use a bounded cache invalidated by the game revision. `groundIsFlat` checks the actual mesh vertices for single trees, rocks, plants, cached detail sprites, flower dots and shoreline reeds; slopes retain only their ground material. Hidden sloping trees also omit their water reflections. `rasterForestComposition` is shared by generated tree artwork and the separate ground-shadow pass. Shadow stamps use a 32 MiB LRU and render before upright objects; visibility and flat-ground checks are shared with the trees. Nearby height edits invalidate cached decoration choices through the existing geometry fingerprint halo.

## Local simulation

`environment.js` is DOM-free and exposes:

- `randomAt(game, day, key, salt=0)`: a stateless sample derived from seed, integer day, entity/cell key and decision channel. Camera renders, frame rates and save restoration cannot consume or reorder random samples.
- `weatherAt(game, x, y, day=game.day)`: spatially blended weather fronts and seasonal/biome/elevation effects, returning `wetness`, `cold`, `heat`, `growth` and `travel` factors.
- `localEnvironment(game, x, y, radius=3)`: a bounded neighborhood survey of infrastructure, vegetation, moisture, housing, shops, services, civic amenities, industry, pollution and active station coverage. Local road access uses adjacent tiles; rail access extends two tiles; active station coverage extends five tiles.
- `hasRoadAccess(game, x, y)`: the same road-access test for a one-tile site (a road in its 3 × 3 ring), used by zone quotes.
- Natural growth (`settlements.js`) prefers level plots: a town's own homes take the best level lot in reach, then the best of the top six sloping lots it can level, then any lot. After placing any grown building, `plotLevelPlan` (`terrain-engineering.js`) moves the plot's corners for free to the height needing the fewest steps, unless a corner shared with a street, another building, a site or water would move or a protected corner nearby would settle with it; empty zoned plots count as open land. A day that levels a plot is not journaled as a sites change, so views rebuild their height-dependent caches.
- `stepEcology(game)`: a daily sparse, asynchronous Moore-neighborhood update. It samples at most `min(4096, ceil(tileCount/128))` cells, buffers changes, then commits together. Grass, sand, snow and forest undergo local vegetation succession; water, mountains, rocks and every occupied/reserved plot remain protected. It returns the changed-tile count.

`settlements.js` exposes `stepSettlements(game, {extendStreets, reserved})` for daily passenger demand, activity/supply decay, organic infill and zone development, plus `settlementSuitability(game, point, kind)` for the inspector's score and short positive/negative explanations. Decisions use seeded per-entity opportunities and local conditions. Building changes commit after proposals are collected, so new neighbors cannot trigger same-day development cascades. Organic growth only occupies vacant plots with road access; paid structures and civic landmarks are retained. Population rises when housing is actually added. Zone development requires a local road and either recent deliveries or active town funding; stalled interest can fade without deleting occupied buildings. A funded town's zones pass that gate and take twice the increment as its last factor; a zone more than 10 tiles from every centre has no town, so it is never funded. `infillChance(quality, demand, weatherGrowth, growthFactor, funded, homesBar)` is the salt-104 organic chance, shared by the daily roll and the forecast so they cannot drift apart. `fundForecast(game, city)` → `{served, plots, zones, homes, residents}` is the town hall's pure read, memoised by town, day and revision: zoned tiles under progress 3 with a road beside them that the town owns (a developed 2 × 2 counts four), the outlook's free plots, and the homes a funded year would build there at `infillChance` over the year's mean weather growth (the 15th of each 30-day month, memoised per town and year), halved for the radius roll and failed sites and capped by the plots, at 12.67 residents each rounded to tens. It never draws `randomAt`.

Organic infill draws a radius of `3 + ⌊rand·4⌋ + min(3, ⌊√(population / 400)⌋)` and shares one lot filter (`openLot`) with street growth: grass, sand, snow or forest without a building, zone, road, rail, station, industry or town center, and not the three tiles at +x, +y and +x+y of a zone, which its 2 × 2 upgrade may still need. When a served town's draw finds no lot, a street may follow: no lot with a road beside it anywhere within the full reach (`6 +` that bonus), demand of at least 1, 30 days since its optional `lastStreetDay`, and `randomAt(…, 107) < .08 × demand × weather.growth`. `townStreet` then extends a road within reach + 2 by two or three straight tiles in any direction that does not point back toward the center. Each tile is open ground (never water, rock, mountain, a bridge, tunnel or span, a zone or its upgrade room, a building, site or terrain parcel), has no road alongside, passes `networkTerrainProblem` along its axis, lies more than two tiles (Chebyshev) from every station and rail tile, and is not in `reserved`, the construction preview the app passes through `tick(game, days, {reserved})`. The street must open at least one lot within reach; the most lots, weighted by a seeded draw (salt 108), wins. At most four towns lay a street per day, and all their tiles go to `extendStreets` once, before any building commits: `tick` passes `placePublicRoads`, which sets `road`, `publicRoad: true` and an empty `detail` (forest becomes open ground) and calls `invalidateNetwork` once. Public roads carry no upkeep, the procedural save delta already encodes them, and `lastStreetDay` validates as finite in [0, `game.day`]. Calls without `extendStreets` never lay streets. Generated towns sit on graded platforms whose connecting roads often ramp sideways, so most of their edges fail the grade check; the node tests use a flat fixture, and `tests/town-streets-browser-check.mjs` loads it the day before its first street to confirm that a held road stroke keeps those tiles for the player.

`townOutlook(game, city)` returns `{plots, reach, growth, change, days}` for the town inspector. `plots` counts the lots the street trigger looks for (`townLots`: a road beside a house-ready `openLot`) within the full reach `6 +` bonus, so a served town with zero plots is one that may lay a street; `growth` is `city.growth`. `change` and `days` come from `townGrowth(game, city)`: the residents gained since the oldest entry of the town's optional `popHistory` and the days since the first of that month, or `null` before the first count. `monthlyUpdate` pushes `floor(population)` onto every town's `popHistory` and keeps the last four; validation accepts `undefined` or at most 12 finite values ≥ 0, so legacy towns load and start counting at the next month. The outlook is cached per game by `floor(day)`, `revision` and city id. The Towns list calls only `townGrowth`, which is O(1), for its *Growing* tag.

`townNeeds(game, city)` lists four needs in a fixed order: comfortable homes (food), prestige homes (goods, furniture or machinery), services (goods or fuel) and construction (stone or cement), each filtered to cargo the biome's industries make. A need is `met` when any of its cargo reached the town within `NEED_WINDOW` (120) days. `model.js` records that day in the covered town's optional `lastSupply[cargo]` whenever town cargo unloads; validation accepts only `TOWN_CARGO` keys with days in [0, `game.day`], and legacy towns simply have none. A zone's increment is multiplied by 0.25 while the need of its next tier (`floor(progress) + 1`) is unmet, and by 1.3 while construction is met. Needs never lower stored progress or stop development, and organic infill ignores them. `settlementSuitability` returns an unmet next-tier need as a neutral `notes` entry ('Faster with food deliveries'), never as a negative. The town inspector's Town economy fold names the cargo only while a need is slowing one of the town's zones (a zone of the town, by `townOf`, whose next tier is unmet); the Towns list shows only cargo a town has received.

`town-market.js` is DOM-free and makes each town a small market. It imports `buildings.js`, `building-sites.js`, `simulation-spatial.js`, `environment.js`, `economy-pricing.js` and `town-authority.js`, re-exports `TOWN_RADIUS` (10) and never imports `model.js` or `settlements.js`; both import it, and `settlements.js` `nearestCity` is `townOf(game, x, y)`: the town at the smallest `Math.hypot` distance strictly under 10, the first in `game.cities` on a tie. `townLedger(game, city, zoneMap)` reads the tiles strictly within 10 of the centre once, without allocating per tile, and keeps those no other town is nearer to (squared distances, so a tie is exact and goes to the town first in `game.cities`): homes, shop units (shops, services and legacy shops and offices, by level), outlets per family (`OUTLET` by kind, plus the level-1 shop a developed commercial zone grew from, so an upgrade never loses one; the pub sells food), workshops (`factory` levels), landmarks and developing zones (progress under 3 with a road in their 3 × 3). `reviewMarket` closes a month when asked (met share per family, the month's visitors and bonus), sets the three demand bars and next month's wants, and resets the month: homes `.5·service + .25·amenity + .25·jobs`, where service is `.6 + .2` per stop (at most 1) for a town served within 60 days; shops `(shoppers ÷ (200·shops + 100) − .5) ÷ 1.5` with shoppers the residents plus twice last month's arriving passengers; workshops half the materials in stock (0 until workshops take deliveries) plus half the unfilled jobs in towns of 150 or more; each rounded to hundredths. Wants are `residents × MARKET.perResident × min(1, outlets × reach ÷ residents)` for food, household cargo (the biome's `HOUSEHOLD`) and fuel, and building materials `min(6 × developing, round(.1 × residents) + 24)`. `monthlyMarkets(game)`, the first statement of `monthlyUpdate`, closes every town in order with one stop count and zone index, so rent or other close steps later items add to `CLOSE_HOOKS` land in the closing month; hooks run only there. `recordTownSupply` (called when town cargo unloads, receiver `coverage.cities[0]`) and `recordVisitors` (arriving passengers only, never mail) create a first-need market from `floor(day)` state and are O(1) afterwards; `recordTownSupply` returns the units still wanted, and `unloadVehicle` adds `round(.25 × fare × wanted ÷ delivered)` to the fare, contracts still paying on the fare alone. `marketView(game, city)` is the pure read for the interface and forecasts: the saved market, or a preview built into a fresh object. Demand scales the zone increment by `1 + .5 × bar` (never while a town need is slowing that tier) and the salt-104 infill chance by `1 + .5 × homes`, after opinion and funding; it never slows anything, adds no `randomAt` salt, notifies nothing and spends no `nextId`. `validMarket` accepts exactly the keys in `MARKET_KEYS`. A market is about 270 bytes of JSON, 86 KB for the 320 towns of a 2048² world, and the monthly pass there takes about a third of one day's tick.

Workshops are town `factory` buildings, developed from industrial zones or placed with the `workshop` tool (`BUILD_COSTS.workshop`; not a `BUILDINGS` entry, so the sprites' `factory` branch draws the biome's works). `data.js` `WORKSHOP` (`{cost: 12000, footprint: 2, rate: .5, store: 150, ratio: 2, maxLevel: 3}`) and the frozen `WORKSHOP_RECIPES` (taiga lumber to furniture and steel to machinery, tundra steel to goods, desert glass and copper wire to goods, worked in that order; no output is any recipe's input, so cargo cannot loop) set the rules. `town-market.js` derives `workshopLevels(game, city)`: the levels of the `factory` anchors within ±10 tiles that `townOf` gives the town, equal to `townLedger(…).works`. It is never saved and is memoised per game by `revision` and the `cities` array and length, counting only the towns asked about; there are no hooks, because placing, developing, expanding, bulldozing, undoing and founding a town all move one of those. `workshopInputs` are the recipe inputs while the levels are at least 1, and `workshopOutputs` the distinct outputs while they are or while a product stock of 1 or more remains, so stock stays loadable after demolition. A town's stock is the optional `city.workshop` `{input, output}`, created by its first materials delivery and validated to the biome's recipe inputs and outputs with finite values in [0, 1e7]. `stepWorkshops(game)`, in `tick` right after `stepIndustries`, visits only towns holding input: each level works `rate` a day, recipes in order, while `levels × store` leaves room for the product (a full store pauses and loses nothing), adding what it worked to the market's optional `processed`; once a town has had workshops, its month close sets the optional `utilization = processed ÷ (works × rate × 30)`, clamped, from the ledger and resets `processed`. `acceptWorkshopInput` stores what fits in `levels × store` and returns every unit, so materials are always taken and paid at the ordinary fare. `expandWorkshop(game, x, y)` in `model.js` adds a level, up to 3, to a workshop the player placed (`owner: 'player'`, with `paid` its running cost; both validated on any building) at `priceFor(12000)`, with no notice; developed workshops grow with their zone. `settlements.js` `workshopAnchor(game, x, y, existing)` sites a developing industrial zone's workshop: in place over its own, else the square among the four holding the tile with the most industrial zoning, anchored on an industrial zone record, holding no other zone kind and clear for `buildingSiteProblem`; ties keep the order (x, y), (x − 1, y), (x, y − 1), (x − 1, y − 1). A lone tile therefore still grows over clear land to its SE, and a zoned block at its NW tile whichever tile is ready first. `settlementSuitability` lists *Needs 2 × 2 clear tiles* for an industrial zone exactly when it returns null.

Company property is what the player paid for in a town, derived from the tiles with no ownership list. A plot is a building whose anchor tile carries `tile.zone` (zones are only ever painted by the player); an owned building has `owner: 'player'`, which `build` sets with `paid` (the price paid) on catalog homes, shops and services and city-workshops sets on placed workshops. Community buildings never get an owner, and legacy catalog placements stay the town's. `propertySector(kind)` is `homes` (the homes group, legacy house and apartment), `shops` (shops and services, legacy shop and office) or `works` (`factory`); anything else is never property, whatever its owner field says. `townLedger` also returns `plots` and `owned`, entries `{x, y, kind, level, tiles, sector, family, zoneKind?}`, allocating only for property tiles. A plot's ground-rent `tiles` is `zone.tiles ?? 1` from its anchor's `game.zones` record, never the footprint: `building-sites.js` `placeBuildingSite` with `allowZone` adds the records it removes inside the footprint to the anchor's optional `tiles` (validated as an integer 1–9), because a level-3 home or level-2 shop may spread onto empty, unzoned neighbours and rent must follow the land that was paid for; a plot consolidated before this counts 1. The frozen `GROUND_RENT` `{homes: 8, shops: 10, works: 12}` (1950 dollars a ground-rent tile and level a month), `BUILT_YIELD` .016 a month and `OCCUPANCY_FLOOR` `{homes: .6, shops: .4, works: .3}` set the rent: `propertyBase(p)` is `GROUND_RENT[sector] × tiles × level` for a plot and `BUILT_YIELD` × the catalog cost (`WORKSHOP.cost × level` for a workshop) for an owned building, and `propertyOccupancy(market, p, population)` is the floor plus the rest times a signal: the homes bar, a shop outlet's `met[family] × saturation` (the family from `OUTLET`, or the shop a commercial zone grew from), `saturation` for other shops (`(residents + 2 × visitors) ÷ (200 × shop units)`, clamped), or the workshops' `utilization`. `bookRent`, a `CLOSE_HOOKS` entry that runs after the bars and workshop use, prices each town's `Σ base × occupancy` with `priceFor` and books it into `money`, `monthlyIncome` and the optional `monthlyProperty` and `totalProperty`, never into `totalRevenue` or route accounts; once a town has had property its market keeps `rent`, `plots` and `owned` (optional `MARKET_KEYS`, 0 after a sale), and a town that never had any keeps its market as it was. A renting town also pushes `{cityId, x, y, rent, day}` to a module `WeakMap` log of at most 64 that `drainPropertyEvents(game)` empties, the same pattern as `drainDeliveryEvents`: never saved and never read by the simulation. `monthlyUpdate` runs `monthlyMarkets` first, so rent lands in the closing month's income, profit and operating profit; the history entry gains `property` only when above zero and `monthlyProperty` is deleted. `propertyValue(game, p)` is today's replacement cost (`priceFor` of the building, or of `BUILD_COSTS[zoneKind] × tiles`); `propertyAt(game, x, y)` returns `{kind: 'plot'|'owned', sector, family, level, tiles, town, occupancy, rent, value, paid}` for any tile of a site, or null, reading the town's `marketView` (occupancy and rent share from the last close; a countryside building has no town, 0 rent and 0 occupancy). `townHoldings(game, city)` counts a town's plots and buildings today, and `companyProperty(game)` lists every town's, memoised by day and revision, for the Company report and company value. `model.js` `sellProperty(game, x, y)` refuses a zone tile or empty tile (*Only buildings you placed can be sold.*) and any other building without a player owner or property sector (*This building is not yours to sell.*) without changing anything; otherwise it deletes `owner` and `paid`, adds `round(SALE_SHARE × propertyValue)` (60%) to money and bumps `revision`, with no notice. The building stays exactly as it is, homes with their `populationCityId` and a workshop with its level and stock. Rent is booked in `game.cities` order with integer money inside the existing monthly pass, with no `randomAt`, `notify` or `nextId`; a company without property saves byte for byte as before. In `app.js`, a building's inspector adds `propertyHTML` (rent and occupancy, worth and price paid, one hint naming the transport lever, and **Sell** confirmed in place through the session-only `sellAsk`), the Town economy fold names last month's rent in its summary and ends with **Your property**, the finances card's `#rent-row` shows the last history `property`, and `openCompany` inserts the Property section before the loan. `rentSeen` is seeded from `totalProperty` at startup and in `activateGame`, so the first-rent toast in `updateHud` shows once and a reload never replays it.

Investment forecasts and returns (city-investment-feedback). `town-forecast.js` is DOM-free and read-only; `app.js` is its only importer (never `model.js`), and it is in `APP_PRELOAD`. It exists because `town-market.js` cannot import `settlements.js`, whose `zoneServiceActive(game, city, served)` is the zone loop's own gate, `recentlyServed || fundedTown(city, game.day)`, now called by `stepSettlements` with its `connectedCities` (bit-identical to the old condition), and whose `servedTownSet(game)` is `activeCities` kept in a `WeakMap` while `floor(day)`, `networkRevision`, the town count and the running routes' stops stay the same. `matureLevel(game, kind, x, y)` walks levels 1-3 of `residentialKind`/`commercialKind` for the tile's variant and stops before the first 2 × 2 kind, since a zoned block has no free land to spread onto: homes settle at 2, shops at 3 or 1. `zoneForecast(game, kind, placements)` takes the quote's placements in state `ok` (their prices are the cost): a tile no town owns (`townOf`) counts in `far`, one without a road in its 3 × 3 ring (`hasRoadAccess`, the development test) in `roadless`, and the rest group by town. Occupancy is `propertyOccupancy` over the town's `marketView` (the saved market, or a preview that writes nothing), so homes follow the homes bar, shops their stocked shelves times shoppers, and workshops their use, each above its floor. Residential tiles give `housingCapacity` and `GROUND_RENT.homes × level`; commercial tiles `GROUND_RENT.shops × level` and the wants their outlets add, `wants(P, outlets + Δ) − wants(P, outlets)` by city-market's formula with `townLedger`'s outlets and the family a zone grew from counted as the ledger counts it (the largest family is reported); industrial strokes count disjoint 2 × 2 squares, row by row, over the stroke's tiles in a town and vacant industrial zones already there, each needing one new tile and one tile beside a road, at 3 levels, 7.5 products a level and `GROUND_RENT.works × 4 × 3`. Rent is `priceFor` of that sum, and payback `ceil(cost ÷ rent) + FORECAST.monthsToBuild` (6) months; both are null until one of the towns passes the gate. `buildingForecast(game, kind, x, y)` gives a placed home, shop, service or workshop the rent `priceFor(BUILT_YIELD × cost × occupancy)` of the town nearest its anchor (0 in the countryside), `stockedRent` with the shop's family met, and payback `ceil(priceFor(cost) ÷ rent)`; community kinds return null. Both keep their last answer keyed by the tile list, `floor(day)`, `revision`, `networkRevision`, the served set and the funded towns (funding moves no revision), and per-town market views once a day and revision; they never call `ensureMarket`, draw `randomAt`, notify or spend `nextId`. `forecastNote(game, tool, placements)` words the tip's second line; `placementNote` returns it as `forecast`, and `updatePlacementTip` appends it as a `.tip-forecast` span after its unchanged quote line, never when the quote is refused.

Each town's market keeps a ledger of what the company earned there. `worksFreightNow` (optional, 0-1e12) collects the month's workshop freight in `unloadVehicle`: materials the town's workshops took credit that town `round(revenue × their units ÷ units delivered)`, so an industry at the same stop keeps its share; a product delivery credits `revenue − market bonus` to the first town at the loading stop that `loadVehicle` would take it from (one the end stop does not reach) and whose `workshopOutputs` hold it, but only when no industry at the loading stop makes that cargo, since the load may have come from there. `recordWorksFreight` never creates a market. `bookReturns`, the last `CLOSE_HOOKS` step after `bookRent`, appends `[rent, bonusLast, worksFreightNow]` to `returns` (optional: 1-12 entries of three finite numbers in 0-1e12, oldest first, the last the month just closed) once the town has earned anything, drops `returns` after twelve months of nothing, and resets `worksFreightNow` to 0; a town that never earned keeps neither key, so an idle company saves byte for byte as before. Twelve months of seven-digit entries in all 320 towns of a 2048² world add about 100 KB to its autosave. `returnsTotals(market)` sums the ledger for the Town economy line (`townReturnsHTML`, with `miniSpark`, the 72 × 18 line the Company report's rent shares), the Towns list's **Your property** row and sort, and the report's **Past 12 months** column. The map's property outlines are view state only: while the renderer builds its scene list it records the anchors of owned buildings and developed plots on the scene cache (rebuilt with it on revision or camera changes, never saved and never read by the simulation), and its overlay pass strokes them, when `app.js` passes `propertyOutlines` (Build › Town open or one of its tools in hand, or an inspected town, plot or owned building) and the zoom is Town or Detail, as two cased strokes in `MAP.property`; `getStats().propertyOutlines` counts those drawn.

`model.js` `freightFits(game, source, destination, cargo)`, over two `stationCoverage` results, is the one freight rule for `planRoute`, `freightPair` and `route-planner.js`: the industry rule first and unchanged, so existing routes validate identically; then source towns the destination does not cover whose `workshopOutputs` hold the cargo, and destination towns whose `workshopInputs` hold it (or, for `TOWN_CARGO`, any that is not such a source). `stationCoverage` adds each covered town's workshop outputs to `produces` and inputs to `accepts`. When neither direction fits because a town both stops reach makes the cargo, `workshopLoop` gives the refusal (*Furniture from Alderbrook workshops must go to another town…*). `loadVehicle` at the first stop takes towns' products after the industries', only from towns the end stop does not cover, so same-town loops need no vehicle field; `unloadVehicle` hands materials to the first covered town with workshops before the `TOWN_CARGO` branch, counting a delivery and a service day, and products delivered to another town go through that branch and can earn the household market bonus. The fleet codec is unchanged. `routeHealth` counts town sources and buyers (*Needs lumber* while a town source has neither stock nor materials), the forecast has a town source send `levels × rate × utilization ÷ ratio` a day (nothing until a month has closed, flagged `workshopsPending`), `defaultRouteName` names such an end *Alderbrook workshops*, `findIndustryTargets(…, {workshops: true})` (the industry inspector only) lists towns whose workshops take an output, `townLensRole` gives towns their lens chips, and an opening's partner may be a town whose workshops buy an output. Nothing here spends `nextId`, draws `randomAt` or notifies.

`town-authority.js` is DOM-free and holds each town's opinion of the company (Transport Tycoon's local authority, made gentle). It imports only `data.js`, `economy-pricing.js` and `simulation-spatial.js`. `townStopCounts(game)` maps each town to the stops of active routes within five tiles of its centre; `activeCities` is its key set, so membership is unchanged. `townOpinion(game, city, stopCounts)` returns `{score, label, growth, reasons}`: 50 plus 2.5 per month of `serviceMonths`, 5 per stop (at most two), 5 per `TOWN_CARGO` delivered within 60 days (at most two) and minus `disturbance`, rounded and clamped to 0–100, then named by `OPINION_BANDS` (Appalling below 15 up to Outstanding from 90). Only Excellent (1.05) and Outstanding (1.10) carry a growth factor above 1; no band is below 1. `monthlyTownRelations(game)` runs in `monthlyUpdate` after the history, `popHistory` and annual close: a town served within 31 days gains a month, one without loses one, `disturbance` fades by 5, and expired `advertisedUntil`/`fundedUntil` keys are deleted, with keys removed at 0. Bulldozing in `build()` is the only source of disturbance: 6 for a building the town owns (`populationCityId`) or, without an owner field, stands within `TOWN_RADIUS` (10) of, nothing for countryside homes with a null owner, and 1 per woodland tile (a whole grove parcel counts once) for the nearest town within 10 tiles; industries, stops, zones, roads, rails, rocks, levelling and simulated redevelopment never disturb, and `disturbTown` caps it at 60. Construction undo records each town's applied change and subtracts it, clamped at 0. `buyTownAction(game, cityId, 'advertise'|'fund')` in `model.js` charges `townActionQuote` (base plus a per-resident price through `priceFor`, rounded up to $100) as investment spending and sets the until day; a running action, a missing town or too little money is refused without changing anything. `fundedTown(city, day)` is `actionActive(city.fundedUntil, day)` and false for no town. `passengerArrivals` multiplies by 1.5 while advertising, so the route forecast sees a campaign; funded towns (the town hall's Fund development) develop the player's zones without service at twice the step, their suitability reads 'Development funded' instead of 'Needs deliveries' at an unchanged score, and they pass the organic infill gate without service or activity, with demand of at least 1 and twice the chance, and may lay streets the same way. Opinion scales only the salt-104 infill and salt-107 street thresholds, and only upward; it never touches `nextId`, adds a `randomAt` salt, notifies or bumps `revision`, and it never blocks construction or changes fares or loading. The app celebrates a town's first Outstanding opinion once a session, seeded in `resetMoments` so a loaded save replays nothing.

`industry-simulation.js` exposes `initializeIndustry(game, industry)`, `stepIndustries(game, notify)` and `industryConditions(game, industry)`. The inspector's productivity score and reasons use the same resource, access, neighboring structure and weather inputs as production. Industries save `lastProductionDay`, `nextProductionDay` and `nextReviewDay` for staggered work and capacity reviews. Production respects complete recipe proportions, available inputs and warehouse space. A capacity review grows a site only while every output store is under half full; a fuller store holds capacity, so a site served by too few vehicles stops expanding. Only idle sites shrink, never below their stock, so no cargo is lost. `outputFill(industry)` returns the fullest output store as a 0–1 share for the expansion notice, the inspector's Storage cell and `industryStatus(industry, game)`, which reports a half-full store as `backlog` and, given the game, names the active route that loads there.

`model.js` advances these processes at simulation-day boundaries, while vehicles move continuously between them. Fleet events advance in chronological order so vehicles competing for limited inventory receive the same cargo regardless of frame partitioning. Vehicles save `dwellRemaining` and `tripSerial` to preserve seeded loading waits. Monthly reporting remains a calendar operation.

Full load (ttd-full-load) is Transport Tycoon's order, optional and for freight only. `route.fullLoad` is absent until the player turns it on (`true`, and `false` once turned off). `vehicle.fullLoadSince` is absent until a vehicle of such a route first waits: it holds the exact simulation day the wait began (the arrival time from the event heap, or `game.day` at a purchase) and turns `null` when the wait ends. Neither field is ever deleted at runtime, since deleting a non-last property drops V8 objects into dictionary mode inside the fleet loops; routes and vehicles that never use the order never gain either field, so they simulate and save byte-identically. `loadVehicle` returns the sources a freight start has: the covered industries that make the cargo, counted whatever their stock, or without one the towns whose workshops could load it there; anywhere else 0. `beginFullLoadWait` starts a wait after the load at stop 0 when the route asks for full loads, the cargo is not town traffic, there is a source and the vehicle is short of full: in `arriveVehicle` after the unchanged dwell draw (the stored dwell runs once the wait ends; planes carry only town traffic and return before it), in `addRoute`, and in `addRouteVehicle` for a vehicle placed at stop 0. `travelPlan` holds a waiting vehicle by giving it no time to spend instead of returning early, so anything its tail counts per elapsed day still counts the wait; it never arrives, and `moveVehicles` recomputes its position facing outbound. `serveFullLoads` runs in the daily block right after `maintenance`: one index loop collects the waiting vehicles (allocating only when it finds one), sorted by `fullLoadSince` then array order, and each retries stop 0 at the integer day. A vehicle of a missing, switched-off or town-traffic route, or one no longer at stop 0 facing out, is released; a broken route stays frozen; any other loads, and is released when full, when its stop has no source or after `FULL_LOAD_MAX_WAIT` days. Producer stock grows only in `stepIndustries`, so within a day it can only shrink, and every partition of a tick meets the same integer boundary: retries are exact, and the line is first to each day's output. The pass uses no `randomAt` or `notify` and leaves `nextId`, `revision` and `networkRevision` alone. `maintenance` charges a waiting vehicle the idle factor .45, the same single factor as a vehicle on a disconnected route (`route?.active && !waitingForFullLoad(v) ? 1 : .45`), so the two never stack; it runs before `serveFullLoads`, so a day is charged by whether the vehicle waited through it. `editRoute` releases the route's waits after snapping its vehicles and keeps `route.fullLoad`. Validation accepts `route.fullLoad` undefined or boolean and `fullLoadSince` undefined, null or finite in [0, `game.day`]; `restoreGame` releases a wait whose route does not ask for full loads and turns a passenger or mail route's `fullLoad` off. `fleet-save-codec` gives vehicles carrying the field their own schema, keeps null in JSON and packs numbers exactly.

`revision` describes visible world changes. `networkRevision` changes when transport infrastructure changes; pathfinding and the cached base infrastructure upkeep use this separate revision. Growing trees or houses therefore do not force routes to replan or recount the entire huge world. Optional simulation fields are validated when present; legacy saves receive deterministic defaults on load. New simulation state remains JSON-serializable and fits the existing compact save envelope.

`network-index.js` also journals the cells each `invalidateNetwork` touched, per company and never saved: at most 64 revisions or 16,384 cells. `networkChangesSince(game, revision)` returns them for `(revision, networkRevision]`, or null after an overflow, a gap, replaced tiles, a restored company or a fixture that set `networkRevision` itself. `updateRoutePath` keeps a running route's path, vehicles and notices and only advances `pathRevision` when the path still joins its current stops a and b and every changed cell c lies at |a−c|+|c−b| > L+2, for path length L. The comment above `unaffectedPath` gives the argument for breadth-first search and A*; any other route searches again as before. `setNetworkJournalEnabled(false)` lets tests compare against a full search of every route.

`change-journal.js` records which cells each ecology day rewrote. `stepEcology` notes its proposals plus every footprint cell of a grove or outcrop it dissolved (`releaseTerrainObjectsCells`, while `releaseTerrainObjects` still returns the dissolved count) under the one revision it creates. `surfaceChangesSince(game, revision)` returns the sorted union only when such entries cover every revision since then for the same `tiles` array. Any other revision, a gap, more than 64 entries or 65,536 cells, or a replaced tile array returns `null`. The journal is never saved and no simulation decision reads it. Ecology never changes heights, water, structures or sites, so the renderer keeps its building, parcel, station and industry indexes, foundations, grid and route paths across a journaled span. It forgets only the changed parcels and fingerprints only cached chunks whose bounds, padded by three tiles, contain a change; every other chunk current at the previous revision is marked current. Those chunks are `lazy`: they keep their last picture and recompose at most two a frame (`LAZY_CHUNKS_PER_FRAME`), queueing another frame through `onInvalidate` while any wait; a render with `view.settle` (the app passes it while paused) finishes them all at once; a structural revision clears every `lazy` flag so the player's own change recomposes at once. The scene is patched rather than rebuilt: every static object and shadow carries the tile that made it, `refreshSurface` marks the changed cells and their two-tile reach (a grove's anchor, a forest's neighbours) in `sceneCache.dirty`, and the next `drawScene` removes those tiles' objects and shadows and runs the same per-tile builder (`tileScenery`) for them at the camera the scene was built from, so the list equals a rebuild's. Objects sort with `staticCompare` (the depth key, then the tile) so equal keys keep the row-major order. Prepared strips hold one depth each, so `regroupScene` partitions only the touched depth runs again and keeps every other strip's picture; a changed shadow list stages a new layer while the old one stays on screen; a second change before that layer is ready drops the old one for the direct pass instead of showing a layer two patches old, and an unchanged list lets a layer still being painted carry on. When the 96 MiB budget cannot hold every strip and the layer, a fresh scene's allocation order decides which strips get pictures, so the patch releases them all and starts that order afresh. More than 6,000 marked tiles rebuild the scene. A day of town growth is journaled too: `stepSettlements` notes the footprints it built on, the old footprint of a building that moved and any grove they dissolved with `noteSiteChanges`, and `viewChangesSince(game, revision)` returns `{surface, sites}` across contiguous surface and site entries. The renderer treats site cells like surface cells, also forgets their cached building sites and foundations, and advances a `siteRevision` in the overlay placement key so markers and nameplates make room for the new homes. `surfaceChangesSince` still answers `null` across a site entry, so terrain geometry and the mini map rebuild after new homes as before. `getStats()` reports `scenePatches` and `lazyChunks`, and `sceneryBatches.pending` counts waiting chunks and an unapplied patch. `null` restores full invalidation, and route paths are keyed on a renderer-local structure revision that advances only then.

## Recipe 8 landscape and towns

New square worlds use recipe 8, three modules in one pass: `world-terrain-v8.js` shapes the land and water, `world-v8.js` settles towns and places industries on their final footprints, and `world.js` adds the recipe-6 groves (`allocateTerrainObjects`). Recipes 3–5's industry and plot passes are not used: every site is valid when placed.

- Fields live on a four-tile lattice: a coast on one map edge (as recipe 2), relief that rises inland, warped hills and ridged mountain ranges confined to a few regions. Hill and range scales are capped in tiles, so larger maps gain more of them instead of stretched ones; inland edges rise slightly so rivers cross them.
- Drainage is a priority flood from the open sea (the ocean component touching the sea edge). Random step costs across flats grow a branching tree instead of lattice diagonals. Rain per climate (`CLIMATES`) accumulates downstream; a cell carries a river once its flow passes the climate's threshold. Basins deeper than the climate's lake depth hold lakes (each keeps at most its deepest cells); a desert has no lakes, its basins dry into salt pans, and an exotic river enters on the edge facing away from the sea.
- Rivers trace the drainage tree from each source to the sea, a lake or the river they join, through jittered lattice points (confluences meet exactly), as Catmull-Rom curves that widen with flow and meander along wide lowland stretches; a channel leaving a lake starts on the lake's cell and one reaching the sea runs on offshore. Every kept lake cell holds water around its own point, and any channel that still loses the sea becomes still water, so every `detail: 'river'` tile belongs to the one network ships can follow.
- The opening keeps recipe 2's contract: towns 24 tiles apart on one row, a straight 25-tile starter road and river berths at `(x, y + 5)` of both centres with a broad channel between them. `openingSites` scores dry, low, even sites by distance from 43% / 47% of the map; `openingChannel` bends a channel through both berths and joins it to the drainage tree, a natural stretch upstream and the tree down to the sea. Candidates that share drainage are skipped, so each attempt tries a new spot.
- After painting the water, a distance transform gives each tile its distance to water and that water's channel radius. Land beside a river is a flat floodplain (wider along big rivers), then valley sides rise at most one level per `VALLEY[biome]` tiles. Tundra adds shallow ponds on flat lowland that carve no banks.
- Vegetation follows moisture, elevation and water: taiga forests with birch and aspen in wet lowland, pine on dry rises and spruce or fir between, bogs and reeds by the water; tundra woodland only in sheltered valleys, cotton grass and willow by water and snow on the uplands; desert green belts along rivers, whose width follows the channel, with dunes, salt pans and scrub, cacti, Joshua trees and acacias on dry uplands. Every listed tree, plant and mountain detail of each climate appears.
- Town sites are dry, even tiles a few tiles back from water, scored by flat room within six tiles, shore distance (decisive in the desert), river size and a regional noise; the best, roomiest tenth become cities. Each town drains ponds within its radius and lowers tiles one level above its usual level, so streets and buildings stand flat (stone plinths drop from about 9% of generated buildings to under 1%). The opening road runs on a levelled bed.
- Streets: a main street along the axis with more open ground (east–west for the opening towns), cross streets every three to five tiles and, from village size, back lanes joining them; a city has a second ring. Streets run on flat ground or straight up a slope along their own axis and may bridge up to four tiles of water to a dry bank; a centre too steep for a street moves onto the main street beside it. Civic kinds come from the town's profile with a chance each (`PROFILES`) and stand at a share of the radius from the centre (`PLACE`): the town hall, church, pub and post office in the core, parks, schools, playgrounds and police further out, sports grounds, garages, stadiums and ballparks at the edge, every building within the ten-tile town reach (`REACH`). Shops line the centre; homes fill the remaining frontage, denser and grander inward, with prestige houses on roomy plots further out. The opening town shows a showcase set, and a final pass gives every building kind a home in the largest towns. Woods around a town open into farmland out to a ragged edge.
- Industry districts take their first anchor at the opening town and spread out by farthest-of-six towns. Extraction needs its resource nearby (`deposit`), factories stay just outside towns, and corner height differences are penalised so sites stand flat. A byte mask rejects taken tiles; the deposit test and `industrySiteProblem` only confirm a candidate that would win.

Generation takes about 0.46 s at 512², 1.2 s at 1024² and 4 s at 2048² in Node, against 0.26, 0.64 and 2.1 s for recipe 7 (PERFORMANCE.md). The start menu honours `?generation=N` (a supported earlier recipe) for QA and comparisons; `createWorldFromMenu` in `tests/browser-start.mjs` passes it and defaults to recipe 7, whose coordinates the browser checks name; `browser-check.mjs` plays the current default. `tests/world-v8.test.mjs` pins the digests of recipes 7 and 8.

## Production and route planning

`chains.js` derives production dependencies and compatible destinations from the economy catalogs. `chains-view.js` and `chains.css` present the current environment's complete graph, an output's recursive ingredient chain, and every world instance of a selected industry type. Locating an instance centers the map and opens its inspector. The inspector shows downstream cargo consumers and up to five closest matching industry or town destinations. Distances describe direct map distance, not a verified road, rail or water connection.

The same targets become map context, view state in `app.js` that is never saved. `industryDestinations` hands its `findIndustryTargets` result to `holdContext`, which stores `selectionContext` as `{selected, industryId, targets:[{x,y,kind,id,rank}], highlight}`. The frame loop passes it as `render(now, {context})` only while its `selected` is still the current selection object, so a different pick, a vehicle card, a tool or closing the inspector hides it without extra bookkeeping. `contextView()` adds `covers`, the display-pixel rects of `#inspector`, `#objective-card` and the open management drawer (which covers the inspector when an inspector button such as **Plan** opens Routes); the drawer's `transitionend` repaints the scene so the bubbles settle at its edge. Before the label pass, `contextArcs` strokes a screen-space quadratic arc from the source's `industryMarker` to each target's marker or town-label anchor (29 px × zoom above its centre), bowed upward by 18% of its length. Each arc is a 3 px `#1f332a40` casing under a 1.5 px `[4,4]` dashed `#f4d397` line, so labels and markers sit on top. Numbered bubbles (r 8, `#f7f4e7f5`, rank in `#354b3e`) are drawn after the industry markers, 70% along the arc. When the target or that point is outside the open map (the canvas inset by 16 px, minus the covers grown by 16 px), the bubble moves to where the arc first leaves it, found by sampling and bisection. Delegated `mouseover`, `mouseleave`, `focusin` and `focusout` on `#inspector` set `highlight` to the rank of the row pointed at or focused, falling back to the other one; a row's **Plan** button (in its `.industry-target-row`) counts as the row. There are no new hit targets. `getStats().contextTargets` counts the arcs drawn in the last frame.

The cargo lens is view state in `app.js` (`cargoLens`, `{cargo, origin, game}`), never saved and never a visibility preference. `lensCargo(kind)` in `chains.js` picks a type's first output, else its first input; `lensRole(kind, cargo)` returns `source`, `buyer` (including `towns` for town cargo) or null. Only explicit choices set it: a freight cargo button or coverage badge in the route form (origin `routes`, never the planner's automatic suggestion), the Industries type filter (`industry`) and Chains Locate (`chains`, the site's first output, or for a town the followed town cargo). Passengers, the chip's × and Escape in Explore clear any lens. A Routes or Industries lens also ends when `setView` leaves its view, when the player closes the drawer (its close button, Manage or the same nav button), and for Routes when the planner folds, which includes a launch, or when the planner's suggestion replaces the cargo; `closeMobile()` calls from picking and locating keep it. A new or loaded world clears it through `setView`. `renderer.setLens` requests a repaint through `onInvalidate`, so the frame loop's dirty check needs no extra field, and `app.js` redraws the minimap itself. The marker pass draws non-role markers first at `globalAlpha` .5 (full strength while hovered or selected), then role markers with a 1.5 px role border, a corner tab (`#4e7747` ▲ source, `#3f7f88` ▼ buyer) and, at Town and Detail, their name pill; hitboxes are unchanged. `route-planner.js` provides the DOM-free route filtering and connection validation used by the Routes panel. The panel keeps its text search and mode/status/cargo filters separate from the route draft. `filterRoutes` status `attention` keeps the routes `routeNeedsAttention` reports, so the filtered count always equals the top-bar chip. Native station selectors remain available alongside map picking. Selecting a departure on the map advances to arrival selection; only stations matching the route's transport mode are accepted. Cancel, Escape and changing away from Routes end the picker. On mobile, choosing the final stop reopens the management panel.

Renaming lives in `app.js`. `renameButton(kind, id)` renders a `.rename-button` pencil after the station inspector's `h3` and inside a route card's title; one delegated click on `#inspector` and `#panel-content` calls `beginRename`, which swaps the title's text for a `.rename-input` (maxlength 36). The focused field holds the inspector's live refresh. Enter or blur (not a window switch) saves through the model and calls `persist()`. The title takes the new name in place, so the click that ended the edit still lands on its target; the live refresh redraws the inspector and route cards, and a stop rename re-renders an open Routes panel at once for its selects and journeys. Escape, an empty field or the unchanged name restore the title; Enter on a refused name keeps the field open with the model's message. The station selectors label names that occur more than once in the mode's list with `· x, y`.

The route planner verifies the actual network and station cargo coverage before launch. Its cached path result is invalidated by selected stops, transport mode or `networkRevision`; changes to available funds and cargo eligibility also update launch availability. The simulation's `addRoute` still performs authoritative validation when the form is submitted. A valid plan also returns `existingRouteId`: a route with the same mode and cargo on the same stops, in either order for passengers and mail and in loading order for freight. The form then offers to add a vehicle to it, keeping **Launch separate service** as a secondary action. Above the launch buttons a folded **More options** (`.route-options`, hidden while the cargo is passengers or mail) holds the one order, **Wait for a full load**. Its checkbox has no `name`, so the form's generic listeners pass it by; `formDraft.fullLoad` and `formDraft.optionsOpen` keep it for the session and through a launch; a goal's launch, a new world or leaving an edit clears them, and Edit opens it ticked on a full-load route. A launch passes `fullLoad` for freight only; adding a vehicle to a served route follows that route's own setting.

A card's **Edit** sets `formDraft.editing` to its route and fills the planner with its mode, stops and cargo; the planner's own `autoKey` is set too, so opening never swaps the cargo. In edit mode the planner reads **Edit route**, names the route and its fleet, disables the transport select and drops the name field, purchase, forecast and upkeep note. Plans ignore funds. Cargo choices, coverage picks and cargo suggestions stay on the route's side of passengers and freight, and a mail route offers only mail. The status never calls the route *Already served by* itself, and **Save changes** stays disabled until the stops, cargo or full-load order differ from the route's. A changed order alone calls `setRouteFullLoad`; with new stops or cargo, `editRoute` runs first and its message is the toast. A cargo change with cargo aboard asks first in the modal. After `editRoute`, a route whose name matched `defaultRouteName` for its old stops takes the one for its new stops through `renameRoute`; a chosen name stays. **Cancel**, **+ New route**, a stop's **New route** and the inspectors' route buttons leave edit mode. Route cards keep three actions (**Show**, **Edit**, **Retire**); the vehicle row shows **Upgrade** while a newer model exists and a muted *Latest model* otherwise.

`routeCargoList(game)` lists the environment's route cargo. `routeCargoOptions(game, draft)` judges each of them for the chosen stops with `validateRoutePlan(game, draft, {ignoreFunds:true})`, so short funds never hide a fit and the cached path is reused. Fitting cargo comes first: loaded at the start, then loaded at the end, then passengers, then mail, so two town stops still pick passengers. The list stays empty until the stops are connected. When connected stops share no cargo at all, the plan's message names what each end handles. `defaultRouteName(game, plan, cargo)` names a launch after its two towns or its cargo flow, within the form's 36 characters; a mail route adds ' mail' (*Alderbrook – Pinehaven mail*). The Routes panel suggests cargo once per change of stops or transport (`formDraft.autoKey`) and never replaces a cargo that still fits. Whether the planner is folded is session-only draft state; it is never saved.

`forecastRoute(game, draft, plan?)` estimates one more vehicle for a valid plan (funds ignored) and returns `null` otherwise: `perVehicleDay`, `supplyDay`, `movedDay`, `netMonth`, `paybackMonths` (∞ when not positive), `vehiclesToSaturate` and `otherModes`, plus `madeDay`, `fullFare` (what one full vehicle pays; `fullFareText(mode, cargo, fare)` words it as *A full truck pays ≈ $1,227*, so *Full load* names only the order), `cost` and `joining`, and the trip: `tiles` (`payTiles`), `travel` (`travelTiles`), `days` (one way, rounded), `share` (`transitPay`), `perUnit` and `wait`. With `draft.fullLoad` on freight, `u = min(1, supplyDay / perVehicleDay)`: the vehicle's upkeep becomes `VEHICLE_UPKEEP × (u + .45 × (1 − u))`, and while `u < 1` the trip adds `wait = min(FULL_LOAD_MAX_WAIT, capacity / supplyDay) / 2` days, which the route form also passes to `planTrip`; the flag is part of the cache key. A round trip takes `2 × scheduledDays(mode, L, generation)` over the path's `L` travel tiles (for road and rail the former `2L / (base speed × (1 + .1·generation) × .88) + .4`; ships now use their measured pace, .78); a passenger or mail vehicle loads at both ends. Each `otherModes` entry adds the `share` that mode would keep on the same path. Freight supply sums the loading stop's producers: a raw producer's recipe at `industryConditions(game, industry, stop)` productivity, which counts the planned stop as active, and at its mean capacity over the next 180 days, growing by `reviewGrowth` at the mean draw every 33 days from its next review; a factory takes the larger of its recent production and the ingredients active routes deliver, never above its recipe. Passenger supply is each town's `passengerArrivals(game, town, day)` at the mean draw, and mail supply its `mailRate(town, localEnvironment(game, town.x, town.y))`. Active routes that load the same cargo from the same producers or towns take their fleet's throughput first. `netMonth` is 30 days of `fareFor` on the carried units, at `payTiles + 1` points and the trip's `days`, less `priceFor` of `VEHICLE_UPKEEP` plus, for a new route, its share of `INFRASTRUCTURE_UPKEEP` split among the routes on each tile and stop, as `infrastructureShares` allocates it. `fareFor(game, cargo, pathLength, units, day, transitDays)` is the fare `unloadVehicle` pays (see Annual economy), and maintenance, `infrastructureShares` and `stepSettlements` use the same shared constants and helpers, so the refactor leaves same-seed saves byte-identical. The forecast is pure and cached per draft, day, revision and fleet size. The route form shows its monthly line under `#route-connection` (muted `#8a6d52` when not positive) and folds the rest into `.forecast-details`, whose open state is kept in `localStorage` under `transport-forecast-details`. A node test compares it with 180 simulated days on flat road and rail lines of 10 and 40 tiles.

`hud.css` fits navigation, finances, date and speed into one header row. Company delivery and connection totals are exposed through the finances button's hover/focus/click tooltip. `places.css` keeps the expanded industry inspector scrollable within the map on desktop and mobile.

Route lines share one cached projected `Path2D` per route (`routeDrawing(r, key)` inside `render`), so a highlight reuses it and is built even with the routes layer off. `strokeRoute` follows DESIGN.md 8.4 with `lineFor(route)`: a core of 3, 3.5 or 4.5 screen px (`MAP.line.core` at Region, Town and Detail) in the line's fill over a paper halo at 90% (core + 3 px) for deep fills or an ink casing at 55% (core + 2.5 px) for light ones. Freight adds `flowChevrons`: small chevrons in the on-colour every 44 screen px, placed by arc length from the path's start (one tile step is `PATH_STEP` projected px) over the visible index ranges `routeDrawing` keeps, offset by `game.day`, not `now`, so a pan never shifts them and paused frames are pixel-identical; passenger routes are two-way and get none. An offline (`active === false`) or paused route draws at 45% with no flow, and an offline one dashes the tiles either side of its `routeBreakPoint` in `--error` on the paper halo (`brokenStretch`); on the minimap lines take their fill and an offline one is a dashed `--error` line. With `highlightRoute`, other routes fade to 35%, and the highlighted route is restroked after the scenery 1.5 px wider, with rings in its fill at both stops. The screen-space label pass pins each visible break with the cut glyph (two slashes across the line in `--error` over paper) and a *Not connected* plate, drawn after the vehicle load badges so a truck stuck at the gap never hides it; `routeBreakPoint` results are cached per route by `networkRevision` and path length. Pins follow the routes layer, except for the highlighted route. `getStats()` adds `routeBreaks` (pins drawn) and `highlightRoute`. Measured on the 1,000-route dense scene and the busy Region scenes, the restyled pass costs about 0.1 ms per frame, as the old dashed stroke did, so it needs no per-colour batching. In `app.js`, delegated pointer and focus events on `#panel-content` highlight a hovered or focused route card until the pointer or focus leaves it. The exported `showRoute(id)` cancels picking, turns route lines on and picks the largest zoom at which the projected extent of the path points (cached per path) fits 80% of the canvas, falling back to Region. It centres that extent and highlights the route for 4 s. The frame's repaint check includes the active highlight. `updateHud` puts `routesNeedingAttention(game)` into the `#offline-routes` chip beside the date as *N routes need attention*; the chip opens Routes filtered to status `attention` and scrolls the first card into view. A card whose `.route-health` state is `blocked` shows its status label in `--warn` (`routes.css`), and only a blocked route gets `.route-offline`.

## Route identity

`route-lines.js` (DOM-free; imports `design-tokens.js`, `data.js`, `simulation-spatial.js`, `industry-sites.js` and `town-market.js`, so it sits in `model.js`'s graph and `index.html` preloads it) gives each route its number, line colour and default name (DESIGN.md 4.3 and 8). `lineFor(route)` returns the frozen `{index, name, fill, on, light}` of `LINE_COLORS` for `route.color`, memoised per hex (`lineColor(hex)`): an exact fill match wins, then the legacy map of the old six-colour palette (`#69c6bc` Cobalt, `#efc16f` Marigold, `#e5966d` Crimson, `#88aee4` Cornflower, `#b3cf83` Plum, `#d893b1` Heather), then the nearest fill by RGB distance; a missing or malformed colour is Cobalt. `index` is 1–9 as in `--line-N`, and `light` fills take ink numerals and an ink casing. Saves keep their stored hex, so every colour read on the map and in panels goes through `lineFor`. `nextLineColor(game, stopIds)` leaves out the lines of every route that calls at one of the stops and takes, of the rest, the one fewest routes use, lowest first; with all nine at the stops it takes the one least used there. `route.number` is optional in saves, an integer from 1 to 9999: `validateGame` deletes any other value rather than failing. `nextRouteNumber` is the lowest free number, so a retired number is the next one given, and `ensureRouteNumbers(game)` (called by `createGame` and `restoreGame`) numbers routes whose number is missing, invalid or taken by an older route in creation order, by the counter in the id and then list order; it never changes a valid number, so a legacy save numbers the same way every time. `routeLabel(route)` reads *Route 2*. `defaultRouteName(game, stations, cargo, except)` names freight *<supplier> to <buyer>*, each end the site its stop serves for the cargo within 5 tiles, else the town there whose workshops make or take it (*Alderbrook workshops*), else the stop's nearest town, else the stop; passengers and mail join the pair of towns `passengerEndpoints` would pick with an en dash. Names are fitted to 36 characters, and a name another route has gets ` 2`, ` 3`; `except` (a route or id) never counts, so an edited route does not collide with itself. `route-planner.js` `defaultRouteName(game, plan, cargo, except)` applies it to a validated plan, freight reversal included, for the form's placeholder and the edit's rename. Names already saved are never rewritten.

`tools/route-stress.mjs` builds twenty routes of road, rail and water on seed 1847 with `planConnection`, `buildPlan` and `addRoute`, screenshots Region, Town and Detail around the first town and draws a sheet of every bullet with `renderer.drawBullet`.

## Local save slots

The automatic checkpoint keeps the existing `transport-save-v1` key and compact tile format. Named snapshots use one independent `transport-slot-v1:<id>` localStorage entry per slot; listing enumerates this prefix without a separate index. Each versioned envelope includes its id, name, biome, game day, balance, save timestamp, dimensions, route count, payload encoding, checksum and complete compact game payload. Native gzip compresses a `tile-binary-v1` frame with raw packed tile bytes before base64 encoding for original sizes or dense 15-bit UTF16 packing for Vast; JSON remains the fallback when compression is unavailable. The payload checksum lets listing flag accidental edits and truncation without expanding each world.

`save-slots.js` provides `listSaveSlots()`, asynchronous `writeSaveSlot(game, {id?, name})` and `readSaveSlot(id)`, plus `renameSaveSlot(id, name)` and `deleteSaveSlot(id)`. List metadata distinguishes ready, corrupt and unavailable entries. The autosave has id `autosave` and is read-only through this API. Writes validate and serialize before a single `setItem`, preserving the previous record when storage rejects a write. Renaming changes metadata without re-encoding its payload. Reading validates and hydrates the complete world but does not activate it or change storage. `slotDate`, `slotMoney`, `slotDetails` and `savedAgo` give the start menu and the Load / save dialog one wording for game dates, balances, map sizes, route counts and save age.

`saves-view.js` and `saves.css` mount the Load / save dialog with named slots, an independent autosave checkpoint, asynchronous progress/errors, and inline confirmations for replacing the world, overwriting a slot or deleting one. Disposal prevents an outstanding read from activating a company after the dialog has closed. The dialog retains an accessible close control while operations run and while its list scrolls.

`start-menu.js` opens on New game. On a fresh page load it waits for the first paint, because summarising the autosave parses the whole save, and then adds a primary `#start-continue` above the tabs when the autosave is ready. Continue takes focus from New game and loads through the same `loadSlot` path as the Load game rows. The in-game Main menu passes `canResume` and offers Resume instead, so it never shows Continue.

`app.js` activates a loaded or generated world only after writing its new autosave successfully. New-world generation paints a progress state before synchronous generation and disables duplicate submission. Atlas/minimap geometry follows the current world aspect ratio. Activation refreshes the renderer, minimap, camera, tool, route draft and filters, inspector and chain selection. Failed activation leaves the current company and prior autosave intact. The dialog pauses the simulation and periodic autosaving; the previous simulation speed resumes on closing. Named saves are independent snapshots and are not updated by periodic autosave or new-world generation.

Delivery income is a live overlay labelled Income (`deliveries`). ## Rivers and shipping

World generation carves connected water channels with `detail: 'river'`, joins tributaries to the trunk rivers and connects river mouths to sea. A navigable river runs beside both starter towns, with shoreline berths within the existing five-tile catchment. Generated streets preserve water and mark crossings as bridges; building placement skips water. River detail uses the existing lossless detail palette without a save format change. ## Airports and flights

`station-sites.js` is a DOM-free leaf (it imports nothing) holding the station geometry every module shares: `STATION_RADIUS` (5, re-exported by `model.js`), `AIRPORT_REACH` (7), `AIRPORT_LENGTH` × `AIRPORT_WIDTH` (6 × 2), `AIRPORT_MIN_TILES` (16), `AIR_TURNAROUND` (1.6 days), `AIR_DEPARTURE_DWELL` (.55) and `AIRPORT_TOOLS`. A stop or port occupies its tile; an airport `{…, mode:'air', axis:'x'|'y'}` occupies 6 × 2 tiles from its north-west anchor, the runway along `axis`. `stationSpan`, `stationTiles`, `stationContains`, `stationReach`, `stationDistance` (Euclidean distance to the nearest tile, bit for bit `Math.hypot` for one-tile stops) and `stationServes` answer for any station. `stationSiteAt(game, x, y)` is an O(1) lookup from a `WeakMap` index per game, rebuilt when `networkRevision`, the stations array, its length or its last entry changes; `model.stationAt` delegates to it, so `buildProblem`, `build` and bulldozing see an airport on all twelve tiles, and `industry-sites`, `building-sites`, `terrain-objects`, `terrain-engineering` (earthworks, protected heights, span ends), `settlements` (growth and the streets' clearance) and `environment` (the ecology `occupied` set; airports give factories no transport access) use it or `stationTiles`. `airPath(game, from, to)` is the flight: a deterministic 4-connected staircase along the straight line between the anchors (ties step along y), so the saved path keeps every invariant: unit steps, stops at both ends, the route codec, `payTiles` = Manhattan distance, progress spacing and Show framing.

`economy-pricing.js` adds `AIR_DEBUT_YEAR` (1952) and `airAvailable(game)`, re-exported by `model.js`. `buildProblem` refuses `airport-x`/`airport-y` before 1 January 1952 (*Air travel arrives on 1 January 1952.*), then asks `airportSiteProblem(game, axis, x, y)`: inside the map, every tile dry and not mountain, free of network, zone, building, industry, station and town centre, and all 21 grid vertices at one level. `build` names the airport after the nearest town it serves (`nextStationName` when that name is taken), clears woods and rocks and charges `BUILD_COSTS['airport-x']` ($60,000). Airports cover passengers and mail only (`stationCoverage`), measured from their nearest tile by `passengerEndpoints`, `routeHealth`, `townService`, `townStopCounts`, route names, headlines and the forecast. `planRoute` wants two airports (*Choose two airports for a flight.*), passengers or mail (*Planes carry passengers and mail.*), two different towns within 7 tiles and 16 tiles between the anchors. `data.js` extends the landed tables: `VEHICLE_COSTS.air` 150,000, `VEHICLE_CAPACITIES.air` 40, `VEHICLE_SPEEDS.air` 12, `TRAVEL_PACE.air` .97, `STOP_DAYS.air` 1.6, `VEHICLE_UPKEEP.air` 150 and `INFRASTRUCTURE_UPKEEP.stop.air` 18; `infrastructureShares` walks only road and rail paths, and `route-tiles.js` indexes only road and rail routes, so bulldozing under a flight never warns.

The flight model: `travelSpeed` gives each plane one speed a day, sampled once at the chord's midpoint (weather counts half as much as on land, and the daily variation reuses salt 511), scaled by Manhattan ÷ straight so the plane crosses the saved staircase at a constant ground speed; its cache key (vehicle id and `air`) does not depend on the segment, so a mid-day cache reset changes nothing. `arriveVehicle` unloads, loads, turns and then sets `dwellRemaining = AIR_TURNAROUND` with no random draw. `moveVehicles` and `addRouteVehicle` place a plane on the straight line between the anchors at `progress ÷ L`; a new route's first plane starts at its stand with `AIR_DEPARTURE_DWELL`, added planes keep the widest-gap start and take that dwell only when it snaps to a stop, and `editRoute` keeps each plane's share of the trip instead of snapping it. `updateRoutePath` returns early for a flight whose path still ends at its airports, so network edits never replan it, and `routeBreakPoint` is null for air. `validateGame` requires `axis` on airports and forbids it elsewhere, reserves only one-tile stations and claims every airport tile after the industries (no network, zone, water or mountain, no overlap); flatness is not validated, so a load never fails over a slope. No save field, `randomAt` salt or `notify()` is new, and a company that never builds an airport saves byte for byte as before.

`air-flight.js` (DOM-free, presentation only; the simulation never reads it) turns `(route, stations, vehicle)` into a pose `{x, y, z, heading, phase, ground}` in continuous tile space. On the ground the 1.6 days are `GROUND` = rollout .2, taxi in .3, parked .5, taxi out .3 and take-off roll .3: a landing touches down at u .9 toward the far end from the other airport (`landingSign`), turns off at the first connector onto the apron lane, parks at one of two stands (`standFor`, a hash of the vehicle id), taxis out at the second connector and rolls the other way to lift off at u 1.4. In the air a cubic (`flightPath`) tangent to both runways is sampled by arc length at the model's `progress ÷ L`, climbing over 7 tiles and descending over 9 (`flightHeight`). `groundPhase(dwell)` names the phase for the plane's card. `airport-art.js` draws the art natively: `paintAirportGround` bakes the biome-tinted field, runway, taxiways and apron into the terrain chunks like roads, and `createAirportSprites` prepares the tower, terminal, hangar, depot, masts and windsock per axis and view, and the airliner per 48-heading bucket and line colour, with softer shadows aloft, in the shared `preparedTransport` LRU. The painterly revision (warm-dark outlines, deeper shade, brick courses, planting, an outlined airliner) keeps the uprights near the houses' tonal weight; generated raster art could later take over through `atlas-runtime`, with this module as the fallback.

`renderer.js` keeps `airportIndex` (every airport tile to its airport) beside the anchor-only `stationIndex`, which still drives stop signs. Chunks paint each airport touching their cells and fingerprint the airport per tile; scenery is suppressed on airport tiles; the uprights join the depth-sorted scene from the first airport tile in view, each sorted by its own front corner (`PART_FRONTS`) and pickable like a billboard. Every visible plane gets one pose a frame (`airPoses`), with a cached `cruiseLevel` 2.4 levels above the highest ground under the line between the airport centres. Shadows are drawn before the scene, planes on the ground sort with the buildings, and planes in the air are drawn after the scene, highest last. A flight's route line is one dashed straight segment between the airport centres, the emphasis rings become footprint outlines, and the minimap draws airport tiles, a straight segment and a pale diamond. The airport's sign stands over the terminal hall (`signTile`) and its delivery figure rises above it (`floaterPoint` in `app.js` marks it `air`). The Airport tool previews its 6 × 2 site, centred on the pointer by `construction-plan.js` `airportPlacement`, and the tool and a selected airport draw the rounded 7-tile reach with its pill. `vehicleAt`, load badges and the chosen ring read the pose, and `vehicleWorldPoint(v)` gives Follow the drawn plane. `getStats()` reports `airports`, `aircraft: {ground, air}` and `airportSprites`.

In the interface Build → Network holds Road, Rail, Stop, Port, Airport (its own row) and Bulldozer; before 1952 the Airport card carries `aria-disabled` and *From 1952*, and choosing it only toasts the date. **A** picks the tool, and again, or `#active-tool-turn`, turns the runway (`airportAxis`, session only); every `buildPlan`/`quoteBuildPlan` call and both renders pass it. On a phone Turn takes the recent-tools dock's place. The route form and the route filter offer Air once air travel has arrived or an airport stands. `app.js` finds stations with `stationAt` in `inspect`, the route picker and the keyboard cursor, so any airport tile opens or picks its airport, and `servingStops` and the town hall use `stationServes`. The January 1952 moment is `headlines.js` `airDebutHeadline` (kind `debut`, priority 2, *Build an airport*), announced by `queueNewYear` only when the year turns to 1952 in play, or as a notice when headline cards are off. `station-sites.js` sits in the start-menu module graph, so `index.html` preloads it before `buildings.js`; `air-flight.js` and `airport-art.js` join `APP_PRELOAD`. `tests/airports-browser-check.mjs` plays the whole feature on seed 1847.

## Annual economy and vehicle generations

`economy-pricing.js` derives Gregorian years from the same January 1950 epoch as the HUD. `inflationInfo(game)` returns calendar year, year index, the seeded annual rate and the compound price index. `priceFor(game, basePrice)` rounds the current price. Rates and unlocked vehicle levels derive from seed and simulation day, requiring no new persisted schedule. A bounded cached calculation handles far-future saves. Monthly financial reports use Gregorian month boundaries from the same epoch. Construction, clearing surcharges, purchases, upgrades, upkeep and delivery revenue share this pricing layer; arrival revenue uses the actual arrival day.

`getVehiclePurchase` quotes the latest generation. Each calendar year unlocks one level, increasing base capacity by 20% and base speed by 10% per level. `getVehicleUpgrade` and `getFleetUpgrade` provide read-only quotes; `upgradeRouteVehicle` and `upgradeFleet` perform authoritative affordability checks and mutate the eligible fleet atomically. Vehicles store `level` and `paidPrice`, and retain load, position, progress and dwell time when upgraded. Legacy vehicles default to level zero and their original base purchase price. Retirement returns 45% of paid price, including upgrades. The UI refreshes quotes with calendar and funds changes.

`vehicle-models.js` (DOM-free, no imports) names the levels. `VEHICLE_SERIES` holds seven frozen series in catalogue order (bus, truck, passenger-train, freight-train, ferry, freighter, airliner), each `{mode, passengers, noun, plural, families: [{year, level, name}]}` from 1950 (the airliner from `AIR_DEBUT_YEAR`, 1952, for passengers and mail alike) with 54 invented family names. `vehicleSeriesKey(mode, cargo)` picks the series (passengers by cargo, mail in the freight body); `vehicleModel(mode, cargo, level)` returns `{series, name, family, mark, year, level, debut, noun, plural}`: the last family with `level ≤ level`, mark `level − family.level + 1`, never below 1 (so every first family's mark is the old generation number, the airliner's is `level − 1`, and the last family counts on), model year `1950 + level`, `debut` for a family's first level after 1950, and *tanker*, *mail truck* or the series noun. A bad level reads as 0. `vehicleAge(year, level)` and `ageText` give whole years since the model year; `fleetModelText(mode, cargo, levels)` gives a fleet's `{text, title}` (*Hollin Mk 4*, *Hollin Mk 4–6* or *Pendle Mk 2 and older*, with counts per model in the title), working once per distinct level. `newYearModel(routes, vehicles, level)` picks the model January names: among used series that debut a family at that level the one with most vehicles, else the most-used series, else the first debuting series, else the bus, ties in catalogue order, with the first cargo seen for the noun (a mail cargo only while the series carries nothing else). `modelHeadline(model)` is the kind `models` headline (`models:<year>`) when that model debuts a family, or `null`. Names, model years and ages come from `level` alone and are presentation only: no vehicle field, cost, speed or reliability depends on them. `getVehicleUpgrade` adds `levels` (fleet order) and `maxLevel`, and `getRouteFleet` returns the same `levels`, both from one loop-based `fleetLevels` helper. `upgradeRouteVehicle` reports the target model's name and `upgradeFleet` the model year. `newYearNotice(year, rate, {generation, model})` names the model when one is given (*vehicles such as the Hollin Mk 2 bus carry…*, or *…the Pendle Mk 1, a new bus series, carry…*) and keeps its older text without one.

Routes keep two optional yearly figures. `addRoute` starts `profitThisYear` at 0; `unloadVehicle` adds each delivery's revenue right after booking `route.revenue`, and `maintenance` subtracts each route's integer upkeep share where it books `route.expenses`, with the same arithmetic as before. `monthlyUpdate` closes December after `closeYear` (whose `bestRouteId` is now the route with the highest positive `profitThisYear`, ties to the earliest): every route's `profitLastYear` takes `profitThisYear ?? 0` and `profitThisYear` returns to 0, so the Jan 1 upkeep charged before `monthlyUpdate` belongs to December, as in the company accounts. `editRoute`, purchases, upgrades and sales leave both alone. `validateGame` accepts each as undefined or a finite number within ±1e15 and restores no default, so a legacy route starts counting at its first delivery or upkeep after loading. The fields pass through every save format and worker transfer unchanged; there is no `randomAt`, `notify()` or `nextId` use, and a whole tick and quarter-day frames across January keep identical books. `app.js` `routeYearHeadline` and `routeYearNote` word the route card's *This year* figure (titled with the net and average since launch) and its *Last year* slot, which shows the monthly average until a year has closed and yields to an active contract's rate. The card's vehicle row names its models where it said *Latest model* (`vehicleModelTag`; `refreshUpgradeControls` rewrites it only when its text differs from the last it wrote, kept in a `WeakMap`), and an up-to-date fleet's title says the year newer ones arrive; an **Upgrade** button sits under the stepper, titled with the models it replaces and the target model. The planner's `#vehicle-purchase-spec` reads *Hollin Mk 3 bus, carries 34* with the model year as its title, and the vehicle card names its model with its model year and age.

Delivery pay is `fareFor(game, cargo, pathLength, units, day, transitDays)` = `priceFor(units × CARGO[cargo].price × distancePay(pathLength − 1) × transitPay(cargo, transitDays), day)`, where `pathLength` counts path points. `economy-pricing.js` (DOM-free, re-exported by `model.js`) holds the helpers and `data.js` their constants. `distancePay(tiles)` is `(tiles + HANDLING_TILES) ÷ DISTANCE_TILES` = `(tiles + 12) ÷ 9`, straight-line growth. `transitPay(cargo, days)` is 1 up to the class's `fullDays` (express 14, perishable 16, standard 25, bulk 45) and for unknown days, then falls by `dailyLoss` a day (1.5%, 1.2%, 0.8%, 0.4%) to `TRANSIT_PAY_FLOOR` (0.5). `payTiles(path)` is the path's tiles capped at `DETOUR_PAY_LIMIT` (2) × the grid distance between its end stops, so a winding connection cannot multiply a fare; `travelTiles(mode, path)` is the path, or the straight endpoint distance for a flight. `scheduledDays(mode, tiles, level)` is the timetable, `tiles ÷ (VEHICLE_SPEEDS[mode] × TRAVEL_PACE[mode] × (1 + .1·level)) + STOP_DAYS[mode]`, with paces .88 on land, .78 on water and .97 in the air, and `STOP_DAYS.air` 1.6 on the ground at each airport; `VEHICLE_SPEEDS` (2.8, 4.6, 1.8, 12) is also what `travelSpeed` multiplies, bit for bit, and what the forecast and the payment chart read.

The clock is `vehicle.loadedDay`, optional in saves and validated as a number in [0, `game.day`]; `restoreGame` adds nothing, and an absent field (legacy cargo) pays the full distance fare. `loadVehicle(game, route, vehicle, stopIndex, context, day)` stamps `floor(day)` when a load starts and a load-weighted mean when one is topped up; `arriveVehicle` passes its arrival day and first restarts the clock of anything still aboard after unloading (nothing at the stop buys it, such as after its buyer was removed), so leftovers are paid by their last leg. `restartCargoClocks` sets the clock of every loaded vehicle to today when `updateRoutePath` reactivates a route and after `editRoute`. `unloadVehicle` pays `payTiles(route.path) + 1` points with `floor(arrivalDay) − loadedDay` transit days; contract bonuses multiply that fare. The key is written only as a number, never `undefined`, so `packFleet` keeps packing the fleet. `recentTransitDays(game, routeId)` is the mean of a route's last eight transit times from a `WeakMap` log that is never saved, cleared by `removeRoute` and `editRoute`, and empty after a load. None of this spends `nextId`, draws `randomAt` or sends a notice, and no status or attention rule reads the pay share.

`payment-rates.js` builds the pay UI as strings (DOM only inside `bindPaymentRates`). `paymentRatesHTML(game)` is the Guide's Resources section: an SVG of `fareFor` for 10 units over 20 tiles by 0–120 days, one path per `routeCargoList` cargo drawn through its knots (0, full-pay end, floor, 120), coloured by class from `LINE_COLORS` (Marigold, Iris, Crimson, Cobalt; the light two with the 35% ink edge of the line language), with a class legend, this year's `scheduledDays` for 20 tiles per mode and a table view. `bindPaymentRates(root, game)` returns `{dispose}`: one `AbortController` for the crosshair and tip on pointer and arrow keys and for legend highlights, and a `ResizeObserver` that redraws the SVG at the plot's width so axis text stays 12 px. `routeTrip(game, route, level)` and `planTrip(game, mode, cargo, path, level, wait)` return `{tiles, travel, capped, days, measured, share, perUnit}`, measured from `recentTransitDays` when a route has recent deliveries; `tripText`, `planText`, `tripTitle` and `keepText` word them for the route card row (refreshed with the route rates, written only on change), the forecast's trip line and the train hint.

## Mail between towns

Mail is Transport Tycoon's second town cargo. `settlements.js` exports `MAIL_RATE` (.0024) and `MAIL_POOL_SHARE` (.08). `mailRate(city, environment)` is the mean of `population × MAIL_RATE × (1 + .15 × min(4, environment.services))` bags a day, and `mailArrivals(game, city, day, environment)` scales it by `.7 + randomAt(game, day, city.id, 121) × .6`, a stateless salt used nowhere else. `stepSettlements` adds a day's letters right after the passengers, with the same `localEnvironment`, and clamps `city.mail` to `population × MAIL_POOL_SHARE`; demolishing housing clamps it too, and `construction-undo.js` records and restores `mail` beside `passengers`, clamped to the restored cap. Waiting mail sends no notice, no goal counts it and nothing else reads it, so a company that never launches mail runs as before: taiga 1847 and desert 42 after 400 days match the previous code once `city.mail` is stripped, with the same `nextId`.

`stationCoverage` produces and accepts `mail` wherever it produces passengers. `planRoute` (so `addRoute` and `editRoute`), `validateRoutePlan`, `loadVehicle`, `unloadVehicle`, `routeHealth`, the forecast's `loadingFlows` and `headlines.js` `arrivalRoute` use `isTownTraffic`; `loadVehicle` takes from `city[route.cargo]`. A mail delivery counts toward the town's `delivered`, `activity` and `lastServiceDay`, like passengers, and is paid by `fareFor` with the vehicle's `loadedDay`, like every cargo: express, full pay for 14 days, then 1.5% less a day, never under half. No vehicle field is added, and vehicle art is unchanged: mail rides in truck, wagon and cargo-ship bodies with the generic crates load, and the load badge and delivery floater show the envelope pictogram. Freight filters (`openProcessor`, `nextProject`, milestones, `industryService`, contracts, industry openings, `suppliedRoutes`, first-delivery toasts, the flow chevrons, the cargo lens and the stop tool's tip) exclude it. Its waiting count is the emptier town's floored pool, which `routeCapacity` reads for room; a blocked mail route reads *No mail*, and a running one *Mail travels both ways.* `vehicleNoun` names a *mail truck*, *mail train* or *mail ship*, and `headlineNoun` delegates to it for mail.

## Biome scenery

`BIOME_NATURE` in `terrain-sprites.js` shares tree, mountain and plant catalogs between seeded world generation and local ecology. Expanded detail strings preserve the seven gameplay terrain classes and use the existing tile codec. Habitat patches choose related species; new woodland often inherits nearby species. `isPlantDetail` identifies decorative vegetation for rendering and environmental calculations. Hiding trees removes foothill vegetation while retaining the mountain itself.

`tree-sprites.js` generates 64 deterministic woodland compositions per biome/detail, containing one to five trees with per-tree species, leaf coverage, height, placement and branch/crown seeds. Composition is independent of zoom; each profile only adjusts fine marks. The renderer hashes tile coordinates, world seed and the saved variant into the artwork seed, so legacy 16-variant maps gain the new art without changing save state. Forest canvases are 48×48 logical pixels (x −8…40, y −16…32); their crowns can overlap neighboring cells. Other sprites keep the 32×40 envelope. Chunk padding covers these overhangs.

`relief-sprites.js` draws irregular mountain crests, layered desert formations and fractured boulders. `terrain-sprites.js` separates geometry and texture streams for stable vegetation between zooms. Nature uses 64 cached variants, other art retains 12; the sprite factory has a 16 MiB LRU limit in addition to the chunk budget.

The map is always in daylight; there is no day/night pass. `hasClearableDecoration` keeps Bulldozer placement previews and authoritative cleanup consistent.

## Simple construction and map controls

`construction-plan.js` adapts the six-tool interface to existing model operations. `resolveBuildTool` chooses bridges/tunnels for Road/Rail, a station mode for Stop and `airport-x`/`airport-y` for Airport from `airportAxis`; explicit legacy tools still pass through. `model.buildProblem(game, tool, x, y, {money})` returns every refusal `build()` would give, in `build()`'s own order and wording, as `{message, reason: 'blocked'|'funds'|'terrain'}`, or null; `build()` itself starts with it, so previews and construction cannot drift. `quoteBuildPlan` deduplicates tiles and walks them with the balance `buildPlan` will spend, giving each placement a `state`: `built`, `blocked` (with its `problem`), `slope`, `funds` or `ok`. `networkTerrainPlanIssues` lists each tile that breaks the grade rules as `uneven`, `sideways` or `ramp-junction` (with the existing ramp `at`); `networkTerrainPlanProblem` keeps its single message. Road and rail strokes are all-or-nothing: any slope issue, blocked tile or unaffordable tile makes the quote `ok: false`, and `buildPlan` then builds nothing and charges $0. Zones and demolition stay partial; their quote reports `partial`, `buildable`, `blocked` and `unaffordable`, and a result with nothing built but a refusal is `ok: false`. A stroke of more than one tile leaves out what it cannot act on, so quote, preview and build agree and those tiles never count as failures: `zonePlanPoints(game, kind, points)` drops road, rail, station, town-center, building and industry tiles, water, mountains and tiles already in that zone (another zone stays in as `blocked`), and a demolition stroke drops empty ground. When nothing would be left, the stroke keeps its tiles so the quote gives `build()`'s refusal. A zone quote also marks each placement it would zone without road access (`needsRoad`, from `hasRoadAccess`) and counts them as `needRoad`; those tiles are still built. In `app.js`, `constructionLine` gives zones, and the Bulldozer with Shift, the rectangle from the start to the far corner, clamped to 16 × 16 (`areaRect`, whose points carry `area: {w, h, capped}` for the tip); Shift keeps a zone's line. A single stop, port or town quotes `buildProblem`'s verdict. `model.buildPath` keeps its documented partial policy for API callers. `buildPlan` delegates every placement to `model.build`, preserving single-placement metadata. The renderer colours each preview tile from the quote's states (error red for problem tiles, muted for the rest of a refused road/rail stroke, a red outline on a ramp it would join sideways, muted amber for a zone tile no road reaches), skips the preview tiles a zone or demolition stroke left out, and uses `buildProblem` for single-tile highlights. `route-tiles.js` indexes the tiles of active road and rail routes, cached by network revision and route paths; the Bulldozer tip and preview use it to name the services a demolition would cut. The placement tip in `app.js` reads a zone rectangle as size, tiles and tiles needing a road before the price (`Residential · 6 × 6 · 32 tiles · 20 need a road · $13,440`, then ` · max 16 × 16` when clamped) and turns `.warning` while any need a road. It shows a refused quote's message as `.invalid`, a partial one as `.partial` (for example `Builds 2 of 9 · funds for 2`), and appends `.warning` notes: a valid stop names what `stationCoverage` loads, accepts and serves (memoised per tile and revision), or says no customers are within 5 tiles. After a release the tip re-quotes the tile under the pointer, and a build that skipped tiles toasts as a warning. The active tool never changes save structure or simulation rules.

`network-router.js` shapes Road and Rail drags on the view side; it never changes the model, saves or simulation. `gridLine(a, b, first)` is the plain L, along the longer axis first unless `first` names `'x'` or `'y'`. `planNetworkStroke(game, mode, from, to, {margin=12, maxExpanded=40000, budgetMs=8})` returns `{path, reason, expanded}`: the plain L as `direct` whenever its quote has no slope issue or blocked tile (funds never reshape a drag), otherwise the other bend as `flipped`, otherwise an A* over tile × arrival direction inside the drag's box plus the margin, with typed-array costs, parents and states and a binary heap. Each tile is classified once through `buildProblem` with unlimited funds, so occupancy, other-mode stations, span metadata and side contact with finished ramps match construction exactly. Ramps are entered and left only along their axis, only flat ground and finished network turn, water and mountain crossings run straight, and `networkEdgeAllowed` keeps span axes. A step costs the tile's `constructionCost` over the mode's base price, 0.6 on finished same-mode tiles, plus 0.2 per turn; the heuristic is Manhattan distance, and ties prefer the state nearer the goal, then the lower index. `quoteBuildPlan` validates the result; a ramp the path itself touches sideways is penalised and searched again, at most three times. A path longer than 1.6 × the Manhattan distance + 8 steps, or dearer than 1.6 × the cheaper L (blocked tiles priced as buildable), returns the plain L as `too-far`; no route, a failed validation, the expansion cap or the time budget returns it as `fallback`, whose red tiles explain the refusal. `constructionLine` in `app.js` calls it only for Road and Rail, never for spans, Level, zones or demolition, and keeps the last plan per company in a `WeakMap` keyed on tool, both end tiles, `networkRevision` and `revision`, so a drag searches again only when its end tile changes. A pointer holding Shift (read at pointerdown and every move) keeps the plain L, bent along `pointer.firstAxis`: the grid axis of the first tile change after the 5 px drag threshold. Touch has no Shift and always follows the terrain. The placement tip appends *follows terrain · Shift: straight* to `flipped` and `routed` strokes, without the Shift hint on touch, and replaces a `too-far` refusal with *No gentle route — level ground or drag in shorter segments*.

`planConnection(game, source, target, mode='road', {margin=10, maxExpanded=400000, budgetMs=250})` is the first-route planner behind **Plan road**. Both functions run the module's internal `gradeSearch(game, mode, box…)`, the A* above with several starts and a goal test, and share its classes, prices, turn cost, tie-breaking and `steer` retry after a refused quote, so a plan builds under exactly the rules a drag does. It reuses same-mode stops that already serve an end: `source` is an industry, `target` an industry or a town, and a stop serving both counts as the source's. The search starts at the serving source stops, else at every stop site in the source catchment (the five-tile reach outside the footprint: flat, ramp or finished ground-level network, never a bridge, tunnel or another stop), each entered at its own step cost. Its goals are the finished network flooded from the serving target stops inside the box, else the stop sites in the target catchment; each goal carries the steps the path still needs so the two stops end at least three tiles apart. The heuristic is the Manhattan distance to the goals' bounding box. A clean quote returns `{ok, mode, path, stops: [{x, y, end, cost}], ends, tiles, cost, vehicleCost, expanded}`: `ends` holds the reused stops, new stops take the path's first or last tile, `tiles` counts the tiles to build and `cost` adds the stops to the quote; otherwise `{ok: false, reason: 'no-site'|'no-route'|'too-far'}`. It is read-only and deterministic, and the `taiga 1847` test builds the quarry plan and runs it for a month.

## Construction undo

`construction-undo.js` is DOM-free and reverses one construction gesture as a diff, never by restoring a snapshot, so vehicles, cargo, inventories and growth elsewhere keep what happened since. `captureUndo(game, tool, points)` runs before `buildPlan`: it clones every tile within Chebyshev distance 3 of the points (and of the site anchor a bulldozer point resolves to), keeps the ordered station, industry, city and zone arrays, each town's population, passengers and mail, the notices, `money`/`monthlyExpenses`/`totalExpenses` and `nextId`. For a town founding it also lists the buildings that still lack `populationCityId`, because `build` pins every home to its town first; a tile array with none left is remembered until the next undo and not scanned again. `finishUndo(entry, game, result)` returns null unless a successful build changed something. It keeps only the tiles that differ, the added and removed objects by identity (removed ones with their index), per-town population and passenger before/after pairs, the ids of added notices and the cost.

The entry also carries a watch. Its core is every changed tile plus the footprint of each station, industry and town it adds or removes and of each building or grove/outcrop parcel it would bring back; each core tile keeps a post-build clone. Tiles up to two to the upper left are watched only for a building anchor that could cover the core, and the neighbours of a changed height are watched like the core, since slopes, bridge clearance and parcel flatness read them. `undoProblem(game, entry)` refuses when a watched tile changed apart from ground cover (`detail`, parcels, and natural terrain among grass, forest, sand and snow; a returning parcel's own tiles must keep their exact terrain), when an added object is gone, when a station, town or industry placed later stands on the core, when a route uses an added stop, when an added industry has shipped or received cargo, or when a building belongs to an added town. `undoStale` marks entries from another tile array, used ones, and any made before `game.routes` was replaced or changed length. There is no calendar limit: a quiet build can be undone in a later month. The one exception is property: `finishUndo` sets `property` when a changed tile now holds a building with `owner: 'player'` that its pre-build clone lacked, and stores the `calendarMonth` it was placed in; such an entry undoes only in that month (*Rent has been paid on this building. Sell it instead.*), so rent is never collected on a refunded build. Selling changes the journaled tile, so a sold placement cannot be undone either.

`undoConstruction(game, entry)` restores each changed tile in place (all keys deleted, then the clone assigned) so `game.tiles` and the save baseline keep their identity. Each array returns to its exact old contents when it is unchanged since the build; otherwise added objects leave and removed ones are spliced back at their index. Town figures, money and both expense totals return exactly while unchanged, else by the recorded difference, with passengers capped at 90 % of population, mail at `MAIL_POOL_SHARE` of it (a town without the field keeps none) and expenses never below zero, since a later month has already booked the spend. Added notices are removed, owners pinned by a founding are unset, and `nextId` goes back only while nothing else consumed an id. The undo ends with `model.invalidateNetworkPoints(game, points)` when network tiles or stations changed, else `game.revision++`.

`app.js` journals every `paintPath` release and keeps a session stack of the last ten entries, emptied by `activateGame`; stale entries are dropped whenever the stack is read. Ctrl/Cmd+Z is handled after the dialog and text-field guard, so inputs keep native undo, and does nothing mid-stroke. The build toast carries an **Undo** action and is keyed by its entry, so each build keeps its own toast and a keyboard undo closes it. Success toasts `Road removed · $X refunded`; refusals and 'Nothing to undo.' are warnings. The app then refreshes route connections, the HUD, the scene and any open panel, re-seeds the notice cursor if its notice was removed, and schedules the same debounced autosave as construction. Nothing new is saved.

## Playability and accounting

`gameplay-insights.js` derives optional next projects, truthful town service, industry input/storage states and actionable route health. It uses the simulation’s five-tile station catchment, measured to an industry’s nearest footprint tile and to a town’s centre, and capacity-dependent900-unit storage. `routeHealth(game, route, stats)` returns `waiting` and fleet `capacity` for a working route: freight sums the whole stock of the start stop's producers, passengers take the smaller waiting count of the two linked towns; `stats.capacity` spares the scan when the caller has already summed the fleet. Spare demand is never a state, since the starter bus always has passengers waiting and a warning would never clear: `routeCapacity(game, route, stats, health)` returns `{waiting, capacity, room, perMonth}`, where `room` holds once a `running` route that is not *Loading* has run 30 days since `accountingStartDay` and its start holds `max(50, 2 × capacity)` of freight, or its quieter town `max(50, 4 × capacity)` passengers or mail, and `perMonth` is what one more vehicle of today's model would carry in 30 days at `2 × scheduledDays` a round trip, loading at both ends for town traffic; pass the health already read to spare a second one. The route card shows it only as an ink-2 *Room for more: 606 waiting* line in `.route-vehicle-spec` (`roomHint`, refreshed with the HUD), titled *Another bus would carry about 72 more passengers a month.*; it never counts toward attention. `unloadVehicle` stores freight in the covered buyers up to 900 × capacity each and hands the rest to town workshops or a town that buys it, as before; whatever is still left, the first covered industry that lists the cargo takes and pays for with the same fare. It counts as delivered and `received` but is not stored, and only stored cargo adds `activity`, so expansion and the capacity reviews that never drop stored cargo are unchanged; nothing new is saved, drawn or notified. Such a route reads *Stores full* (`running`, `info`) once no supplier warning or full-load line comes first: *Deliveries still pay. Supply iron ore too and Steel mill will make steel.*, or *Carry lumber away from Sawmill and it will use more timber.* while the buyer's output is half full or more, else *Deliveries still pay while Sawmill works through its timber.* On a route with `fullLoad`, `fullLoadQueue(game, routeId)` returns `{count, head}` from one scan (the head is the smallest `fullLoadSince`, array order on a tie), or `stats.queue` passes the line the caller found: `updateHud` gathers each route's line in its load pass. Vehicles in the line never count as loaded, a supplier short of an input still reads *Needs* it, and the waiting-for-supply reading gives way to *Loading* (`running`, `ok`) with the reason *Waiting for a full load, 10 of 24.*, which adds *, with 2 more in line* for the vehicles behind the head; with no line the running reason says the vehicles leave the start full, or after a month at most. Routes without the order read and scan exactly as before. The vehicle card's trip line reads *Waiting for a full load at* its first stop while it waits. Every status (`routeHealth`, `industryStatus`, `townService`) has one shape: the machine `state` the interface already reads, a DESIGN 6.4 `tone` (`ok`, `warn`, `error`, `paused` or `info`), one `word`, a `reason` template, an optional `fix` `{action, label, cost?}` (`show-gap`, `edit`, `zone`), and `label` and `detail` equal to the word and the plain reason. Route words are *Running*, *First trip* (before the first delivery), *Loading* (a full-load line), *Stores full*, *Needs* a cargo (its supplier is short of an input), *Not connected*, *Stop missing*, *No supplier*, *No buyer*, *No passengers* and *No mail*; nothing produces *Paused* yet. A route waiting for its supplier or a town's workshops to make more is `running` too, so the machine state `waiting` always means a *Needs* warning and the interface's state colours never mark normal service as a fault. `routesNeedingAttention(game)` counts the routes whose health is `blocked` (disconnected, missing a stop, no two towns, no producer or no buyer), and `routeNeedsAttention(game, route)` tests one; waiting routes and spare demand never count. The blocked set is memoised in a `WeakMap` keyed by `networkRevision`, the identities and lengths of the route, industry, station and town lists, and the indices of inactive routes, since `updateRoutePath` flips `active` without moving any revision. `game.revision` moves daily and stays out of the key, so a recompute (about 20 ms for 300 freight routes, less than re-pathing them after the same construction) follows only a player's change; a cached call takes microseconds. `industryService(game)` maps industry ids to `{source, buyer, color}`: each active freight route marks the producers of its cargo in reach of its first stop and the buyers in reach of its last, taking the first such route's colour, and each stop's catchment is read once per call; passenger routes never serve an industry. `industryStatus` reads *Producing*, *Idle* (a factory nothing has supplied yet), *Needs* its missing inputs once supplied, *Output piling up* from half full (`backlog`) and *Storage nearly full* from nine tenths (`full`); given the game, a backlogged or full store names the active route that loads there. `townService` keeps `connected`, `served` and its transport `label`; its words, *Growing*, *Needs* a cargo (only while zones nearby wait on it), *Out of room* or *Steady*, are getters worked out when first read, because the HUD counts connected towns on every tick. The interface keeps search/filter inputs mounted during periodic entity refresh, returns explicit view changes to the top, and exposes building benefits in the catalog and inspector.

The Industries and Towns lists sort around `entityAnchor`, the tile at the camera centre (`camera.x / TILE − .5`), which `anchorEntities()` captures when `setView` opens either view and when the search, the industry type or `#entity-sort` changes; each capture returns `entityPage` to 0. Page turns and the 7 s refresh keep the anchor, so the pages stay one partition of one order. `entityFilters.sort` holds a sort per view: `nearby` (squared distance, the default), `name` (an `Intl.Collator`), `attention` for industries (`full`, `backlog`, `waiting`, then `producing`) or `population` for towns, with distance breaking ties. `entityRows()` filters and ranks every entity but reads status and population ranks once per anchor from a `WeakMap`, so a refresh updates a card's figures without moving it. `entityCards()` builds only the visible page of `ENTITIES_PER_PAGE` (40), between two `pageControls` bars shared with the route list, and computes town service from one `activeStops` list. Each card's `.entity-place` line gives the distance from the anchor and, for an industry, `nearTown(site)`: the town closest to the site centre, cached per site until the town list changes. `refreshEntities()` moves already drawn portraits into new cards of the same industry kind, so `drawUIArtwork` skips them, and restores `#panel-content` `scrollTop`. The refresh waits while focus is inside `#entity-list`, so a pointer page turn lets focus go with the old buttons and only a keyboard one refocuses its button, or the other one at either end. On a 2048² world Industries opens in about 9 ms and refreshes in about 9 ms, against 93 ms and 79 ms for all 576 cards before; Towns opens in about 5 ms instead of 44 ms.

`nextProject(game, {source})` returns one goal. Until a freight route has delivered it is the first cargo route: the 40 raw producers nearest the home town are ranked by buyer distance, home distance and extra buyer inputs, then walked lazily through `stopSiteKind(game, site)`. That returns `'road'` for a free road/rail tile or dry, non-mountain, unoccupied land that is not a complex slope within the catchment, `'port'` for shoreline water, and `null` otherwise; towns always count. Unservable producers and buyers are skipped, port-only producers rank 60 behind, a free road in the catchment ranks 5 ahead, and up to three `choices` `{source, buyer:{id,kind,name,x,y}, cargo, distance}` name distinct producer/buyer pairs. `source` keeps a chosen alternative when it is still offered. `firstRouteSteps(game, choice)` ticks a stop near each site, a same-mode path of at least three tiles between the three nearest stops on each side, a launched route of that cargo touching both sides, and its first delivery; steps carry the tool, button label and route-form draft the interface needs. The first-route goal also carries `plan`, the mode **Plan road** would lay, until the connect step is done. Later stages are 100 freight deliveries (with `progress`), the cheapest servable raw-producer-to-factory pair while no freight route ends at a factory that takes its cargo (stations nearest the source first; each extra factory input costs 40 tiles), carrying a supplied factory's output to its nearest servable buyer, a Chains fallback, a neighborhood in a town served within the last month, then the company milestones (see Company milestones), and finally free play once every chapter is complete. Searches are memoised in a `WeakMap` by network revision, site counts and last ids, station count and, for factory stages, route count; `game.revision` changes daily and is never part of a key. The stage itself, delivery totals and first delivery are re-read on every call, so a repeated call on a 2048 world takes well under a millisecond.

`app.js` shows the goal as `#objective-card` over the map’s top-right corner. `renderGoal` runs from `updateHud` and repaints only when a signature of title, detail, steps, progress and the chosen alternative changes. Only the first open step has a button; `runProjectAction(action, target, extra)` serves the card and the Build drawer’s project card alike (`source`, `city`, `stop`, `connect`, `launch`, `chains`, `routes`, `towns`, `atlas`). Stop and connection steps frame both sites, switching to the Region view when they are over 20 tiles apart or do not fit on screen. `connect` takes `extra.tool`, so a milestone can open Rail or Port directly; the drawer passes it as `data-project-tool`. The × stores the fold as a preference, `'folded'` or `'open'` under `transport-next-goal-v2` in `localStorage`; a non-empty v1 value (the old folded title) reads as folded. While folded, a new title only updates `#objective-chip-title` and sets `.changed` until the card is opened: a 1.2 s fade to the orange tint (instant under reduced motion) and, on phones, an orange instead of green pill dot. The `goal` layer hides the card entirely; Show on map opens it and turns the layer back on. When a goal has no checklist, **Company goals** takes the place of How to connect at the foot of the card. `notices.css` hides the card while the game menu, layers or map options are open, and below 1100px while the drawer or inspector is open. At 700px and below it is a one-line pill at the bottom left that expands on tap, and toasts move to the top while it is open.

While the first route's ends are not joined, `nextProject` sets `plan` to the connect step's mode (never when either site is port-only) and `#objective-plan` shows **Plan road**. `planFirstConnection` runs `planConnection` for the chosen pair; a pair that is already joined goes straight to the route draft, a failed plan toasts a warning, and otherwise it switches to Explore, keeps `connectionPlan` (view state, never saved), frames the path and both sites beside the card and the banner, and shows `#connection-plan-banner` in the route-pick banner's style. `connectionView()` hands the renderer the plan's mode as `tool`, its path as `preview`, no hover and its stops as `routeStops`, so it draws as a normal stroke preview while pointer input stays with Explore. `cancelRoutePicking` drops the plan, so a tool, any view but Routes, Escape, another world or a route pick ends it, and `renderGoal` drops it once Another idea or a finished connection changes the goal. **Build** plans again first: a different path or stop sites (growth or construction since the preview) replace the banner instead of building. It then takes one `captureUndo(game, 'connection', …)` journal, builds the path with `buildPlan` (all-or-nothing) and each new stop, rolls the whole bundle back with `undoConstruction` if a stop fails, pushes one undo entry (*Connection removed*), and calls `runProjectAction('launch')` with both stop ids and the cargo.

Passenger loading and delivery share `passengerEndpoints`, selecting a distinct pair of covered towns by nearest combined walking distance. Homes record `populationCityId` to retain population ownership after new towns are founded; outlying homes explicitly retain null. Housing creation and demolition share `housingCapacity`. A finished construction gesture refreshes network connections while paused.

`monthlyOperatingExpenses` separates upkeep from total cash expenditure. Routes accumulate allocated vehicle/station/network expenses; shared infrastructure is charged once, with unassigned infrastructure and factories left as company overhead. Legacy saves establish revenue baselines and accounting start days so historical fares are not compared with nonexistent historical upkeep. New worlds and loaded saves both write the next autosave before replacing the active game.

## Company report and loan

`createGame({startingFunds})` accepts 100000, 200000 or 400000 (anything else is 400000) for both money assignments and stores `game.startingFunds` only for a non-default choice. The start menu's **Starting funds and seed** section passes it through the worker payload. `monthlyUpdate` closes December (`lastMonth % 12 === 11`) into the optional `game.annual`, at most 200 entries of `{year, revenue, operatingProfit, delivered, population, routes, bestRouteId}`, right after that month's history entry: sums of the year's history months, the cumulative delivery count minus the one before the year, the December population, the current route count, and the route with the highest positive `profitThisYear` (before that December's rollover), or `null`. It reads only closed history, so it adds no randomness, ids or notices. The entry gains `property`, the year's summed history `property`, only when it is above zero.

`loanTerms(game)` returns `{loan, step, limit, rate, monthlyInterest, borrow, borrowInterest, repay}` from `LOAN_STEP` $50,000 and `LOAN_LIMIT` $250,000 in 1950 prices through `priceFor`, and `LOAN_MONTHLY_RATE` 0.005. `borrow` adds the next step up to the limit and `repay` removes one step when the balance covers it; both change only `money`, `loan` and `revision`, never income or expenses, and a cleared loan deletes `game.loan`, so a company that never borrowed keeps its original shape. `monthlyUpdate` first books the rounded interest into monthly and total expenses and operating expenses, before the month's profit is computed, and never into `route.expenses`; it runs only at month boundaries, so any frame partition charges the same. Validation accepts `loan` in [0, 1e12], whitelisted `startingFunds`, and finite `annual` fields with a string or null `bestRouteId`; saves without them load unchanged. A month closed below zero still posts its warning, now with topic `credit`, so `nextId` is unchanged.

`app.js` `openCompany` fills `#modal` with four inline-SVG sparklines over `game.history` (operating profit, balance, residents and each month's delivery delta, with a dashed zero line when a series crosses zero), the yearly table newest first, the top five routes by net a month (`net / days × 30.44`, at least a month old) and routes at least 90 days old with a negative net since tracking began, then the loan with Borrow and Repay; an action redraws the dialog in place, keeping its scroll and the pressed button. Game menu → Company and `#open-report` in the finance card open it. The card takes pointer input when pinned by a click or tap, when the button has keyboard focus, and when hovered on screens wider than 700px, where a strip bridges the gap under the balance; the full-width phone card still lets unpinned taps through. `#loan-row` and `#interest-row` appear only with a loan. `queueNewYear` adds `yearReview`, the closed year's operating profit, its change and its best route, with **Open report** beside **Review upgrades**, so `toast` accepts an array of actions and stacks two. `creditToast(notice, history)` in `ui-notices.js` passes a `credit` notice to the toast queue only when the month before it closed at or above zero or when it closes December; News still lists every one. `retireRoute` warns when the route is the last active one not needing attention and the balance plus its sale is below a road vehicle.

## Company milestones

`milestones.js` is DOM-free. `MILESTONES` is an ordered list of sixteen `{id, chapter, title, detail, unit, action, tool, target(game), button, progress(game) → {value, target}}` in four `CHAPTERS`. Each check is O(routes + cities + industries): freight milestones sum `route.delivered` over non-passenger routes only, never `game.totalDelivered`; town counts and the town of 2,000 use `activeCities` from `settlements.js` (towns within five tiles of a stop on an active route; generated towns reach about 1,800, so only a served town counts); profit compares the last history entry's `operatingProfit` with `priceFor(game, base)`; the industry at 200% needs an active route loading from it; the full chain walks the biome's `productionChain` edges (cached per biome) for raw → factory → factory → town cargo, each carried and the last delivered to a stop that covers a town. A founded town carries `founded: true`, validated as a boolean when present.

`evaluateMilestones(game)` runs once per simulated day from `tick`, after `maintenance`. It creates `game.milestones ??= {}` and stamps every unstamped id whose progress meets its target with `floor(day)`, in any order; the first run backfills an older save the same way. It spends no `nextId`, sends no notice and never grants money, so frame partitions and whole ticks stay identical. `validMilestones(game)` accepts `undefined` or a plain object of at most 64 ids of at most 40 characters whose days are integers in `[0, floor(day)]`; unknown ids are kept and ignored. Milestones are recognition only: a test asserts that nothing but `milestones.js` and `app.js` reads `game.milestones`.

`nextMilestone(game, preferred)` returns the first unmet goal of the lowest open chapter, or `preferred` when it is one of that chapter's unmet goals, with `choices` and `chapter`. A chapter is complete when all but one of its goals are stamped or met, so one unwanted goal never blocks the next. `nextProject` maps it to the card shape with `progress: {value, max}` (hidden for yes/no goals), `milestone` and `chapter`, and `progressText` formats counts, money, percentages and levels for the card and the dialog. `milestoneChapters(game)` lists every chapter with each goal's stamp, live progress and done state.

`app.js` seeds `seenMilestones` in `resetMoments` from the stamps, or for a company without any from `metMilestones(game)`, so a loaded save or its backfill announces nothing. `watchMilestones` runs with `watchRoutes` on each HUD update and queues `Milestone · <title>` (type `milestone`, action **Goals**) for at most one milestone per calendar month; later ones that month appear only in News and the dialog. The company's first freight delivery adds ` · Milestone` to its first-delivery toast and counts as that month's toast. News merges stamps within the log's span by day. **Game menu → Company goals** (`onGoals` in `compact-play.js`) and the card's **Company goals** link open `openGoals`, which lists the chapters, dates reached, progress and the card's current goal; like every modal it pauses the game until closed.

## Company rating

`company-rating.js` is DOM-free and imports only `economy-pricing.js`, `data.js`, `network-index.js` and `town-market.js`; `model.js` imports it, never the reverse, and `index.html` preloads it beside `milestones.js`. `RATING_PARTS` lists nine `{id, label, target, max, money?, linear?}` in a fixed order (their maxima sum to 1,000): `vehicles` 250/100, `stops` 150/100, `weakest` $25,000/100, `weakQuarter` $5,000,000/50, `bestQuarter` $10,000,000/100, `delivered` 400,000/400, `cargo` 8/50 (linear), `cash` $100,000,000/50 and `loan` (50, linear). Money targets are 1950 dollars priced with `priceFor` at the review day (`partTarget`). `ratingInputs(game, loan)` returns `{values, weakestRouteId}`: the vehicles of routes with a positive `profitLastYear`; the distinct stops of active, unpaused routes; the lowest `profitLastYear` a vehicle, only once `MIN_RATED_FLEET` (10) rated vehicles exist, else `null` with no route; the lowest and highest of the last twelve whole calendar quarters of `operatingProfit` in `history`; the last 12 months of `delivered`; the cargo kinds with `delivered > 0`; rounded `money`; and the loan. A route is rated (`ratedYear`) only when it has a `profitLastYear` (ttd-vehicle-models' yearly roll, the one per-route yearly mark) and its `accountingStartDay` is no later than 1 January of that year, so a route launched or edited during the year waits for its first whole year. `ratingPoints(game, values, day, loanLimit)` gives `floor(√share × max)` (or the share for linear parts), 0 for a null, zero or negative value, and for the loan 50 without one, `floor((limit − loan) / limit × 50)` with one.

`monthlyUpdate` calls `reviewPerformance(game, {loanLimit: loanTerms(game).limit})` when it closes March, June, September or December (`lastMonth % 3 === 2`), after the history entry, `closeYear` and the December `profitLastYear` roll, and copies a December score into that year's `annual` entry as `performance`. The review writes only `game.performance = {day, score, best, values, points, reached, weakest}`: `reached` holds the day each title was first earned (index = title, `titleForScore(score) = min(8, floor(score / 120))`), only ever grows, and stamps every title a jump passes with the review day; `best` never falls. When December 2049 closes (`CENTURY_MONTH` 1199, day 36525) it adds `century = {day, score, title, value}` once, with `companyValue(game).total`; later reviews keep it. `companyValue(game)` is on demand only (report, century card, century stamp): rounded cash, 45% of each vehicle's `paidPrice` (the sale refund), half of `priceFor` of the network (each `networkIndex` tile once: bridge or tunnel by mode, otherwise private road plus rail from `BUILD_COSTS`), each stop by mode and each `owner: 'player'` industry, plus `property`, less the loan. `property` is the resale value of `town-market.js` `companyProperty`: `SALE_SHARE` (60%, the sale refund) of each owned building's `propertyValue` and half of each plot's, rounded; countryside buildings earn nothing and count nothing. It runs one ledger a town, about 7 ms on a 2048² world.

`validPerformance(game)` (from `validateGame`, after the notification checks) accepts `undefined`, or integer `day` in `[0, floor(day)]`, `score` 0–1000, `best` from `score` to 1000, nine finite `values` (only `values[2]` may be null), nine integer `points` summing to `score`, one to nine non-decreasing integer `reached` days no later than `day`, a string (≤ 100 characters) or null `weakest`, and an optional `century` whose `title` is below `reached.length`; an `annual` entry's `performance` is an integer 0–1000. The displayed title is always `reached.length − 1`, so retuning thresholds never invalidates a save. `restoreGame` reviews a save without `performance` and with at least three history months once, silently (`backfill`): every title it meets is stamped with today and no century is added. `createGame` writes nothing.

The review runs at a day boundary inside `monthlyUpdate`, so whole, quarter and irregular ticks give identical results, and it never calls `notify`, `randomAt` or `makeId` or touches `money`, `revision` or `nextId`. It is O(routes + vehicles + history), under 20 ms for 2,000 routes and 10,000 vehicles; a save grows by about 300 bytes. Nothing in the simulation reads `game.performance`, and a test keeps its readers to `company-rating.js`, `model.js` and `app.js`.

`app.js` rewrites the finances card's `#rating-row` (the title and `N of 1,000`, with the score, review date and next title in its tooltip) when the review day, score, title or world changes. `resetMoments` seeds `ratingSeen` from `reached.length` and `century`, so a load announces nothing, and `watchPerformance` runs after `watchRoutes` on each HUD update: a longer `reached` sends one `rating:<title>` headline naming the highest new title (action **Open report**), the century one `rating:century` headline (action **See evaluation**), each falling back to a paced toast when `announceHeadline` returns false. `performanceSectionHTML` opens the Company report with the title, the score, an ink meter to the next title, the review dates, the company value (its parts in the tooltip), the century line and a folded **What counts** table (value, full marks at the review day and points per part, the weakest route with **Show**, then the titles earned grouped by day); the yearly table gains a Rating column. `openCenturyCard` opens only on request, through `openModal`, which pauses like every dialog.

## Achievements

`achievements.js` is DOM-free and imports only `data.js`, `chains.js`, `economy-pricing.js` and `settlements.js`; `model.js` imports it, never the reverse, and `index.html` preloads it beside `company-rating.js`. `ACHIEVEMENT_GROUPS` lists six `{id, name}` groups and `ACHIEVEMENT_FAMILIES` 21 frozen families `{id, group, name, detail, cadence: 'day'|'month'|'year', unit, measure(game, state, ctx) → number, rungs: [{id, tier, target, title}], hidden?}`; `ACHIEVEMENTS` flattens their 41 rungs in catalog order with `family`, `group`, `detail` and `hidden`, and `ACHIEVEMENT_IDS` is their set. Targets are round and rise within a family; every ladder starts beyond the Company goals' last step (10× the freight target, a $10M year, 50 towns, 5,000 residents, ten industries at 300%, every cargo, a 250-tile line). Money families compare 1950 dollars. `CARGO_ORDER` is frozen and append-only (mail is bit 20); `CARGO_BIT[key] = 1 << index` and `cargoMask(biome)` ORs the biome's `chainProducts` with mail (taiga 13 kinds, tundra 11, desert 12). city-property's `property` family (Rent, 1e4/1e5/1e6) reads `history[].property` and `annual[].property`, 0 when absent.

`game.achievements = {unlocked: {[id]: day}, since, cargo, yearCargo, bestYear, bestRouteYear, bestRent, red}` is optional and JSON-serializable; `createGame` adds `createAchievementState(0)`, and the codecs carry it as top-level state. `unloadVehicle` calls `noteDelivery(state, route.cargo)` on every paid delivery, which ORs the cargo bit into `cargo` (lifetime) and `yearCargo`. `tick()` takes the served-town set `stepSettlements` now returns and, after the month close, calls `stepAchievements(game, {closedMonth, served, networkTotals})` once per day boundary, so quarter days and whole days stamp the same records on the same days. A closed month with money below zero sets `red`. A December close divides the year's operating profit (its `annual` entry, else its history months), the best route's `profitLastYear` (ttd-vehicle-models' one per-route yearly mark, rolled just before) and the year's rent by that year's `inflationInfo` index into `bestYear`, `bestRouteYear` and `bestRent`, checks the yearly families (Whole economy reads `yearCargo`), then clears `yearCargo`. Month families then share one lazy context: `served` (injected, else `activeCities`), `networkTotals`, the longest active non-air path, the most distinct partner stops of one stop over active routes (a Map of Sets; duplicate routes on one pair count once), big and founded towns, industries at capacity 3, and one vehicle pass for the largest load and the oldest model year, which only Heavy haul (from 1981) and Museum piece (from 2000) ask for. Museum piece is any vehicle still running 50 years after its model year, so upgrading the first fleet never makes it missable. Day families (deliveries, fleet, back from the red, a nominal billion) run every day. A family whose rungs are all stamped is skipped; each newly met rung is stamped with `floor(day)` and never removed. Nothing here calls `notify`, `randomAt` or `makeId` or touches money, `revision` or `nextId`, and a test keeps the readers of `game.achievements` to `achievements.js`, `achievements-view.js`, the `model.js` hooks and `app.js`. The month step stays under 8 ms with 10,000 routes and vehicles and 2,000 stops, and 100,000 daily steps under 50 ms.

`stepAchievements` returns the ids stamped that day in catalog order and appends them to a module `WeakMap` log; `drainAchievementUnlocks(game)` returns and clears it, and is never saved. `validAchievements(game)` (the last check in `validateGame`) accepts `undefined`, or a plain `unlocked` object of at most 64 ids of at most 40 characters stamped with integers in `[0, floor(day)]`, an integer `since` in the same range, `cargo` and `yearCargo` integers in `[0, CARGO_MASK]`, integer bests in `[0, 1e15]` (`bestRent` optional) and a boolean or missing `red`; unknown ids are kept and ignored everywhere. `restoreGame` gives a save without records `backfillAchievements(game, {networkTotals})` after the route defaults: `since` is today, `cargo` ORs every route with deliveries, `red` reads money and history, `bestYear` and `bestRent` the best closed year of `annual` and of whole history years, `bestRouteYear` the routes' `profitLastYear`, and every family but Whole economy is checked and stamped today, with nothing logged, so a load never celebrates. `achievementProgress(game, familyId, context)` gives `{value, target, pct, rung, complete}` for the dialog without stamping.

`achievements-view.js` is DOM-free and builds the dialog as strings. `medalIcon(tier, {locked, mark, label})` is a tier roundel (`--tier-*` fill, ink `achievements` glyph); a locked one is a pale tint of its tier with an `--edge` ring, and an unfound hidden record shows **?**. `renderAchievements(game, {served, network})` returns the count earned (and **Records began** when `since` is after day 0) and one section per group with a row per family: its medal strip (each titled with tier, title and date), the next title or the top one, the detail, an ink meter with the measure (money in compact 1950 dollars, *This year so far* when the open year leads, the missing cargo tiles for Every cargo, *earned when the month closes* once met) and the last one earned with its date. Rows turn into one column with the medals first at 520 px and below; the rules live at the end of `dialogs.css`.

`app.js` opens the dialog from **Game menu → Achievements** (`compact-play.js` `onAchievements`, after Company goals), from a notice's or headline's **Open achievements**, and from the **Open** button on the Company report's summary line and the century card, through `openModal`, which pauses. `frame()` drains the log just before showing queued notices, on frames whose HUD pass has just run, so the day's century and title news are queued first; `activateGame` drains and discards it after `resetMoments()`. `queueAchievements` sends gold and platinum as `achievement:<id>:<tier>` headlines through `announceHeadline`; the rest, and any headline refused, go through `ui-notices.js` `achievementNotices(ids)`: one paced milestone toast naming a single record, or one line at the highest tier for two or more (`names()`). At most one such toast is shown a game month (`achievementMonth`, seeded in `resetMoments` from the stamps, like `milestoneMonth`); later records that month wait in the dialog. `toast(message, {tier})` leads with the medal, edges the toast in the tier colour (`notices.css`) and holds gold and platinum for 8 seconds. The century record waits on the century card, which shows the platinum medal beside the count.

## Transport contracts

`contracts.js` is DOM-free and takes station coverage as a `coverageOf(station)` callback, so it never imports `model.js`. `game.contracts` is optional: absent until the first offer, then an array of at most `MAX_CONTRACTS` (8) `{id, cargo, sourceId, target: {kind: 'industry'|'city', id}, distance, multiplier, offeredDay, expiresDay}`, where an awarded contract adds `{routeId, awardedDay, until, earned}` with integer days and `until = awardedDay + 365`. `validContracts(game)` checks those shapes and ranges (multiplier 1–4, `expiresDay = offeredDay + 365`, days no later than today, freight cargo only). Ids are never checked against the world: `contractState(game, contract)` reads a missing producer, buyer or route as `'expired'`, otherwise `'offer'`, `'active'` or `'complete'`, so bulldozing a site cannot invalidate a save.

`stepContracts(game, coverageOf)` runs from `monthlyUpdate` after the month's accounts close. It keeps offers, active contracts and complete ones for 31 more days (so the interface sees the finish), then, once any freight route has delivered or offers already exist, fills empty slots up to `OFFER_SLOTS` (3) while the list has room. Each slot draws at most 64 candidates from `randomAt(game, calendarMonth, 'contract', slot * 64 + k)`: one draw picks a generated producer (`owner !== 'player'`, with outputs, and producing if it has inputs), its fractional parts pick the output and a buyer among industries with that input and, for `TOWN_CARGO`, towns, whose centres lie 20–70 tiles away (`nearbyIndustries`/`nearbyCities`). A pair already listed, or served by an active route of that cargo, is skipped. Ids are `contract-<month>-<sample>`; no `nextId` is spent and no notice is sent. `multiplier = clamp(1.6 × f(10) / f(d) − 1, 1, 4)` with `f(L) = distancePay(L) / L = (L + 12) / 9L`, rounded to hundredths: fares grow with `distancePay` while trips grow with `L`, so a served pair earns 1.6× what a 10-tile route earns per vehicle-day; the bonus is about 1.2 at 20 tiles, 1.7 at 40 and 2.0 at 70, and never reaches the 4× the validation still allows for older saves. A 2048² month takes well under 2 ms.

`unloadVehicle` adds `contractBonus(game, route, fare, day, coverageOf)` to a paid fare when `game.contracts` exists. A route serves a pair when its first stop's coverage holds the producer and its last stop's holds the buying industry, or has the town as `cities[0]`, the town that receives town cargo. Pair matches are cached per route in a `WeakMap` keyed by `game.revision` and the list's identity (every step that changes the list assigns a new array), so unloading stays O(1). The first delivery on an open, unexpired offer stamps the award; while `day < until` the route's deliveries earn `round(fare × multiplier)` more, added to route revenue, monthly income, money, total revenue and the delivery event, and summed in `earned`. A route holds one contract at a time. `forecastRoute` never reads route revenue, so forecasts stay at normal fares.

`app.js` renders `#contract-offers` from `fleetControls` as a `<details>` folded by default (its open state lives for the session) and hidden while no offer or contract is live; `refreshUpgradeControls` refreshes its count and rows. Rows name each site, an industry by its nearest town, and **Show** frames both in the map area the inspector leaves free and inspects the producer, or only frames them at 700px and below. `routeRate` returns base net and bonus side by side for a route with an active contract and `markContractRoutes` flags its rate with `data-contract`, so the card keeps its height. `watchContracts` runs with `watchMilestones` and compares states with the previous HUD update: a new `'active'` queues *Contract won* (type `milestone`) and `'active'` → `'complete'` queues the completion with its earnings (type `ok`), both with the route as target; the first update after a world is activated only records states, so loading replays nothing.

## Industry openings

`industry-openings.js` is DOM-free and pure: it reads the game, never mutates it and never imports `model.js`. `planIndustryOpening(game, month, {force=false})` returns `{kind, x, y, anchorId}` or null. Unless forced it returns null before month 24 (January 1952) and until `hasCarriedFreight(game)`: a route whose cargo some `INDUSTRIES` entry outputs has delivered, so passengers and town-only cargo never count and, whenever it holds, `nextProject`'s first-route stage is over. The month's roll `randomAt(game, month, 'industry-opening', 901)` comes next, and at or above `maxChance` (.1) nothing else runs, so nine months in ten cost one hash. `openingAnchors(game)` lists, in town order, the towns with a stop within 5 tiles (`hypot`) of their centre, walking the stops through `nearbyCities`. No anchor, a roll at or above `openingChance(n) = min(.1, .03 + .005n)`, or `openedCount(game) >= openingCeiling(game)` ends the month. The ceiling is `max(4, ceil(.5 × original))`, where original sites are `owner !== 'player'` without `openedDay`, so legacy saves need nothing. Salt 903 picks the anchor town; attempt k (48 at most) picks a kind of the biome's catalog by weight with salt 1200+k (raw producers 2; oil wells and processors 1), an angle with 1000+2k and a distance of 10–24 tiles with 1001+2k, and the first plot `openingSiteProblem` accepts wins. The channel and salts are new; no existing key changes.

`openingSiteProblem(game, kind, x, y)` returns a reason or null, cheapest first: `site` (bounds; water, road, rail, bridge, tunnel or zone on the footprint; mountain the kind cannot use; the kind's terrain), `habitat` (the anchor tile's resource as world placement chooses it: forest for logging camps, rock or mountain for mines and quarries, sand for sand pits, grass for farms; fisheries already need a shore), `town` (a Chebyshev gap under 10 from the footprint to a town centre, which keeps it outside the widest square a town grows its streets in), `stop` (`industryDistance ≤ 5` to a stop, the test `stationCoverage` uses, so no catchment changes), `same-kind` (a twin within 12), `crowded` (5 industries within 16), `margin` (another industry's footprint within 5 tiles, or a zone or building within 4: industry surveys reach 4 tiles and settlement surveys 3, so nobody gains pollution), `slope` (the footprint's vertex heights span more than 1), `partner` (within 40 tiles an industry buys an output, or a town does for `TOWN_CARGO` or with workshops that take it, and a processor also has an industry making one of its inputs) and last the Build tool's `industrySiteProblem`, reported as `site`. `OPENINGS.catchment` equals `STATION_RADIUS`, and a test holds them together.

`model.js` `openIndustry(game, month = calendarMonth(game), {force=false})` runs from `tick` right after `monthlyUpdate` (so after `stepContracts`) and places the plan with `placeIndustry(game, kind, x, y, {owner, openedDay})`, which `build()` shares: every recipe cargo starts at 0, except that a world raw producer starts with twelve days of output as a generated one does; then `initializeIndustry`, `releaseTerrainObjects` on the footprint and an unjournaled `revision` bump. An opened site is `owner: 'world'` with `openedDay = floor(day)`, validated as an integer in `[0, floor(day)]` when present. Industry and town ids come from `freshId(game, prefix, list)`, which skips any id the list already holds: generated towns and industries are numbered from 1 while `nextId` starts at 100, so on 1024 and 2048 maps a built or opened industry, or a founded town, used to duplicate a generated id and make the save unloadable. Without a collision ids are unchanged. Each opening spends one industry id and sends one notice, which spends a `nextId` as an expansion notice does; it is a real simulation event, at most once a month and never before 1952: *New coal mine opens near Pinehaven.*, type `success`, topic `industry-opening`, the site as target and a template with the site's `{industry}` token and the `{town}` closest to its footprint. The toast is silent, **Show** inspects the site while it exists, News keeps the notice, and the inspector adds *Opened in 1953*. Industries never close: bulldozing an opened site frees a ceiling slot. `force` is for tests and debugging only.

## Notices and news

`model.js` keeps the newest 24 notices first, as `{id, day, message, text, type}`. `notify(game, message, type, {topic, target, template})` adds an optional `topic` (up to 32 characters), `target` `{kind: 'industry'|'city'|'route', id}` and `template` (up to 1,000 characters), the same sentence with `copy.js` tokens in place of names; every notice that names something carries one. Route disconnections use topic `route-connection`, industry expansion uses `industry-growth`, an industry opening uses `industry-opening` (grouped as *3 new industries opened: …*), and town founding targets the new city. Bulldozing an industry collects, before removal, the freight routes with a stop in its catchment whose `freightPair` holds; after removal, each one whose pair fails gets a `route-supply` warning targeting the route: *lost its timber supplier* naming the start stop, or *lost its buyer* naming the end stop. It is a player action, so the extra ids shift `nextId` only then. Validation checks both fields only when present, so older saves load unchanged. Every notice consumes one `nextId`, which keys vehicle randomness, so the interface derives its own moments instead of adding model notices.

`ui-notices.js` is DOM-free. `collectNotices(notifications, lastId, max=24)` returns unseen notices oldest first, or the newest six when the last shown id is no longer in the log. `groupNotices(list)` merges each burst of a groupable topic (`route-connection`, `route-supply`, `industry-growth`) into one entry that keeps every target and, when every member has a target, a template naming each one (*3 routes are no longer connected: {route:a}, {route:b} and {route:c}.*); legacy notices without a topic are recognized by their wording, old and new. `crossedMilestone` and `newYearNotice` define the town thresholds and the January text, and `creditToast` decides which below-zero warnings toast.

`app.js` collects and groups notices on each HUD update into a queue. The queue shows at most two entries every 400 ms, warnings first, and paces town moments to one every two seconds; a batch beeps at most once. `toast(message, options)` still accepts the boolean error flag, or takes `{type: 'ok'|'warning'|'error'|'milestone', action: {label, run} or a list of them, key, silent}`; a repeated key on a visible toast updates its ×N count and restarts its timer. Only the action button takes pointer input. `activateGame` seeds the pricing year, the known routes and town population peaks, so loading a save replays nothing; a world before its first day shows its welcome. A freight route launched during the session, or a loaded one that has not delivered, announces its first delivery. A January repricing waits while an input in the panel has focus and re-renders when focus leaves it. The News dialog reads `game.notifications` directly and offers Show only for targets that still exist. When a clicked action reveals a control in the drawer, the focused control inherits the pointer press, so Space still pauses instead of pressing it.

`headlines.js` is DOM-free and derives rare good news from state the simulation already keeps, so it never calls `notify()`, spends `nextId`, bumps `revision` or draws on `randomAt`. `headlineWatch(game)` holds the towns already served (a finite `lastServiceDay`, plus `cities[0]` and `cities[1]`, which the starter bus serves) and the modes already run (road, every mode with `delivered > 0`, and each saved `first:<mode>`); `activateGame` rebuilds it, so loading replays nothing. `detectHeadlines(game, watch)` reports each town's first `lastServiceDay` as an arrival, naming the vehicle and route that `arrivalRoute` finds (the newest delivering passenger route whose `passengerEndpoints` include the town, or town freight into a stop within `STATION_RADIUS`), and the first rail and water deliveries as company firsts; a first that also brings a town its first arrival is one entry about that town. `headlineTier` and `townHeadline` give the 2,500, 5,000 and 10,000 resident tiers from the town peaks the HUD already tracks, and `vehicle-models.js` `modelHeadline(model)` the models headline when January's named model begins a new family (headlines.js holds no model copy). Entries are `{key, kind, day, title, detail?, art?, target?}` with a transient `routeId`. `recordHeadline(game, entry)` is the only writer of the optional `game.headlines` log, newest first and at most 24, with company firsts never pruned; it trims and clips every field to what `validateGame` accepts (unique keys up to 64 characters, kinds up to 24, a whole day up to today, titles up to 140, details up to 240, art up to 16, a target of an industry, city or route), because one bad entry would stop every save. Older saves have no log and load unchanged.

`app.js` calls `watchHeadlines()` on each HUD update, before `watchRoutes()`, and routes the town tiers from `watchTowns` and the models from `queueNewYear` through `announceHeadline(entry)`, the hook later company news can use too (kinds `rating`, `achievement` and `contract`). It records the entry and, with headlines on, queues it and takes over the route's first-delivery toast; it returns false when the log already has the key or the card is off, and the caller then toasts as before. The queue keeps three entries by `HEADLINE_PRIORITY`, drops any older than 120 s, and shows one card in `#headline-slot` only on the plain map (inspect tool, no route picking, no dialog) and at least 15 s after the last one closed. A card lasts 10 s of visible time: pointing at it or focusing inside it holds it, and while CSS hides the slot under a menu, the tool bar, a route-pick banner or a raised phone sheet, `checkVisibility` stops its clock. It never takes focus or changes speed; × and Escape dismiss it and return focus to the map. The News dialog merges the log with the notices by day, headlines first on a day, and its **Show headlines on the map** checkbox is kept in `transport-headlines-v1`.

## Square-world persistence and material detail

`transport-procedural-v1` retains the generation descriptor and packed changed tiles. `rememberGeneratedWorld` stores an exact four-byte baseline per tile plus sparse extras in a WeakMap, using 16 MiB for 2048² without retaining a second object grid. Every save compares current fields with that baseline, preserving direct edits, unknown properties, nested fields and deletion/reversion. Changed indices use delta varints and existing UTF16 tile packing. Loading regenerates the explicitly versioned recipe, captures its baseline and applies patches. Legacy JSON and compact-v1 saves continue to decode. Metadata listing validates packed fields without regenerating a second continent.

`water-art.js` paints cached depth/bank detail in the water clip; small live ripples derive from simulation day. `raster-houses.js` supplies nine generated house designs per biome, with 256×256 transparent masters and prefiltered 16/32/64/128-pixel sprite cells. The runtime chooses a cell size matching `32 × zoom × devicePixelRatio` and loads each density, the 256-pixel master included, the first time a draw needs it. Artwork occupies a 32×32 square within the existing 32×40 sprite envelope. 

Startup waits at most four seconds for house and world artwork, loading both groups concurrently, and only the densities a view draws at once: `startupArtCells()` gives the 16–64-pixel cells, or up to 128 at a device pixel ratio of 1.5 or more. Requests go out density by density across atlases, so a slow connection shows authored art everywhere before any of it sharpens. Every draw works out the cell an eager load would use (the smallest density covering its size, or the nearest healthy neighbour of a failed one) and fetches it if missing; the best loaded density stands in meanwhile, so the map converges to exactly what eager loading draws. 256-pixel cells therefore load only when a view needs them, such as upright industries at Town zoom on a Retina display, Detail zoom or interface portraits. Each decoded density becomes available independently; a missing resolution uses another loaded resolution of the same artwork. Only changes to drawn pixels are published: the first art of an atlas or climate, a density a draw stood in for, or its failure. Changes publish together 150 ms after the last one, at most 500 ms after the first, and at once when nothing is loading. Each publication increments a separate artwork revision, refreshing sprite/chunk caches and interface thumbnails without changing game state. `preloadWorldArt()` and `preloadHouses()` without `cells` stay eager loaders for pixel checks. Missing biome artwork can use the same identity from another available climate; native drawings remain the final fallback when no image is usable. Connectivity recovery retries only missing densities. `worldArtStats()` reports usable atlases, failures and actual generated-image draws by identity. Asset loading, downscaling provenance and prompts are documented in `assets/houses/README.md`. `processing-sprites.js` retains native factory/extractor fallback drawings; production rules remain in the economy catalog.

`index.html` includes a visible full-screen loading dialog and an inert game shell. The lightweight `boot.js` promotes that dialog to the native top layer and paints before importing `app.js`; import/startup failures keep a retry action available. `loading-screen.js` reports three actual preparation stages, with live status text and reduced-motion support. Startup, new-world creation and named-save reading paint the loader before expensive synchronous work, then render the map and minimap before revealing the game. Loading blocks gameplay shortcuts, simulation frames and background autosaves. Recoverable save/generation failures close the loader in `finally` and return to the original dialog. `tests/loading-screen-browser-check.mjs` exercises delayed and failed imports, local-save loading, storage failure/retry and mobile reduced motion in isolated storage.

Module loading is phased so neither import chain is walked one level at a time. `index.html` has `modulepreload` links for `loading-screen.js` and the whole static graph of `start-menu.js`, dependencies first. That graph is 13 imports deep. After the menu paints, `start-menu.js` waits for an idle moment (`requestIdleCallback`, or 500 ms without it) and adds links once for `APP_PRELOAD` from `app-preload.js`. These are the game modules the menu does not load, `app.js` last. They download and parse without running, so Create no longer waits on `app.js`'s own graph. Preloading both graphs from `index.html` delayed the menu. `world-worker.js` is never listed, because a document preload does not reach a module worker. A preload that fails fails the later import the same way, so the retry screen still appears. `tests/module-preload.test.mjs` compares both lists with the static imports: a changed import needs a matching list edit.

`world-v2.js` combines the terrain and placement recipes in `world-terrain-v2.js` and `world-placement-v2.js`. Recipes through version 6 retain their original geography: recipe 4 preserves underlying elevation beneath roads and settlements, recipe 5 allocates full building and industry plots, and recipe 6 adds level multi-tile terrain objects. The starter dry-land area blends into its surroundings. This avoids rectangular trenches around settlements. New square worlds use recipe 7: `world-mountains-v7.js` adds seeded local peaks, short asymmetric ridges and desert mesas to the saved elevation field before settlement placement. High ground between features becomes broad valleys; water and the protected opening corridor keep their original elevations. Peaks reach the visual level-7 ceiling without a second world-sized height array. New square worlds now use recipe 8 (see Recipe 8 landscape and towns); `world.js` retains recipes 1–7 and the old rectangular sizes, with frozen digest fixtures for each. Shared deterministic primitives live in `world-noise.js`. The save descriptor, baseline and validation carry the explicit generation version, so old companies regenerate their original geography. Never change a released recipe without introducing a new version and retaining existing digest fixtures.

## References and camera

DESIGN.md 7, 8 and 10 in code: three modules that import without a DOM build the markup and the motion, `refs.css` styles them (tokens only, loaded right after `components.css`), and `app.js` wires it to the map and the camera. Surfaces adopt them one by one; `tests/ui-refs.test.mjs` checks the markup and timing as strings, and `refs.css` against the 16.3 class contract.

**`ui-motion.js`** (no imports). `reducedMotion()` reads `prefers-reduced-motion` live on every call. `scrollIntoViewSafe(el, opts)` scrolls inside a panel smoothly, or with `behavior: 'auto'` under reduced motion; every scroll that was smooth goes through it (`tests/ui-lint.test.mjs` counts `behavior:'smooth'` down to none). `cameraDuration(screens)` is `280 + 60 × screens` ms clamped to 280–480, and 0 (a cut) under reduced motion. `tint(el)` adds `.is-tinted` for 600 ms, `delta(anchor, text)` floats a `.delta` beside the anchor in a fixed layer for 1.2 s (error or ok colour by the sign), and `crossfade(container, render)` holds the old height as `min-height`, swaps the content, fades it in over 120 ms and lets the height go after the next frame's measure. Tints and fades do nothing under reduced motion.

**`ui-line.js`** (the line language). `bullet(route, {size: 20|16, named})` is `span.bullet.bullet--<mode>` (plus `bullet--16`, `bullet--wide` from two digits and `bullet--light` for light fills) whose inline `--c`/`--on` are the `var(--line-N)` tokens `lineFor` picks; the numeral is `route.number`, and it is `aria-hidden` beside a name or else `role="img"` named *Route 2*. Road is a rounded square, rail a circle or stadium, water a pill 1.6 times as wide and air a diamond or pointed hexagon drawn by `clip-path` layers under the upright numeral. `roundel({unused})` is a stop. `strip({route, stops, vehicles, waiting, direction, broken, proposed, label})` returns the 56 px strip: the 4 px line, a roundel at each stop (both ends, others by their nearest path point), capsules placed at `progress / (path.length - 1)` (`STRIP_CAPSULES` = 8, then a `+N` tag), a cargo tile and count above stops with cargo waiting, three chevrons for freight, a dashed error gap with the `broken` glyph at `broken` (a share of the line), a dashed proposed line, the end names underneath through `label(stop, i)` (surfaces pass stop references), and an `aria-label` that reads the diagram. `drawOnce(stripEl)` draws the line once in 400 ms. `ladder({steps})` marks each `{label | html, done, current, part, meta}` done, current (the first not done unless one says so) or next, and dashes the connector into a new part.

**`ui-refs.js`**. `ref(kind, id, label, {variant, route, cargo, mode, onInk, gone, size, after})` is the one reference: `<button class="ref ref--prose" data-ref="kind:id" aria-label="<label>, <kind>">` holding the kind's mark (`REF_KINDS` route, stop, town, industry, vehicle, cargo: a bullet, a roundel, the town glyph, the output cargo tile, the mode glyph with the route's small bullet after the label, a cargo tile) and the escaped label; variants `prose`, `row` (a whole list row, `after` holding the rest of it), `compact` (the mark alone) and `onInk`. No id, or `gone`, gives plain `span.ref--gone`. `resolveRef(game, ref, {vehiclePoint})` returns `{exists, kind, id, label, entity, frame}`; a frame is inclusive tiles `x0..x1, y0..y1` with `cx, cy` when the view centres elsewhere: a route's path bounds centred on its projected extent (as Show frames it), an industry's footprint, a town's centre ± 4 tiles, a stop's tile or an airport's 6 × 2 site, a vehicle's position (`vehiclePoint`, the renderer's `vehicleWorldPoint`, for planes in flight). Cargo has no frame. `refFor(game, ref, options)` reads label and mark from the game, and says *a retired route*, *a removed stop*, *a closed industry* or *a sold vehicle* for what has gone; `refMark` gives the mark alone; `renderTemplate(template, game, {onInk})` turns `copy.js` tokens into prose references, `{money:n}` and `{date:day}` into copy text, and escapes the rest. `installReferences({getGame, view, onOpen, onCargo})` adds one delegated set of document listeners: pointer hover counts after 150 ms (leaving waits 700 ms while an edge pointer for the same target is up), keyboard focus (`:focus-visible`) at once; either sets `view.hoverRef` and toggles `.is-linked` on every `[data-ref]` with that value. A click or Enter calls `onOpen(ref, {source, open: true, keyboard})`, `data-ref-action="show"` asks for `{open: false, hold: 4000}`, and a cargo reference calls `onCargo`. A touch press held 450 ms previews the target and swallows its context menu and click. `linkFromMap(ref)` links the panel references of whatever the map pointer is over.

**`app.js`**. `initReferences()` runs at startup with `revealRef` as `onOpen` and a Chains-style cargo lens as `onCargo` (it stays until its × or Escape). `revealRef(ref, {source, open, hold, keyboard})` opens the target first (a route through `showNoticeTarget`: Routes at its card; a place through `inspect`, a vehicle through `inspectVehicle`, ending a construction tool; the drawer it came from stays open unless on a phone or where it would hide most of the inspector, `underDrawer`), closes the dialog a reference came from, then moves the camera with `glideCamera(frame, {zoom, offset, ref})`: Town view for places, the current view for vehicles. `glideCamera` measures the jump with `renderer.screensTo`, glides for `cameraDuration(screens)`, or cuts past 3 screens and under reduced motion and rings `ref` for 1.2 s; a jump past 3 screens puts **Back to where you were** (`.back-chip`) at the bottom left of the band for 8 s, which cuts back to the camera it saved. `showRoute`, `locateIndustry`, `locateDestination`, the town list, `showNoticeTarget` (a route is shown as well as opened), `showContract`, the Next goal steps (`runProjectAction`, `framePoints`) and Follow keep their framing maths and call `glideCamera`; Follow's frame follows its carrier while it glides, and ending Follow before it lands stops the camera (`glideTo(null)`). `refShown` rings a target for `hold` ms (Show on map) or after a cut, and `frame()` passes `refView.hoverRef` or that ring to `render()` as `hoverRef`; the redraw key includes it and `stepCamera`'s answer.

The visible band (`syncBand`) is the map less the panels over it: the open drawer, the inspector (a phone sheet too) and anything marked `data-band`. Each panel gives up the side of the map that keeps the most of it, and one that would leave under a third is ignored; layout boxes (`offsetLeft` up the offset chain) count a sliding drawer where it will rest. A `ResizeObserver` and a class and `hidden` observer on the drawer and inspector, and the drawer's `transitionend`, re-measure it in a frame; camera moves measure it at once. It is kept as `--band-l`, `--band-r`, `--band-t` and `--band-b` on `.map-section` and passed to `renderer.setBand`. `#map-overlays` (`aria-hidden`; its buttons take no focus) holds the ink overlays, placed with `worldToScreen` and recomputed only when the camera, the band or the target changes: one `.edge-pointer` toward a hovered target whose frame lies outside the band (its mark, name and `copy.tiles` distance from the tile under the band's centre, a signal chevron turned toward it; itself a Show on map reference), the `.map-tag` selection tag above a selected vehicle, building or workshop, or a town, stop or site whose name the map is not already showing, and the back chip. In Explore, each new tile the pointer handler picks calls `linkFromMap` with the stop, industry or town centre on it (reusing that pick).

`inspect(x, y, kind, origin, {from, source, back})` and `inspectVehicle(id, refresh, {from, source, back})` keep `inspectorTrail`: a reference inside the inspector (`from`, the place it showed with its scroll and name) gives the next inspector a `.inspector-back` line, *‹ Back to Stone quarry*, which reopens that place at its scroll; any other opening starts a fresh trail, and a live refresh keeps it. `inspectorSource`, the reference that opened the inspector, takes focus back when Esc or × closes it (the map takes it when focus was inside and the source is gone). Escape steps back one level at a time (DESIGN 10.5): an open popover or menu first (the zoom menu, map options, layers, the game menu), then a stroke, the tool or a planned connection, the inspector (its Back target first), the drawer (dropping a Routes or Industries lens), and with nothing open the cargo lens; dialogs handle their own Escape.

**`renderer.js`**. `glideTo(frame, {duration, zoom, offset})` eases the camera (the `--ease` curve, `cubic-bezier(.2,.7,.2,1)`, solved by bisection) from where it is to put the frame's centre at the middle of the band (or `offset` px from the canvas centre, which Follow and the Next goal framing use), on a clock from `performance.now()`; a zoom step lands first when zooming out and last when zooming in, `duration` 0 cuts at once, and `glideTo(null)`, `pan`, `zoomAt`, `setZoom` and `focus` cancel it. `stepCamera(now)` advances it from `frame()` and `render()` alike and returns true while the camera glides or a locator fades in. `setBand(rect)` sets the band in canvas CSS px; `screensTo(frame, {zoom, offset})` is the jump in band widths or heights at the lower of the two zooms. `render(now, {hoverRef})` draws a hovered route like `highlightRoute` with its bullet at both end stops (after the stop's row where the row left it out, or under the roundel when a town name is in the way), and a town, industry or stop (an airport's whole site) or an on-screen vehicle with the `MAP.locator` ring, fading in over 120 ms (at once under reduced motion). `getStats()` adds `hoverRef` and `gliding`. `tests/interconnection-browser-check.mjs` covers the whole loop on seed 1847 with the stone route.

## Continuous terrain relief

`terrain-elevation.js` reads the precise saved `tile.elevation` on a 0–16 scale; water is level zero. This legacy scale remains the source representation for old procedural recipes and save metadata; player-facing heights use eight discrete vertex levels. Rendering does not mutate terrain or add a second saved height field. A nonnegative cubic B-spline over neighboring tile centers blends heights, biome ground colors and geological coverage into a continuous surface. The overview retains analytical gradient lighting. The isometric mesh requests `terrainReliefRaster(..., {lighting:false})` (fourth parameter), retaining the blended texture colors while applying lighting from the actual geometric faces.

Ground is sampled at six points per tile into a reusable small canvas, then smoothly drawn into the existing bounded chunk cache. Sampling phases, soil moisture, fine grain and geological texture are world-aligned, producing byte-identical shared samples in overlapping chunks. Two-tile fingerprint padding covers the spline support, and fingerprints include fractional elevation. Forest density follows neighboring woodland and regional noise. Single-tile rock density is reduced to 18% of its former selection rate; large rock parcels retain their visible footprints. Mountain sprites are suppressed, with their geological texture retained on the raised ground. The overview uses the same altitude colors and a cheaper slope estimate. A material field combines world-aligned moisture patches, fine grass/sand grain and restrained geological variation. The renderer avoids repeated per-tile sand arcs and pale washes that would obscure that material. `landscape-scenery.js` selects presentation-only patches of local flowers and grasses, keeping scattered detail stones rare without rewriting saved ecology. Habitat patches mix species instead of repeating lichen everywhere; empty detail stays bare after bulldozing or earthworks. `tests/terrain-elevation.test.mjs` verifies interpolation and seams; `tests/terrain-elevation-browser-check.mjs` covers live elevation edits across chunks, exact restoration, all environments, zooms and display densities.

`shoreline.js` traces water boundaries, filters neighboring contour controls and adds subtle world-aligned bank variation. The resulting curves replace repeated rounded tile corners while preserving land/water tile centers, isolated ponds and narrow channels. Padded chunks produce identical shared curves; `water-art.js` adds local shallows and damp banks without a uniform bright outline. Its coast pass follows the same smoothed contours, ignores artificial chunk edges, and clips translucent shelves and broken foam to water. Animation uses a sparse seed-based selection at every zoom and simulation time, so Pause freezes the exact frame; moving ripples never rebuild terrain chunks. `tests/shoreline.test.mjs` checks navigation clearance and seams. `tests/landscape-realism-browser-check.mjs` captures deterministic town, forest, highland and coast scenes across environments, zooms and display densities, and checks canopy clipping and cache limits in isolated browser storage.

## Raised isometric geometry

`terrain-geometry.js` maps source elevation to eight integer vertex heights, 0–7, with 24 projected pixels per height step. The legacy 0–16 source helpers and structure metadata remain unchanged. An exact Chebyshev lower envelope limits all eight neighboring vertices to one level of difference, using an eight-point halo; a 96-entry LRU caches 32×32 vertex chunks without a whole-world height array. Each tile has two triangles split along NW–SE. Shared corner points touching water are at sea level. The diagonal bound prevents folded faces even on the taller slopes. Centers interpolate from NW and SE; they are not independent height samples. `surfaceHeight`, `projectGround` and `pickGround` use the same planes for rendering, pointer selection and overlays.

`terrain-mesh.js` warps the existing authored ground and network textures onto those triangles. Each face uses orientation-dependent surface-normal lighting, with antialiased joins tested at every supported raster scale. Each visible 6×6 terrain chunk caches only its projected mesh against the existing memory budget. One reusable source-texture canvas serves every chunk, avoiding redundant Retina bitmaps and eviction churn without reducing texture resolution. The geometry halo participates in chunk fingerprints, so nearby height edits refresh every affected slope. Large-map minimaps retain bounded sampling.

Camera focus, panning and anchored zoom use the raised projection. Ground grids and construction previews follow the mesh. Buildings sit on foundations at the highest center or corner in their complete footprint, with retaining faces where necessary. Bridge decks resolve a constant span height from their displayed bank levels; network-only shore textures ramp to that deck at the shared edge, and vehicle positions follow the same approach. Lighting receives separate building, ground and transport projection callbacks. None of these view transforms alter saved elevation, networks or routes.

## Terrain construction controls

`app.js` groups earthworks and explicit crossings in the expandable Network → Terrain & crossings panel. Raise/lower gestures use the same deduplicated construction plan, prices, notifications, revision handling and autosave path as other tools. Terrain tools snap to visible grid vertices and mark their connecting edges. Each raise/lower drag captures every selected point’s target before mutation, verifies the final limited surface, and commits the complete stroke atomically. A point already moved by a neighboring edit is not lowered twice. Quotes and previews use the same plan. Level area uses a rectangle anchored at its first point’s displayed integer height. `planTerraformLevel`, `quoteTerraformLevel` and `buildTerraformLevel` preflight the complete area and funds before charging per changed height step. A point already displayed at the requested height is a free no-op, even when its legacy source is fractional. Raises and leveling boundaries reject heights the limiter cannot display; edited sources save as level/7 through the existing codec. Adjoining water and occupied cells protect their shared corners. A bounded counterfactual also rejects edits whose slope influence would move more distant occupied corners. Bridge/tunnel gestures snap to one horizontal or vertical axis; the shared plan quote provides level, total price and validation feedback. Road/rail selection changes the explicit crossing mode without adding four permanent toolbar buttons.

Span validation and atomic construction belong to the model and construction planner, so previews and committed spans share the same geometry and constraints. New crossings require flat endpoint cells at matching displayed heights. Interior bridge faces stay at or below the deck with clearance, and tunnel faces stay at or above the bore with cover. Legacy raw-height validation remains available for saved crossings; new source-clipped banks use the geometric envelope. The renderer uses the existing saved elevation for terrain and span metadata for level crossings. `tests/earthworks-browser-check.mjs` exercises the controls through browser pointer events and isolated local storage.

`terrain-engineering.js` centralizes earthwork protection, span geometry and network edge validation. New ordinary networks use the rendered four-corner surface: near-flat ground accepts junctions, while monotonic straight inclines permit only their uphill axis. Side slopes, corner slopes, crowns and turning/joining a ramp sideways reject the complete stroke before payment. Existing saved networks remain traversable. Interior span tiles store `structureLevel` and `structureAxis`; approaches remain ordinary network tiles. Pathfinding permits entry along the span axis at its deck or bore level, while legacy untagged networks retain their original connection rules. Construction invalidates route caches once, demolition removes the metadata, and the existing sparse save codec preserves both elevation edits and span fields without a format migration. `structure-visibility.js` decides underground vehicle visibility for the renderer. Model tests cover atomic failures, routing, repairs and saved-world restoration; the engineering renderer check verifies portals, underground vehicles, previews and cache limits at all three zooms.

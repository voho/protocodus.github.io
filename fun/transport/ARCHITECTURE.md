# Transport module reference

Static ES modules. No build step. `model.js` owns all game state and exports:

- `BIOMES`: object keyed taiga/tundra/desert, each `{name, description}`.
- `INDUSTRIES`: object keyed kind, each `{name, inputs: {cargo:count}, outputs: {cargo:count}, cost, biomes: string[]}`.
- `CARGO`: object keyed cargo, each `{name, color, price}`.
- `createGame({biome='taiga', seed=1847, size='square512'}={})` returns JSON-serializable state.
- `build(game, tool, x, y)` returns `{ok, message}`; tools `road`, `rail`, `bridge`, `railbridge`, `tunnel`, `railtunnel`, `bus-stop`, `train-stop`, `port`, `residential`, `commercial`, `industrial`, `city`, `bulldoze`, or industry kind.
- `buildPath(game, tool, points)` returns `{ok, message}` for array `{x,y}`; safe partial placement is allowed but message must report errors/cost. Deduplicate points.
- `addRoute(game, {name, mode:'road'|'rail'|'water', stops:[stationId,stationId], cargo:'passengers'|cargoKey})` returns `{ok,message,route?}`. Requires connected infrastructure and a suitable cargo source/destination. Buys vehicle, exact upfront cost exposed by `VEHICLE_COSTS` export.
- `removeRoute(game, routeId)` returns `{ok,message,refund}`; `getRetirementRefund(game, routeId)` quotes that refund, 45% of each vehicle's paid price.
- `renameStation(game, stationId, name)` and `renameRoute(game, routeId, name)` trim the name and return `{ok,message}`. They refuse an empty name (*Enter a name.*), one over 36 characters or the current name; otherwise they set it and bump `revision`. Duplicate names are allowed but never generated: `build` numbers a new stop from `stations.length+1` upwards until `${place} Stop|Station|Port ${n}` is unused, so fresh games keep their old names and nothing new is saved.
- `addRouteVehicle(game, routeId)` buys one more vehicle at `getVehiclePurchase` for an active route and returns `{ok,message,vehicle?,cost?}`. `sellRouteVehicle(game, routeId)` sells the lowest generation, then the emptiest, then the last in array order, and refuses the last vehicle; it returns `{ok,message,vehicle?,refund?}`. `getRouteFleet(game, routeId)` returns `{count,capacity,load,minLevel,maxLevel,sellRefund}`. `vehicleNoun(mode, cargo)` names a route's vehicle (bus, truck, train or ship). `addRoute` and `addRouteVehicle` refuse once the fleet holds `MAX_VEHICLES` (10,000), the most `validateGame` accepts.
- `tick(game, days)` advances time, vehicles, economy, growth. Can receive fractional days; sim rate one day per real second at 1x.
- `findPath(game, from:{x,y}, to:{x,y}, mode)` returns tile coordinate array or null.
- `saveGame(game)` / `loadGame()` / `deleteSave()` localStorage with validation/version.
- `drainDeliveryEvents(game)` returns and clears the paid deliveries since the last call, `{x,y,revenue,cargo,amount,routeId,day}` at the receiving stop, at most 64. A module `WeakMap` keyed by the game holds them: never saved, never touching `nextId` or `randomAt`.
- `routeBreakPoint(game, route)` returns null for a running route or one without a path. For a disconnected route it returns `{x,y,index}`: the first point of its last path, from the start stop, that fails `findPath`'s own tile (`validNetwork`) or edge (`networkEdgeAllowed`) rule, or the path midpoint when the gap lies elsewhere, such as a removed stop.
- Optional additional exports welcome. `model.js` must stay DOM-free for Node tests, apart from guarded localStorage.

`background-jobs.js` wraps creation, restoration and save encoding in cancellable module workers. `world-worker.js` uses the same model and codecs as synchronous callers. `world-transfer.js` transfers a four-byte tile buffer, sparse exact extensions, route-coordinate buffers and the procedural-save baseline rather than cloning millions of tile objects. Main-thread capture/hydration yields in small slices; the transfer format is internal and does not change local save formats. Unsupported/blocked workers fall back to the existing model.

`createGameAsync` and `restoreGameAsync` return hydrated games with a one-shot `preparedSave(game)`. `autosave-storage.js` commits that already validated JSON when a new or loaded company is activated. Its `noteAutosaveTime()`, also called by `app.js` `saveFinished`, records the wall-clock time of each autosave write under `transport-autosave-at` for the start menu's Continue line. Live autosaves hold edits and daily steps only during `captureGame`, resume before `encodeCapturedGame`, coalesce overlapping requests, and reject results from cancelled or replaced worlds. Vehicles keep moving inside the current day: tiles and route paths change only with edits or daily steps, and `captureWorld` clones all other state, including route state, before its first slice. Edits, a day boundary or a replaced route path during capture cause a fresh snapshot attempt. Periodic autosaves start in the first quarter of a day while running; construction strokes debounce their autosave by three seconds. A failed autosave, other than repeated snapshot changes, toasts once, marks `#game-menu-button[data-alert]` and `#save-status.save-failed`, and backs off to 60 seconds until a later save succeeds. Page-leave saves retain synchronous validation/encoding because the browser can stop workers during navigation. Save dialogs opt into cooperative capture with `capturePaused:true`; synchronous snapshot semantics remain available to older `writeSaveSlot` callers. Cancellation and storage failures preserve the previous complete slot.

State shape:
```
{version:1, seed, biome, width:512, height:384, size:'huge', tiles:Tile[],
 money:400000, day:0, totalDelivered:0, totalRevenue:0,
 monthlyIncome:0, monthlyExpenses:0, history:[], notifications:[],
 cities:City[], industries:Industry[], stations:Station[], routes:Route[], vehicles:Vehicle[], zones:Zone[], revision:0, networkRevision:0 }
```
`tiles[y*width+x]` = `{terrain:'grass'|'water'|'forest'|'mountain'|'rock'|'sand'|'snow', elevation:number, variant:number, detail?:string, publicRoad?:boolean, road:false, rail:false, bridge:false, tunnel:false, building:null|{kind: keyof BUILDINGS | 'house'|'apartment'|'shop'|'office'|'factory',level:number}, zone:null|'residential'|'commercial'|'industrial'}`. Roads and rails can coexist for crossings; bridges/tunnels terrain traversal. Coastline water has water neighbors; rivers same water.

City `{id,name,x,y,population,activity,growth}`. Industry `{id,kind,name,x,y,capacity,inventory:{cargo:number},production:number}`. Station `{id,name,x,y,mode:'road'|'rail'|'water'}`. Zone `{x,y,kind,progress}`. Building and industry anchors carry an explicit `footprint` of 1–3 tiles per side; missing fields preserve legacy one-tile sites. Stops remain one tile and their piers can visually overhang. Terrain-object anchors carry `terrainObject: {kind, detail, variant, footprint:2|3}`. Child cells retain their base terrain and have no duplicate object. Route `{id,name,mode,stops:[id,id],cargo,delivered,revenue,color,path:[{x,y}],active:true}`. Vehicle `{id,routeId,x,y,angle,load,capacity,progress,direction}` uses tile-coordinate floating x/y, angle in radians. A route runs one or more vehicles that reference it by `routeId`; `fleetIndex` groups them per revision. A vehicle's place in the round trip is its phase, `progress` outbound or `2L − progress` on the way back for a path of `L` tiles. `addRouteVehicle` starts the new vehicle at the middle of the widest phase gap (ties take the lowest start); within half a tile of a stop it starts there, loaded and departing. It needs no new saved field. Renderer must tolerate optional/missing stats.

`createGame` starts with at least 3 cities, environment-specific industries, visible terrain varieties, an already working two-stop passenger road route and initial bus, plus an unconnected production opportunity. The starter city is centered near 43% of world width and 47% of height, with a second town 24 tiles to its east. Name taiga initial city Alderbrook. Starting roads avoid obstacles. Industry growth and zoning service depend on activity; connected routes earn income only by actual loading/delivery. Starting game economy net positive at 1x. Seed deterministically changes generated terrain.

A label rises clear of the signs of stops within one tile of its town centre (found per station-index revision); signs never move, so picking is unaffected. Vehicle load badges that cross a label draw at 35% opacity
- `industryMarker(industry)` -> `{x,y,size}` in local CSS pixels for the center of a site's resource badge
- `screenToInspectTile(clientX,clientY,{slop=0}={})` -> `{x,y}`; picks stop signs, then industry resource markers (the draw order above the scene), then signs within `slop` px, then visible opaque artwork from front to back before falling through to the ordinary map tile. Explore passes a 12 px slop for touch. Construction always uses `screenToTile`. Artwork is tested with the exported `opaqueAt(image,sx,sy)`. A pointer move that stays on the hovered tile keeps `app.js`'s `hover` object, so it does not repaint a paused map.

- `getCamera()` -> `{x,y,zoom}`; zoom is exactly 0.5 (Region), 1 (Town), or 2 (Detail), as defined in `zoom.js`

- `setLens(cargo)` lights the producers and buyers of one freight cargo, or clears the lens with null or `passengers`; `getStats().lens` is `{cargo,sources,buyers,towns}` counted on screen in the last frame, or null
- `drawMinimap(canvas)`

Renderer handles camera and art only; UI handles DOM/pointers. Use requestAnimationFrame while the company or view is changing; paused unchanged worlds do not redraw. Static terrain is invalidated via game.revision. Sprites use bundled generated artwork for buildings, industries, nature, vehicles and infrastructure, with code-native drawing for continuous networks, terrain and unavailable-art fallbacks. Isometric 2D, detailed recognizable realistic sprite aesthetic; all assets are served with the game. `scenery-batches.js` partitions the exact static depth order into narrow diagonal strips. Prepared strips and a separate complete tree-shadow layer share a 96 MiB budget. Picking continues to use original sprite masks. Preparation is staged with a roughly 3 ms frame budget after ordinary scene drawing, and unfinished strips use their original sprites. ## Freedom rules

Every system stays optional and safe to ignore. `tests/idle-company.test.mjs` leaves the regional taiga 1847 company alone for 30 years: money never falls from one year end to the next, the starter service keeps working, no warning or error notice appears and the next goal never speaks of deadlines. Every new mechanic must keep this test green. A reward for engaging is fine; a loss or a warning for not engaging is not.

1. No mechanic may reduce what an unattended network earns, or make an asset decline over time.
2. Transport Tycoon systems arrive only in reward-only form: yearly new models with an optional Upgrade, as today; subsidies as contracts without expiry nags; town growth from service; industry growth from service. Town needs follow this: missing cargo slows the next housing tier, and never stops or reverses it.
3. Never add breakdowns, aging or servicing; station-rating cargo loss; industry closures (idle sites never shrink below half capacity and are never removed); construction bans; bankruptcy or game over; AI competitors.
4. A new warning notice must come from a player action, such as bulldozing or disconnecting, or appear at most once per streak.

## Isometric presentation

`isometric.js` is a DOM-free projection shared by the renderer, lighting and new-world previews. World pixel positions project to `(x − y, (x + y) / 2)`, giving a 64×32 diamond for a 32×32 logical tile. The inverse is `(screenY + screenX / 2, screenY − screenX / 2)`. Camera coordinates remain unprojected world pixels. Pointer picking, screen-space pan deltas and zoom anchors use the inverse; game state, generation recipes, paths, distances and save data keep their existing square grid.

Ground, water and continuous networks occupy the projected plane. Upright artwork is positioned by projected anchors and sorted from back to front; interface labels stay in screen space. `projectAngle` projects each vehicle direction vector, so eight-direction artwork, load overlays and headlights follow the visible track. The flat overhead minimap continues to use world coordinates. New-world biome cards show miniature isometric landscapes using the same projection. `tests/isometric.test.mjs` covers corner geometry, inverse picking through 2048-tile maps, all eight vehicle headings and pointer zoom anchors.

All 27 houses and 51 civic/commercial climate variants were regenerated for the fixed camera; `assets/world/isometric-architecture-prompts.json` records the built-in imagegen prompts. `prepare-building-atlas.py` preserves disconnected source RGBA silhouettes in padded cells, then existing house/world packers create 256px masters and display densities. House atlas input can use `--normalize-atlas` for tier-specific widths and a common foundation line. Window anchors are measured on final isometric masters and track each climate's recorded registration transform.

The later camera audit is recorded in `assets/world/camera-audit.md`. Active commerce atlases use `buildings-commerce-camera-v2`, replacing only bank, garage and hardware-store cells in all climates. Stops/ports and portals use their `-v2` siblings; stops and port art use square runtime bounds shared with their measured light panes. These corrections preserve original source directories. Generated edges retain small painterly variations around the exact terrain projection. Small stone details are upright objects, like other authored nature art; they must not be baked into ground textures and projected a second time.

## Multi-tile terrain objects

`terrain-objects.js` resolves anchors from any covered cell with a bounded 3×3 lookup. A 2×2 or 3×3 site requires matching base terrain, an equal rounded elevation level throughout, continuous height variation of at most 0.3 levels, and at most 0.6 levels across its complete one-tile collar. Water, buildings, networks, zones and other objects exclude placement. The allocator does not flatten or change the original terrain.

`world-terrain-objects.js` uses sparse seeded candidates and a temporary byte occupancy mask to add occasional large groves, rock outcrops and mountain formations. Mountain anchors are retained for save compatibility but no longer rendered as scenery: their saved elevations produce the mountain geometry. A large forest/rock parcel is rendered only when every displayed grid vertex across its full footprint has the same height. Invalid parcels can use small scenery only on individually flat child cells, without changing save occupancy. Recipe 6 runs this after recipe 5's building allocation; recipes 1–5 remain available unchanged for procedural saves. Restoring a company without `terrainObjectVersion:1` safely allocates eligible objects once. Explicit anchors round-trip through existing sparse tile extras.

Successful construction dissolves intersected terrain objects into their remaining single-tile scenery. Forest and rock demolition clears the complete parcel for one charge, preserving elevation. Mountain formations retain the ordinary terrain/tunnel rules. Earthworks also dissolve objects whose smoothing collar was changed; ecological succession releases a parcel before changing one of its constituents. Rejected construction never alters a parcel. Validation checks shape, overlap, terrain and flatness before accepting a save.

The renderer suppresses small scenery over covered parcels, positions each large object on its full ground diamond and sorts by its front corner. Groves distribute separately sized trees across the parcel. Inspection and clearing highlight the whole footprint; parcel and opaque sprite picks resolve to the anchor. Terrain lookups use a bounded cache invalidated by the game revision. `groundIsFlat` checks the actual mesh vertices for single trees, rocks, plants, cached detail sprites, flower dots and shoreline reeds; slopes retain only their ground material. Hidden sloping trees also omit their water reflections. `rasterForestComposition` is shared by generated tree artwork and the separate ground-shadow pass. Shadow stamps use a 32 MiB LRU and render before upright objects; visibility and flat-ground checks are shared with the trees. Nearby height edits invalidate cached decoration choices through the existing geometry fingerprint halo.

## Local simulation

`environment.js` is DOM-free and exposes:

- `randomAt(game, day, key, salt=0)`: a stateless sample derived from seed, integer day, entity/cell key and decision channel. Camera renders, frame rates and save restoration cannot consume or reorder random samples.
- `weatherAt(game, x, y, day=game.day)`: spatially blended weather fronts and seasonal/biome/elevation effects, returning `wetness`, `cold`, `heat`, `growth` and `travel` factors.
- `localEnvironment(game, x, y, radius=3)`: a bounded neighborhood survey of infrastructure, vegetation, moisture, housing, shops, services, civic amenities, industry, pollution and active station coverage. Local road access uses adjacent tiles; rail access extends two tiles; active station coverage extends five tiles.
- `stepEcology(game)`: a daily sparse, asynchronous Moore-neighborhood update. It samples at most `min(4096, ceil(tileCount/128))` cells, buffers changes, then commits together. Grass, sand, snow and forest undergo local vegetation succession; water, mountains, rocks and every occupied/reserved plot remain protected. It returns the changed-tile count.

`settlements.js` exposes `stepSettlements(game)` for daily passenger demand, activity/supply decay, organic infill and zone development, plus `settlementSuitability(game, point, kind)` for the inspector's score and short positive/negative explanations. Decisions use seeded per-entity opportunities and local conditions. Building changes commit after proposals are collected, so new neighbors cannot trigger same-day development cascades. Organic growth only occupies vacant plots with road access; paid structures and civic landmarks are retained. Population rises when housing is actually added. Zone development requires recent deliveries and a local road; stalled interest can fade without deleting occupied buildings.

`townNeeds(game, city)` lists four needs in a fixed order: comfortable homes (food), prestige homes (goods, furniture or machinery), services (goods or fuel) and construction (stone or cement), each filtered to cargo the biome's industries make. A need is `met` when any of its cargo reached the town within `NEED_WINDOW` (120) days. `model.js` records that day in the covered town's optional `lastSupply[cargo]` whenever town cargo unloads; validation accepts only `TOWN_CARGO` keys with days in [0, `game.day`], and legacy towns simply have none. A zone's increment is multiplied by 0.25 while the need of its next tier (`floor(progress) + 1`) is unmet, and by 1.3 while construction is met. Needs never lower stored progress or stop development, and organic infill ignores them. `settlementSuitability` returns an unmet next-tier need as a neutral `notes` entry ('Faster with food deliveries'), never as a negative. The town inspector shows the needs under Grows faster with once the company has a zone or a freight route; the Towns list shows only cargo a town has received.

`industry-simulation.js` exposes `initializeIndustry(game, industry)`, `stepIndustries(game, notify)` and `industryConditions(game, industry)`. The inspector's productivity score and reasons use the same resource, access, neighboring structure and weather inputs as production. Industries save `lastProductionDay`, `nextProductionDay` and `nextReviewDay` for staggered work and capacity reviews. Production respects complete recipe proportions, available inputs and warehouse space. A capacity review grows a site only while every output store is under half full; a fuller store holds capacity, so a site served by too few vehicles stops expanding. Only idle sites shrink, never below their stock, so no cargo is lost. `outputFill(industry)` returns the fullest output store as a 0–1 share for the expansion notice, the inspector's Storage cell and `industryStatus(industry, game)`, which reports a half-full store as `backlog` and, given the game, names the active route that loads there.

`model.js` advances these processes at simulation-day boundaries, while vehicles move continuously between them. Fleet events advance in chronological order so vehicles competing for limited inventory receive the same cargo regardless of frame partitioning. Vehicles save `dwellRemaining` and `tripSerial` to preserve seeded loading waits. Monthly reporting remains a calendar operation.

`revision` describes visible world changes. `networkRevision` changes when transport infrastructure changes; pathfinding and the cached base infrastructure upkeep use this separate revision. Growing trees or houses therefore do not force routes to replan or recount the entire huge world. Optional simulation fields are validated when present; legacy saves receive deterministic defaults on load. New simulation state remains JSON-serializable and fits the existing compact save envelope.

`change-journal.js` records which cells each ecology day rewrote. `stepEcology` notes its proposals plus every footprint cell of a grove or outcrop it dissolved (`releaseTerrainObjectsCells`, while `releaseTerrainObjects` still returns the dissolved count) under the one revision it creates. `surfaceChangesSince(game, revision)` returns the sorted union only when such entries cover every revision since then for the same `tiles` array. Any other revision, a gap, more than 64 entries or 65,536 cells, or a replaced tile array returns `null`. The journal is never saved and no simulation decision reads it. Ecology never changes heights, water, structures or sites, so the renderer keeps its building, parcel, station and industry indexes, foundations, grid and route paths across a journaled span. It forgets only the changed parcels and fingerprints only cached chunks whose bounds, padded by three tiles, contain a change; every other chunk current at the previous revision is marked current. Scenery lists and prepared strips are still rebuilt. `terrain-geometry.js` keeps its height fields and `lighting.js` its static emitters under the same test. `null` restores full invalidation, and route paths are keyed on a renderer-local structure revision that advances only then.


## Expanded worlds

`cargo-icons.js` owns the 20 resource pictograms used throughout the interface. `cargoIcon(kind, {decorative})` returns an SVG; `cargoBadge(kind, {count, label})` adds a resource name/quantity and accessible description; `cargoRecipe(inputs, outputs, {counts, labels})` renders grouped input/output badges and an accessible recipe sentence. Decorative nested SVGs defer their accessible name to the containing badge. The route form’s illustrated cargo buttons update `formDraft.cargo` and a hidden native select, so changing stops or rebuilding the panel preserves the selected resource.

`NEW_WORLD_SIZES` exposes square512, square1024 and square2048; 512 is the default. `WORLD_SIZES` also retains regional 128×96, large 256×192, huge 512×384 and vast 768×576 for compatibility. Square maps have 48/128/320 towns and 8/20/48 complete industry districts. `MAX_WORLD_TILES` bounds decoding at 2048². Version 2 uses domain-warped regional fields sampled on a four-tile lattice, spatial lake buckets, branching river curves, weighted settlement regions and habitat-scored industry sites; digest fixtures prevent silent changes that would invalidate procedural saves. Old 100×72 saves remain valid. The tile codec stores base properties in four bytes per tile, uses exact elevation/detail palettes, and stores buildings/zones/extra flags sparsely. Public generated roads are excluded from company road upkeep.

`BUILDINGS` defines the 26 architectural identities used by world generation, growth, construction, inspectors and sprite selection. `residentialKind(variant, level)` chooses among the nine house designs; `commercialKind` selects shops/services. Legacy generic kinds still render.

Rendering uses 6×6 tile chunks with an LRU memory budget. Each of the three zoom views uses its own sprite detail profile and a native raster scale of `zoom × devicePixelRatio` (DPR capped at 2). `createSprites(biome, {pixelScale, detailLevel})` draws directly at the target resolution; it does not enlarge a low-resolution image. Chunks include raster scale and detail profile in their identity, while revision fingerprints update changed terrain in every cached view. Camera transforms align to physical pixels, keeping tile picking and drawing consistent. The three zoom factories retain prepared artwork in a shared 128 MiB sprite LRU. Land vehicles, ships, stops, ports and portals share a separate 32 MiB LRU across zooms. Their direction frames, cargo and route markings are composed once at the physical display size, then copied without resizing their pixels. An artwork revision invalidates prepared fallbacks; a climate or world replacement releases the old factories. Small camera drags reuse padded scenery lists and cached foundation geometry, merging sorted moving vehicles into the existing scenery order. Night lights reuse sparse emitter lists, prepared window groups and directional headlight images; opacity continues to follow exact simulation time.

`getStats()` reports chunk count, bytes, memory limit, maximum canvas dimensions, raster scale, detail profile and DPR. It also counts visible vehicle load indicators by empty, partial and full state. Vehicle indicators render after map labels in screen coordinates: loaded carriers show their route's cargo pictogram and a proportional meter, while empty carriers have a smaller unfilled meter. Resource images share the existing local SVG cache with industry markers. A per-frame route lookup avoids scanning the route list separately for every vehicle and indicator.

The cache budget starts at 48 MiB and can grow for large high-density viewports, up to 256 MiB. The minimap/atlas caps its raster at 512 pixels per side and reuses its pixel buffer across ecology revisions. A sparse road/rail overlay preserves one-tile networks even when terrain is downsampled, and rebuilds its network index only when `networkRevision` changes. `getStats()` separates sampled minimap dimensions from logical world dimensions and exposes sample/scan counters. The app coalesces continuous wheel gestures into a single neighboring view change, and all button and keyboard inputs use the same three-level contract.

## Production and route planning

`chains.js` derives production dependencies and compatible destinations from the economy catalogs. `chains-view.js` and `chains.css` present the current environment's complete graph, an output's recursive ingredient chain, and every world instance of a selected industry type. Locating an instance centers the map and opens its inspector. The inspector shows downstream cargo consumers and up to five closest matching industry or town destinations. Distances describe direct map distance, not a verified road, rail or water connection.

The same targets become map context, view state in `app.js` that is never saved. `industryDestinations` hands its `findIndustryTargets` result to `holdContext`, which stores `selectionContext` as `{selected, industryId, targets:[{x,y,kind,id,rank}], highlight}`. The frame loop passes it as `render(now, {context})` only while its `selected` is still the current selection object, so a different pick, a vehicle card, a tool or closing the inspector hides it without extra bookkeeping. `contextView()` adds `covers`, the display-pixel rects of `#inspector` and `#objective-card`. Before the label pass, `contextArcs` strokes a screen-space quadratic arc from the source's `industryMarker` to each target's marker or town-label anchor (29 px × zoom above its centre), bowed upward by 18% of its length. `route-planner.js` provides the DOM-free route filtering and connection validation used by the Routes panel. The route planner verifies the actual network and station cargo coverage before launch. Its cached path result is invalidated by selected stops, transport mode or `networkRevision`; changes to available funds and cargo eligibility also update launch availability. The simulation's `addRoute` still performs authoritative validation when the form is submitted. A valid plan also returns `existingRouteId`: a route with the same mode and cargo on the same stops, in either order for passengers and in loading order for freight. The form then offers to add a vehicle to it, keeping **Launch separate service** as a secondary action.

`routeCargoList(game)` lists the environment's route cargo. `routeCargoOptions(game, draft)` judges each of them for the chosen stops with `validateRoutePlan(game, draft, {ignoreFunds:true})`, so short funds never hide a fit and the cached path is reused. Fitting cargo comes first: loaded at the start, then loaded at the end, then passengers. The list stays empty until the stops are connected. When connected stops share no cargo at all, the plan's message names what each end handles. `defaultRouteName(game, plan, cargo)` names a launch after its two towns or its cargo flow, within the form's 36 characters. The Routes panel suggests cargo once per change of stops or transport (`formDraft.autoKey`) and never replaces a cargo that still fits. Whether the planner is folded is session-only draft state; it is never saved.

`forecastRoute(game, draft, plan?)` estimates one more vehicle for a valid plan (funds ignored) and returns `null` otherwise: `perVehicleDay`, `supplyDay`, `movedDay`, `netMonth`, `paybackMonths` (∞ when not positive), `vehiclesToSaturate` and `otherModes`, plus `madeDay`, `fullLoad`, `cost` and `joining`. A round trip takes `2L / (base speed × (1 + .1·generation) × .88) + .4` days over the path's `L` tiles, with `travelSpeed`'s base speeds 2.8, 4.6 and 1.8; a passenger vehicle loads at both ends. Freight supply sums the loading stop's producers: a raw producer's recipe at `industryConditions(game, industry, stop)` productivity, which counts the planned stop as active, and at its mean capacity over the next 180 days, growing by `reviewGrowth` at the mean draw every 33 days from its next review; a factory takes the larger of its recent production and the ingredients active routes deliver, never above its recipe. Passenger supply is each town's `passengerArrivals(game, town, day)` at the mean draw. Active routes that load the same cargo from the same producers or towns take their fleet's throughput first. `netMonth` is 30 days of `fareFor` on the carried units less `priceFor` of `VEHICLE_UPKEEP` plus, for a new route, its share of `INFRASTRUCTURE_UPKEEP` split among the routes on each tile and stop, as `infrastructureShares` allocates it. `fareFor(game, cargo, pathLength, units, day)` is the fare `unloadVehicle` pays, and maintenance, `infrastructureShares` and `stepSettlements` use the same shared constants and helpers, so the refactor leaves same-seed saves byte-identical. The forecast is pure and cached per draft, day, revision and fleet size. The route form shows its monthly line under `#route-connection` (muted `#8a6d52` when not positive) and folds the rest into `.forecast-details`, whose open state is kept in `localStorage` under `transport-forecast-details`. A node test compares it with 180 simulated days on flat road and rail lines of 10 and 40 tiles.

In `app.js`, delegated pointer and focus events on `#panel-content` highlight a hovered or focused route card until the pointer or focus leaves it. ## Local save slots

The automatic checkpoint keeps the existing `transport-save-v1` key and compact tile format. Named snapshots use one independent `transport-slot-v1:<id>` localStorage entry per slot; listing enumerates this prefix without a separate index. Each versioned envelope includes its id, name, biome, game day, balance, save timestamp, dimensions, route count, payload encoding, checksum and complete compact game payload. Native gzip compresses a `tile-binary-v1` frame with raw packed tile bytes before base64 encoding for original sizes or dense 15-bit UTF16 packing for Vast; JSON remains the fallback when compression is unavailable. The payload checksum lets listing flag accidental edits and truncation without expanding each world.

`save-slots.js` provides `listSaveSlots()`, asynchronous `writeSaveSlot(game, {id?, name})` and `readSaveSlot(id)`, plus `renameSaveSlot(id, name)` and `deleteSaveSlot(id)`. List metadata distinguishes ready, corrupt and unavailable entries. The autosave has id `autosave` and is read-only through this API. Writes validate and serialize before a single `setItem`, preserving the previous record when storage rejects a write. Renaming changes metadata without re-encoding its payload. Reading validates and hydrates the complete world but does not activate it or change storage. `slotDate`, `slotMoney`, `slotDetails` and `savedAgo` give the start menu and the Load / save dialog one wording for game dates, balances, map sizes, route counts and save age.

`saves-view.js` and `saves.css` mount the Load / save dialog with named slots, an independent autosave checkpoint, asynchronous progress/errors, and inline confirmations for replacing the world, overwriting a slot or deleting one. Disposal prevents an outstanding read from activating a company after the dialog has closed. The dialog retains an accessible close control while operations run and while its list scrolls.

`start-menu.js` opens on New game. On a fresh page load it waits for the first paint, because summarising the autosave parses the whole save, and then adds a primary `#start-continue` above the tabs when the autosave is ready. Continue takes focus from New game and loads through the same `loadSlot` path as the Load game rows. The in-game Main menu passes `canResume` and offers Resume instead, so it never shows Continue.

`app.js` activates a loaded or generated world only after writing its new autosave successfully. New-world generation paints a progress state before synchronous generation and disables duplicate submission. Atlas/minimap geometry follows the current world aspect ratio. Activation refreshes the renderer, minimap, camera, tool, route draft and filters, inspector and chain selection. Failed activation leaves the current company and prior autosave intact. The dialog pauses the simulation and periodic autosaving; the previous simulation speed resumes on closing. Named saves are independent snapshots and are not updated by periodic autosave or new-world generation.

## Map visibility

`visibility.js` defines sixteen independent display preferences: `trees`, `buildings`, `roads`, `rails`, `stations`, `names`, `industryIcons`, `vehicles`, `vehicleLoads`, `deliveries`, `routes`, `zones`, `lighting`, `weather`, `grid` and `goal`. Defaults enable every layer, including the gentle grid. `layerPreset('all')` enables all sixteen, while `layerPreset('terrain')` disables all sixteen. The renderer ignores `goal`; `app.js` uses it to show or hide the Next goal card. Normalization accepts only known boolean fields. Browser persistence uses `transport-visibility-v1`, independently of both the active autosave and named game slots; read/write failures leave the current interface usable.

`visibility-view.js` and `visibility.css` present a nonmodal popover with native labeled checkbox switches, presets, keyboard support and outside/Escape dismissal. It reads current flags through callbacks and delegates changes to `app.js`, without touching simulation state. Opening this panel does not pause the game. Loading or generating a company retains the existing display preferences.

`renderer.js` applies scenery/network flags to cached terrain composition. Changing trees, buildings, roads, railways, stations or zones invalidates baked chunks across zoom levels. Names, industry icons, vehicles, load indicators, routes and the grid are live overlays. Vegetation includes forest sprites and plant details; sparse rocks remain scenery, while mountains use the ground geometry. Buildings includes houses, civic structures and industry art. Roads, rails and stops remain independently controllable. Hidden vehicles never draw load indicators, while hiding only their loads retains the vehicles.

`getStats().layers` exposes a copy of renderer preferences alongside cache and vehicle-indicator statistics. Legacy `render(now, {showGrid, showRoutes})` arguments remain optional per-render overrides and do not rewrite stored preferences. The minimap and atlas reflect applicable scenery/network flags. Hidden industry icons no longer contribute extended inspection hitboxes; hidden stop badges likewise lose their extended map-picker hitboxes. Their actual tiles remain inspectable and all gameplay occupancy/network rules remain intact. Selection, coverage and construction previews are contextual interaction overlays rather than persistent layers.

Delivery income is a live overlay labelled Income (`deliveries`). Right after each `tick`, `app.js` drains `drainDeliveryEvents` into at most 24 screen floaters, merging deliveries at one stop within 300 ms, and drops them after 1600 ms. It repaints a paused map only until the last one fades, then returns to zero redraws. `renderer.js` draws them after the load indicators and before the vignette: a pill with the cargo icon, 58 px above the stop (58 × zoom at Detail), rising 22 px with ease-out unless reduced motion is preferred, opaque until 60% of its life and then fading. Town labels are drawn first, so a pill that would start over a label's rectangle starts 3 px above it, and one starting below a label stops rising 3 px under it. At Region zoom it sums each 3×3-tile cell into one pill at its newest delivery. `updateHud` adds a 600 ms `.income-pulse` (`compact-hud.css`) to `#profit` when monthly income rose since the last HUD update. With sound on, a new on-screen floater plays a two-tone chime at most every 700 ms; `transport-sound-v1` remembers the sound choice, and a remembered "on" resumes the audio context on the first pointerdown.

## Rivers and shipping

World generation carves connected water channels with `detail: 'river'`, joins tributaries to the trunk rivers and connects river mouths to sea. A navigable river runs beside both starter towns, with shoreline berths within the existing five-tile catchment. Generated streets preserve water and mark crossings as bridges; building placement skips water. River detail uses the existing lossless detail palette without a save format change. Existing saved terrain is not regenerated.

`build(game, 'port', x, y)` creates a water-mode station on unoccupied water cardinally adjacent to land. Ports cannot overlap bridges or other structures. `findPath(..., 'water')` follows cardinally connected water, including bridge tiles, and requires no network flags. Ports share `stationCoverage`, freight recipes, passenger eligibility, route validation, load/unload and saved state with land transport. A ship costs $64,000 and carries 140 units; a port costs $18,000. Water travel uses a slower base speed with seeded weather, shoreline, bridge-approach and port-traffic effects; port loading pauses and upkeep use the same deterministic simulation clocks.

The route planner, filters, map picking, port inspector and save validation accept the water mode. Ship and ferry rendering respects the Vehicles and Cargo loads switches; ports follow Stops. Ships pass under the visible bridge deck, while road and rail vehicles render above it. Port badges retain the existing 14-pixel station hitbox, using an anchor rather than the bus/train letter.

## Annual economy and vehicle generations

`economy-pricing.js` derives Gregorian years from the same January 1950 epoch as the HUD. `inflationInfo(game)` returns calendar year, year index, the seeded annual rate and the compound price index. `priceFor(game, basePrice)` rounds the current price. Rates and unlocked vehicle levels derive from seed and simulation day, requiring no new persisted schedule. A bounded cached calculation handles far-future saves. Monthly financial reports use Gregorian month boundaries from the same epoch. Construction, clearing surcharges, purchases, upgrades, upkeep and delivery revenue share this pricing layer; arrival revenue uses the actual arrival day.

`getVehiclePurchase` quotes the latest generation. Each calendar year unlocks one level, increasing base capacity by 20% and base speed by 10% per level. `getVehicleUpgrade` and `getFleetUpgrade` provide read-only quotes; `upgradeRouteVehicle` and `upgradeFleet` perform authoritative affordability checks and mutate the eligible fleet atomically. Vehicles store `level` and `paidPrice`, and retain load, position, progress and dwell time when upgraded. Legacy vehicles default to level zero and their original base purchase price. Retirement returns 45% of paid price, including upgrades. The UI refreshes quotes with calendar and funds changes.

## Biome scenery and lighting

`BIOME_NATURE` in `terrain-sprites.js` shares tree, mountain and plant catalogs between seeded world generation and local ecology. Expanded detail strings preserve the seven gameplay terrain classes and use the existing tile codec. Habitat patches choose related species; new woodland often inherits nearby species. `isPlantDetail` identifies decorative vegetation for rendering and environmental calculations. Hiding trees removes foothill vegetation while retaining the mountain itself.

`tree-sprites.js` generates 64 deterministic woodland compositions per biome/detail, containing one to five trees with per-tree species, leaf coverage, height, placement and branch/crown seeds. Composition is independent of zoom; each profile only adjusts fine marks. The renderer hashes tile coordinates, world seed and the saved variant into the artwork seed, so legacy 16-variant maps gain the new art without changing save state. Forest canvases are 48×48 logical pixels (x −8…40, y −16…32); their crowns can overlap neighboring cells. Other sprites keep the 32×40 envelope. Chunk padding covers these overhangs.

`relief-sprites.js` draws irregular mountain crests, layered desert formations and fractured boulders. `terrain-sprites.js` separates geometry and texture streams for stable vegetation between zooms. Nature uses 64 cached variants, other art retains 12; the sprite factory has a 16 MiB LRU limit in addition to the chunk budget.

`lighting.js` derives a 60-second cycle at 1× from saved simulation day, beginning at noon. A smooth ambient tint and cached glow sprites render after terrain and before screen-space labels. Windows, lamps, port reflections, headlights and navigation lights obey the matching visibility flags; the Lighting preference disables the pass for constant daytime. Lighting never advances the economy or invalidates baked terrain chunks. `hasClearableDecoration` keeps Bulldozer placement previews and authoritative cleanup consistent.

## Simple construction and map controls

`construction-plan.js` adapts the five-tool interface to existing model operations. `resolveBuildTool` chooses bridges/tunnels for Road/Rail and a station mode for Stop; explicit legacy tools still pass through. `model.buildProblem(game, tool, x, y, {money})` returns every refusal `build()` would give, in `build()`'s own order and wording, as `{message, reason: 'blocked'|'funds'|'terrain'}`, or null; `build()` itself starts with it, so previews and construction cannot drift. `quoteBuildPlan` deduplicates tiles and walks them with the balance `buildPlan` will spend, giving each placement a `state`: `built`, `blocked` (with its `problem`), `slope`, `funds` or `ok`. `networkTerrainPlanIssues` lists each tile that breaks the grade rules as `uneven`, `sideways` or `ramp-junction` (with the existing ramp `at`); `networkTerrainPlanProblem` keeps its single message. Road and rail strokes are all-or-nothing: any slope issue, blocked tile or unaffordable tile makes the quote `ok: false`, and `buildPlan` then builds nothing and charges $0. Zones and demolition stay partial; their quote reports `partial`, `buildable`, `blocked` and `unaffordable`, and a result with nothing built but a refusal is `ok: false`. A single stop, port or town quotes `buildProblem`'s verdict. `model.buildPath` keeps its documented partial policy for API callers. `buildPlan` delegates every placement to `model.build`, preserving single-placement metadata. The renderer colours each preview tile from the quote's states (error red for problem tiles, muted for the rest of a refused road/rail stroke, a red outline on a ramp it would join sideways) and uses `buildProblem` for single-tile highlights. `route-tiles.js` indexes the tiles of active road and rail routes, cached by network revision and route paths; the Bulldozer tip and preview use it to name the services a demolition would cut. The placement tip in `app.js` shows a refused quote's message as `.invalid`, a partial one as `.partial` (for example `Builds 2 of 9 · funds for 2`), and appends `.warning` notes: a valid stop names what `stationCoverage` loads, accepts and serves (memoised per tile and revision), or says no customers are within 5 tiles. After a release the tip re-quotes the tile under the pointer, and a build that skipped tiles toasts as a warning. The active tool never changes save structure or simulation rules.

`network-router.js` shapes Road and Rail drags on the view side; it never changes the model, saves or simulation. `gridLine(a, b, first)` is the plain L, along the longer axis first unless `first` names `'x'` or `'y'`. `planNetworkStroke(game, mode, from, to, {margin=12, maxExpanded=40000, budgetMs=8})` returns `{path, reason, expanded}`: the plain L as `direct` whenever its quote has no slope issue or blocked tile (funds never reshape a drag), otherwise the other bend as `flipped`, otherwise an A* over tile × arrival direction inside the drag's box plus the margin, with typed-array costs, parents and states and a binary heap. Each tile is classified once through `buildProblem` with unlimited funds, so occupancy, other-mode stations, span metadata and side contact with finished ramps match construction exactly. Ramps are entered and left only along their axis, only flat ground and finished network turn, water and mountain crossings run straight, and `networkEdgeAllowed` keeps span axes. A step costs the tile's `constructionCost` over the mode's base price, 0.6 on finished same-mode tiles, plus 0.2 per turn; the heuristic is Manhattan distance, and ties prefer the state nearer the goal, then the lower index. `quoteBuildPlan` validates the result; a ramp the path itself touches sideways is penalised and searched again, at most three times. A path longer than 1.6 × the Manhattan distance + 8 steps, or dearer than 1.6 × the cheaper L (blocked tiles priced as buildable), returns the plain L as `too-far`; no route, a failed validation, the expansion cap or the time budget returns it as `fallback`, whose red tiles explain the refusal. `constructionLine` in `app.js` calls it only for Road and Rail, never for spans, Level, zones or demolition, and keeps the last plan per company in a `WeakMap` keyed on tool, both end tiles, `networkRevision` and `revision`, so a drag searches again only when its end tile changes. A pointer holding Shift (read at pointerdown and every move) keeps the plain L, bent along `pointer.firstAxis`: the grid axis of the first tile change after the 5 px drag threshold. Touch has no Shift and always follows the terrain. The placement tip appends *follows terrain · Shift: straight* to `flipped` and `routed` strokes, without the Shift hint on touch, and replaces a `too-far` refusal with *No gentle route — level ground or drag in shorter segments*.

`app.js` owns compact zoom/options popovers and the active-tool Done control. Every tool/view/dialog change cancels captured gestures. The gesture stores the original tool; releases cannot apply a subsequently chosen tool. Single-object dragging pans, while line tools build on release. A second touch cancels construction, pans with the midpoint and advances at most one of the three zooms per pinch gesture; releases remain inert until all touches lift. A chorded right press (a pointermove with `buttons&2`) or the first Escape marks the captured stroke cancelled and keeps the tool; line-tool drags pick with `clamp`, so a stroke past the map edge ends at the edge. Space retains native button behavior for keyboard focus, but a button focused by a pointer press still pauses; a pan cannot also toggle pause. E, [, ], N and 1-3 also match `e.code` (KeyE, BracketLeft/Right, KeyN, Digit1-3), so they survive QWERTZ and AZERTY layouts; a printed + still zooms. `controls.css` keeps map targets at least 44px and moves secondary options behind menus.

The keyboard tile cursor lives in `app.js` as `keyCursor` (`{x, y, keyboard: true}`), `keyStart` and `keyGame`; it is view state, never saved. `keyCursorKey(e)` runs in the document keydown handler after the menu, layer and Ctrl/Cmd+S guards and before the route-pick Escape, only for keys whose target is `#world` with no Ctrl, Cmd, Alt, captured pointer or touch gesture. Enter with no cursor, or with one whose screen point left the canvas, calls `centreKeyCursor()`: `renderer.screenToTile` (or `screenToVertex` for earthworks) at the canvas centre with `clamp`, and a line tool (`lineTools`, outside route picking) also sets `keyStart` there. Otherwise Enter calls `pickRouteStopAt` while picking (a finished pick focuses the first enabled launch button, else the end-stop picker, waiting for the drawer's `transitionend` when it is still hidden), `inspect(x, y, '', 'keyboard')` in Explore, sets `keyStart` for a line tool, or `paintPath` with `constructionLine(keyStart, keyCursor, tool)` or the single tile; repeats are swallowed. Unshifted arrows move the cursor x±1 (Right/Left) or y±1 (Down/Up), clamped to the world, then `renderer.pan` scrolls it back inside the central 70 % of the canvas; an off-screen cursor is re-centred instead. Shifted arrows fall through to the 90 px pan. Escape clears `keyStart`, then the cursor, then reaches the existing tool Escape. `showKeyCursor()` sets `hover` to the cursor and `preview` to the line, writes `#tile-coordinates`, anchors `updatePlacementTip` at the tile's screen point with `pointerType: 'keyboard'` (which, like touch, omits the Shift hint) and, 400 ms after the last change, writes `'<x>, <y> · <place> · <tool> · <cost or problem>'` into the visually hidden polite region `#map-cursor-status`, reusing the tip's text. `setTool` keeps the cursor and drops `keyStart`; canvas focus re-shows it, blur hides its tip, and keyup and wheel re-anchor the tip after camera moves. Capture-phase `pointerdown`, and `pointermove` with nonzero movement, on the canvas drop the cursor before the pointer handlers run; `keyOwned()` also drops one from another world or whose `hover` the pointer has replaced, and an Enter on a cursor that is not drawn only re-shows it. `renderer.render` frames a `hover` marked `keyboard` just outside its tile (a ring around the grid point for earthworks) in a pale casing and the `#e17b4a` focus orange, after the hover preview, so the validity colour inside stays visible.

Browser page zoom is contained in `controls.css`. Under `.compact-play`, the top bar, workspace and status bar allow only panning, and the zoom controls, active-tool bar, route-pick banner and toast actions allow no browser gesture, so a pinch that starts on game chrome cannot zoom the page. `#modal` and the start menu sit outside these rules and stay pinch-zoomable. `app.js` mirrors `visualViewport.scale > 1.01` as `#app.page-zoomed`; while it is set the rules lift and `#world` allows `pinch-zoom`, so a pinch over the map returns the page to normal size. The browser cancels those pointers, so the map zoom does not also step. Safari's `gesturestart`/`gesturechange` are prevented under the same conditions. `html` and `body` disable overscroll (no pull-to-refresh), and the drawer, inspector, game menu and dialog contain their own scrolling.

HUD updates re-run `inspect()` for the open inspector. It builds the markup as a string and writes it only when the selection changed, the inspector was hidden, or the string or its `worldSerial|x,y,kind` key differs from the last write. It compares with that string, never `innerHTML`, because drawn portraits add canvas attributes. An unchanged place keeps its nodes, handlers and native tooltips. Safari and iPad never focus a pressed button, so a focus guard alone cannot stop a rebuild from replacing the button mid-press and losing the click. Capture-phase `pointerdown` on `#inspector` and `#panel-content` holds the inspector and entity-list refreshes until `pointerup`/`pointercancel` plus 250 ms; the focus guard remains for keyboard users. `#inspector` is a `region` labelled by `#inspector-title` (`tabindex=-1`). Target rows and town/industry cards activated by keyboard (`detail === 0`) pass `origin 'keyboard'`, which focuses that heading without scrolling; pointer inspects never move focus. Changed values still rebuild the inspector, so a resource tooltip resets when its amount changes.

The card reuses the inspector's generated-string key (`worldSerial|vehicle:id`) but fills its load and trip lines and Follow's `aria-pressed` in place, so a moving vehicle never replaces its buttons, and a pressed or focused control holds structural rebuilds. `follow` keeps the vehicle object and the camera it last set: before each frame's camera read it calls `renderer.focus` once the vehicle has moved more than 0.01 tiles (then pans it to the middle of the open map above the card where, on a phone, the card covers the map's centre), and stops when the card closes, the tool is not Explore, a drag, pinch or wheel reaches the canvas, or anything else moves the camera more than 2 world pixels. Under `(pointer: coarse)` the route-pick banner and status say *Tap* and *Drag to explore*; a miss reads *Choose a road stop.* for every pointer.

Inspectors link places to their services. `servingStops(site)` returns the stops within `STATION_RADIUS` of a town centre or of an industry's nearest footprint tile (`nearbyStations` around the site centre, filtered by `industryDistance`), nearest first. ## Construction undo

`construction-undo.js` is DOM-free and reverses one construction gesture as a diff, never by restoring a snapshot, so vehicles, cargo, inventories and growth elsewhere keep what happened since. `captureUndo(game, tool, points)` runs before `buildPlan`: it clones every tile within Chebyshev distance 3 of the points (and of the site anchor a bulldozer point resolves to), keeps the ordered station, industry, city and zone arrays, each town's population and passengers, the notices, `money`/`monthlyExpenses`/`totalExpenses` and `nextId`. For a town founding it also lists the buildings that still lack `populationCityId`, because `build` pins every home to its town first; a tile array with none left is remembered until the next undo and not scanned again. `finishUndo(entry, game, result)` returns null unless a successful build changed something. It keeps only the tiles that differ, the added and removed objects by identity (removed ones with their index), per-town population and passenger before/after pairs, the ids of added notices and the cost.

The entry also carries a watch. Its core is every changed tile plus the footprint of each station, industry and town it adds or removes and of each building or grove/outcrop parcel it would bring back; each core tile keeps a post-build clone. Tiles up to two to the upper left are watched only for a building anchor that could cover the core, and the neighbours of a changed height are watched like the core, since slopes, bridge clearance and parcel flatness read them. `undoProblem(game, entry)` refuses when a watched tile changed apart from ground cover (`detail`, parcels, and natural terrain among grass, forest, sand and snow; a returning parcel's own tiles must keep their exact terrain), when an added object is gone, when a station, town or industry placed later stands on the core, when a route uses an added stop, when an added industry has shipped or received cargo, or when a building belongs to an added town. `undoStale` marks entries from another tile array, used ones, and any made before `game.routes` was replaced or changed length. There is no calendar limit: a quiet build can be undone in a later month.

`undoConstruction(game, entry)` restores each changed tile in place (all keys deleted, then the clone assigned) so `game.tiles` and the save baseline keep their identity. Each array returns to its exact old contents when it is unchanged since the build; otherwise added objects leave and removed ones are spliced back at their index. Town figures, money and both expense totals return exactly while unchanged, else by the recorded difference, with passengers capped at 90 % of population and expenses never below zero, since a later month has already booked the spend. Added notices are removed, owners pinned by a founding are unset, and `nextId` goes back only while nothing else consumed an id. The undo ends with `model.invalidateNetworkPoints(game, points)` when network tiles or stations changed, else `game.revision++`.

`app.js` journals every `paintPath` release and keeps a session stack of the last ten entries, emptied by `activateGame`; stale entries are dropped whenever the stack is read. Ctrl/Cmd+Z is handled after the dialog and text-field guard, so inputs keep native undo, and does nothing mid-stroke. The build toast carries an **Undo** action and is keyed by its entry, so each build keeps its own toast and a keyboard undo closes it. Success toasts `Road removed · $X refunded`; refusals and 'Nothing to undo.' are warnings. The app then refreshes route connections, the HUD, the scene and any open panel, re-seeds the notice cursor if its notice was removed, and schedules the same debounced autosave as construction. Nothing new is saved.

## Playability and accounting

`gameplay-insights.js` derives optional next projects, truthful town service, industry input/storage states and actionable route health. It uses the simulation’s five-tile station catchment, measured to an industry’s nearest footprint tile and to a town’s centre, and capacity-dependent900-unit storage. `routeHealth(game, route, stats)` returns `waiting` and fleet `capacity` for a working route: freight sums the whole stock of the start stop's producers, passengers take the smaller waiting count of the two linked towns. From two full fleet loads (and at least 50) waiting it reports `busy`, which the card shows in orange with a hint to add a vehicle; `stats.capacity` spares the scan when the caller has already summed the fleet. `routesNeedingAttention(game)` counts the routes whose health is `blocked` (disconnected, missing a stop, no two towns, no producer or no buyer), and `routeNeedsAttention(game, route)` tests one; waiting and busy routes never count. The blocked set is memoised in a `WeakMap` keyed by `networkRevision`, the identities and lengths of the route, industry, station and town lists, and the indices of inactive routes, since `updateRoutePath` flips `active` without moving any revision. `game.revision` moves daily and stays out of the key, so a recompute (about 20 ms for 300 freight routes, less than re-pathing them after the same construction) follows only a player's change; a cached call takes microseconds. The interface keeps search/filter inputs mounted during periodic entity refresh, returns explicit view changes to the top, and exposes building benefits in the catalog and inspector.

`nextProject(game, {source})` returns one goal. Until a freight route has delivered it is the first cargo route: the 40 raw producers nearest the home town are ranked by buyer distance, home distance and extra buyer inputs, then walked lazily through `stopSiteKind(game, site)`. That returns `'road'` for a free road/rail tile or dry, non-mountain, unoccupied land that is not a complex slope within the catchment, `'port'` for shoreline water, and `null` otherwise; towns always count. Unservable producers and buyers are skipped, port-only producers rank 60 behind, a free road in the catchment ranks 5 ahead, and up to three `choices` `{source, buyer:{id,kind,name,x,y}, cargo, distance}` name distinct producer/buyer pairs. `source` keeps a chosen alternative when it is still offered. `firstRouteSteps(game, choice)` ticks a stop near each site, a same-mode path of at least three tiles between the three nearest stops on each side, a launched route of that cargo touching both sides, and its first delivery; steps carry the tool, button label and route-form draft the interface needs. Later stages are 100 freight deliveries (with `progress`), the cheapest servable raw-producer-to-factory pair while no freight route ends at a factory that takes its cargo (stations nearest the source first; each extra factory input costs 40 tiles), carrying a supplied factory's output to its nearest servable buyer, a Chains fallback, a neighborhood in a town served within the last month, then the company milestones (see Company milestones), and finally free play once every chapter is complete. Searches are memoised in a `WeakMap` by network revision, site counts and last ids, station count and, for factory stages, route count; `game.revision` changes daily and is never part of a key. The stage itself, delivery totals and first delivery are re-read on every call, so a repeated call on a 2048 world takes well under a millisecond.

`app.js` shows the goal as `#objective-card` over the map’s top-right corner. `renderGoal` runs from `updateHud` and repaints only when a signature of title, detail, steps, progress and the chosen alternative changes. Only the first open step has a button; `runProjectAction(action, target, extra)` serves the card and the Build drawer’s project card alike (`source`, `city`, `stop`, `connect`, `launch`, `chains`, `routes`, `towns`, `atlas`). Stop and connection steps frame both sites, switching to the Region view when they are over 20 tiles apart or do not fit on screen. `connect` takes `extra.tool`, so a milestone can open Rail or Port directly; the drawer passes it as `data-project-tool`. The × stores the fold as a preference, `'folded'` or `'open'` under `transport-next-goal-v2` in `localStorage`; a non-empty v1 value (the old folded title) reads as folded. While folded, a new title only updates `#objective-chip-title` and sets `.changed` until the card is opened: a 1.2 s fade to the orange tint (instant under reduced motion) and, on phones, an orange instead of green pill dot. The `goal` layer hides the card entirely; Show on map opens it and turns the layer back on. When a goal has no checklist, **Company goals** takes the place of How to connect at the foot of the card. `gameplay.css` hides the card while the game menu, layers or map options are open, and below 1100px while the drawer or inspector is open. At 700px and below it is a one-line pill at the bottom left that expands on tap, and toasts move to the top while it is open.

Passenger loading and delivery share `passengerEndpoints`, selecting a distinct pair of covered towns by nearest combined walking distance. Homes record `populationCityId` to retain population ownership after new towns are founded; outlying homes explicitly retain null. Housing creation and demolition share `housingCapacity`. A finished construction gesture refreshes network connections while paused.

`monthlyOperatingExpenses` separates upkeep from total cash expenditure. Routes accumulate allocated vehicle/station/network expenses; shared infrastructure is charged once, with unassigned infrastructure and factories left as company overhead. Legacy saves establish revenue baselines and accounting start days so historical fares are not compared with nonexistent historical upkeep. New worlds and loaded saves both write the next autosave before replacing the active game.

## Company milestones

`milestones.js` is DOM-free. `MILESTONES` is an ordered list of sixteen `{id, chapter, title, detail, unit, action, tool, target(game), button, progress(game) → {value, target}}` in four `CHAPTERS`. Each check is O(routes + cities + industries): freight milestones sum `route.delivered` over non-passenger routes only, never `game.totalDelivered`; town counts and the town of 2,000 use `activeCities` from `settlements.js` (towns within five tiles of a stop on an active route; generated towns reach about 1,800, so only a served town counts); profit compares the last history entry's `operatingProfit` with `priceFor(game, base)`; the industry at 200% needs an active route loading from it; the full chain walks the biome's `productionChain` edges (cached per biome) for raw → factory → factory → town cargo, each carried and the last delivered to a stop that covers a town. A founded town carries `founded: true`, validated as a boolean when present.

`evaluateMilestones(game)` runs once per simulated day from `tick`, after `maintenance`. It creates `game.milestones ??= {}` and stamps every unstamped id whose progress meets its target with `floor(day)`, in any order; the first run backfills an older save the same way. It spends no `nextId`, sends no notice and never grants money, so frame partitions and whole ticks stay identical. `validMilestones(game)` accepts `undefined` or a plain object of at most 64 ids of at most 40 characters whose days are integers in `[0, floor(day)]`; unknown ids are kept and ignored. Milestones are recognition only: a test asserts that nothing but `milestones.js` and `app.js` reads `game.milestones`.

`nextMilestone(game, preferred)` returns the first unmet goal of the lowest open chapter, or `preferred` when it is one of that chapter's unmet goals, with `choices` and `chapter`. A chapter is complete when all but one of its goals are stamped or met, so one unwanted goal never blocks the next. `nextProject` maps it to the card shape with `progress: {value, max}` (hidden for yes/no goals), `milestone` and `chapter`, and `progressText` formats counts, money, percentages and levels for the card and the dialog. `milestoneChapters(game)` lists every chapter with each goal's stamp, live progress and done state.

`app.js` seeds `seenMilestones` in `resetMoments` from the stamps, or for a company without any from `metMilestones(game)`, so a loaded save or its backfill announces nothing. `watchMilestones` runs with `watchRoutes` on each HUD update and queues `Milestone · <title>` (type `milestone`, action **Goals**) for at most one milestone per calendar month; later ones that month appear only in News and the dialog. The company's first freight delivery adds ` · Milestone` to its first-delivery toast and counts as that month's toast. News merges stamps within the log's span by day. **Game menu → Company goals** (`onGoals` in `compact-play.js`) and the card's **Company goals** link open `openGoals`, which lists the chapters, dates reached, progress and the card's current goal; like every modal it pauses the game until closed.

## Transport contracts

`contracts.js` is DOM-free and takes station coverage as a `coverageOf(station)` callback, so it never imports `model.js`. `game.contracts` is optional: absent until the first offer, then an array of at most `MAX_CONTRACTS` (8) `{id, cargo, sourceId, target: {kind: 'industry'|'city', id}, distance, multiplier, offeredDay, expiresDay}`, where an awarded contract adds `{routeId, awardedDay, until, earned}` with integer days and `until = awardedDay + 365`. `validContracts(game)` checks those shapes and ranges (multiplier 1–4, `expiresDay = offeredDay + 365`, days no later than today, freight cargo only). Ids are never checked against the world: `contractState(game, contract)` reads a missing producer, buyer or route as `'expired'`, otherwise `'offer'`, `'active'` or `'complete'`, so bulldozing a site cannot invalidate a save.

`stepContracts(game, coverageOf)` runs from `monthlyUpdate` after the month's accounts close. It keeps offers, active contracts and complete ones for 31 more days (so the interface sees the finish), then, once any freight route has delivered or offers already exist, fills empty slots up to `OFFER_SLOTS` (3) while the list has room. Each slot draws at most 64 candidates from `randomAt(game, calendarMonth, 'contract', slot * 64 + k)`: one draw picks a generated producer (`owner !== 'player'`, with outputs, and producing if it has inputs), its fractional parts pick the output and a buyer among industries with that input and, for `TOWN_CARGO`, towns, whose centres lie 20–70 tiles away (`nearbyIndustries`/`nearbyCities`). A pair already listed, or served by an active route of that cargo, is skipped. Ids are `contract-<month>-<sample>`; no `nextId` is spent and no notice is sent. `multiplier = clamp(1.6 × f(10) / f(d) − 1, 1, 4)` with `f(L) = (1 + .55√L) / L`, rounded to hundredths: fares grow with `1 + .55√L` while trips grow with `L`, so a served pair earns 1.6× what a 10-tile route earns per vehicle-day, or a little less beyond about 62 tiles, where the bonus stops at 4×. A 2048² month takes well under 2 ms.

`unloadVehicle` adds `contractBonus(game, route, fare, day, coverageOf)` to a paid fare when `game.contracts` exists. A route serves a pair when its first stop's coverage holds the producer and its last stop's holds the buying industry, or has the town as `cities[0]`, the town that receives town cargo. Pair matches are cached per route in a `WeakMap` keyed by `game.revision` and the list's identity (every step that changes the list assigns a new array), so unloading stays O(1). The first delivery on an open, unexpired offer stamps the award; while `day < until` the route's deliveries earn `round(fare × multiplier)` more, added to route revenue, monthly income, money, total revenue and the delivery event, and summed in `earned`. A route holds one contract at a time. `forecastRoute` never reads route revenue, so forecasts stay at normal fares.

`app.js` renders `#contract-offers` from `fleetControls` as a `<details>` folded by default (its open state lives for the session) and hidden while no offer or contract is live; `refreshUpgradeControls` refreshes its count and rows. Rows name each site, an industry by its nearest town, and **Show** frames both in the map area the inspector leaves free and inspects the producer, or only frames them at 700px and below. `routeRate` returns base net and bonus side by side for a route with an active contract and `markContractRoutes` flags its rate with `data-contract`, so the card keeps its height. `watchContracts` runs with `watchMilestones` and compares states with the previous HUD update: a new `'active'` queues *Contract won* (type `milestone`) and `'active'` → `'complete'` queues the completion with its earnings (type `ok`), both with the route as target; the first update after a world is activated only records states, so loading replays nothing.

## Notices and news

`model.js` keeps the newest 24 notices first, as `{id, day, message, text, type}`. `notify(game, message, type, {topic, target})` adds an optional `topic` (up to 32 characters) and `target` `{kind: 'industry'|'city'|'route', id}`. Route disconnections use topic `route-connection`, industry expansion uses `industry-growth`, and town founding targets the new city. Bulldozing an industry collects, before removal, the freight routes with a stop in its catchment whose `freightPair` holds; after removal, each one whose pair fails gets a `route-supply` warning targeting the route: *lost its timber producer* naming the start stop, or *lost its buyer* naming the end stop. It is a player action, so the extra ids shift `nextId` only then. Validation checks both fields only when present, so older saves load unchanged. Every notice consumes one `nextId`, which keys vehicle randomness, so the interface derives its own moments instead of adding model notices.

`ui-notices.js` is DOM-free. `collectNotices(notifications, lastId, max=24)` returns unseen notices oldest first, or the newest six when the last shown id is no longer in the log. `groupNotices(list)` merges each burst of a groupable topic (`route-connection`, `route-supply`, `industry-growth`) into one entry that keeps every target; legacy notices without a topic are recognized by their wording. `crossedMilestone` and `newYearNotice` define the town thresholds and the January text.

`app.js` collects and groups notices on each HUD update into a queue. The queue shows at most two entries every 400 ms, warnings first, and paces town moments to one every two seconds; a batch beeps at most once. `toast(message, options)` still accepts the boolean error flag, or takes `{type: 'ok'|'warning'|'error'|'milestone', action: {label, run}, key, silent}`; a repeated key on a visible toast updates its ×N count and restarts its timer. Only the action button takes pointer input. `activateGame` seeds the pricing year, the known routes and town population peaks, so loading a save replays nothing; a world before its first day shows its welcome. A freight route launched during the session, or a loaded one that has not delivered, announces its first delivery. A January repricing waits while an input in the panel has focus and re-renders when focus leaves it. The News dialog reads `game.notifications` directly and offers Show only for targets that still exist. When a clicked action reveals a control in the drawer, the focused control inherits the pointer press, so Space still pauses instead of pressing it.

## Square-world persistence and material detail

`transport-procedural-v1` retains the generation descriptor and packed changed tiles. `rememberGeneratedWorld` stores an exact four-byte baseline per tile plus sparse extras in a WeakMap, using 16 MiB for 2048² without retaining a second object grid. Every save compares current fields with that baseline, preserving direct edits, unknown properties, nested fields and deletion/reversion. Changed indices use delta varints and existing UTF16 tile packing. Loading regenerates the explicitly versioned recipe, captures its baseline and applies patches. Legacy JSON and compact-v1 saves continue to decode. Metadata listing validates packed fields without regenerating a second continent.

`water-art.js` paints cached depth/bank detail in the water clip; small live ripples derive from simulation day. `raster-houses.js` supplies nine generated house designs per biome, with 256×256 transparent masters and prefiltered 16/32/64/128-pixel sprite cells. The runtime loads only the smaller atlases, choosing a cell size matching `32 × zoom × devicePixelRatio`. Artwork occupies a 32×32 square within the existing 32×40 sprite envelope. `lighting.js` uses hand-measured pane rectangles for each house and biome.

Startup waits at most four seconds for house and world artwork, loading both groups concurrently. Each decoded density becomes available independently; a missing resolution uses another loaded resolution of the same artwork. Late arrivals increment a separate artwork revision, refreshing sprite/chunk caches and interface thumbnails without changing game state. Missing biome artwork can use the same identity from another available climate, with matching window anchors; native drawings remain the final fallback when no image is usable. Connectivity recovery retries only missing densities. `worldArtStats()` reports usable atlases, failures and actual generated-image draws by identity. Asset loading, downscaling provenance and prompts are documented in `assets/houses/README.md`. `processing-sprites.js` retains native factory/extractor fallback drawings; production rules remain in the economy catalog.

`index.html` includes a visible full-screen loading dialog and an inert game shell. The lightweight `boot.js` promotes that dialog to the native top layer and paints before importing `app.js`; import/startup failures keep a retry action available. `loading-screen.js` reports three actual preparation stages, with live status text and reduced-motion support. Startup, new-world creation and named-save reading paint the loader before expensive synchronous work, then render the map and minimap before revealing the game. Loading blocks gameplay shortcuts, simulation frames and background autosaves. Recoverable save/generation failures close the loader in `finally` and return to the original dialog. `tests/loading-screen-browser-check.mjs` exercises delayed and failed imports, local-save loading, storage failure/retry and mobile reduced motion in isolated storage.

`world-v2.js` combines the terrain and placement recipes in `world-terrain-v2.js` and `world-placement-v2.js`. Recipes through version 6 retain their original geography: recipe 4 preserves underlying elevation beneath roads and settlements, recipe 5 allocates full building and industry plots, and recipe 6 adds level multi-tile terrain objects. The starter dry-land area blends into its surroundings. This avoids rectangular trenches around settlements. New square worlds use recipe 7: `world-mountains-v7.js` adds seeded local peaks, short asymmetric ridges and desert mesas to the saved elevation field before settlement placement. High ground between features becomes broad valleys; water and the protected opening corridor keep their original elevations. Peaks reach the visual level-7 ceiling without a second world-sized height array. `world.js` retains recipes 1–6 and the old rectangular sizes, with frozen digest fixtures. Shared deterministic primitives live in `world-noise.js`. The save descriptor, baseline and validation carry the explicit generation version, so old companies regenerate their original geography. Never change a released recipe without introducing a new version and retaining existing digest fixtures.

## Continuous terrain relief

`terrain-elevation.js` reads the precise saved `tile.elevation` on a 0–16 scale; water is level zero. This legacy scale remains the source representation for old procedural recipes and save metadata; player-facing heights use eight discrete vertex levels. Rendering does not mutate terrain or add a second saved height field. A nonnegative cubic B-spline over neighboring tile centers blends heights, biome ground colors and geological coverage into a continuous surface. The overview retains analytical gradient lighting. The isometric mesh requests `terrainReliefRaster(..., {lighting:false})` (fourth parameter), retaining the blended texture colors while applying lighting from the actual geometric faces.

Ground is sampled at six points per tile into a reusable small canvas, then smoothly drawn into the existing bounded chunk cache. Sampling phases, soil moisture, fine grain and geological texture are world-aligned, producing byte-identical shared samples in overlapping chunks. Two-tile fingerprint padding covers the spline support, and fingerprints include fractional elevation. Forest density follows neighboring woodland and regional noise. Single-tile rock density is reduced to 18% of its former selection rate; large rock parcels retain their visible footprints. Mountain sprites are suppressed, with their geological texture retained on the raised ground. The overview uses the same altitude colors and a cheaper slope estimate. A material field combines world-aligned moisture patches, fine grass/sand grain and restrained geological variation. The renderer avoids repeated per-tile sand arcs and pale washes that would obscure that material. `landscape-scenery.js` selects presentation-only patches of local flowers and grasses, keeping scattered detail stones rare without rewriting saved ecology. Habitat patches mix species instead of repeating lichen everywhere; empty detail stays bare after bulldozing or earthworks. `tests/terrain-elevation.test.mjs` verifies interpolation and seams; `tests/terrain-elevation-browser-check.mjs` covers live elevation edits across chunks, exact restoration, all environments, zooms and display densities.

`shoreline.js` traces water boundaries, filters neighboring contour controls and adds subtle world-aligned bank variation. The resulting curves replace repeated rounded tile corners while preserving land/water tile centers, isolated ponds and narrow channels. Padded chunks produce identical shared curves; `water-art.js` adds local shallows and damp banks without a uniform bright outline. Its coast pass follows the same smoothed contours, ignores artificial chunk edges, and clips translucent shelves and broken foam to water. Animation uses a sparse seed-based selection at every zoom and simulation time, so Pause freezes the exact frame; moving ripples never rebuild terrain chunks. `tests/shoreline.test.mjs` checks navigation clearance and seams. `tests/landscape-realism-browser-check.mjs` captures deterministic town, forest, highland and coast scenes across environments, zooms and display densities, and checks canopy clipping and cache limits in isolated browser storage.

## Raised isometric geometry

`terrain-geometry.js` maps source elevation to eight integer vertex heights, 0–7, with 24 projected pixels per height step. The legacy 0–16 source helpers and structure metadata remain unchanged. An exact Chebyshev lower envelope limits all eight neighboring vertices to one level of difference, using an eight-point halo; a 96-entry LRU caches 32×32 vertex chunks without a whole-world height array. Each tile has two triangles split along NW–SE. Shared corner points touching water are at sea level. The diagonal bound prevents folded faces even on the taller slopes. Centers interpolate from NW and SE; they are not independent height samples. `surfaceHeight`, `projectGround` and `pickGround` use the same planes for rendering, pointer selection and overlays.

`terrain-mesh.js` warps the existing authored ground and network textures onto those triangles. Each face uses orientation-dependent surface-normal lighting, with antialiased joins tested at every supported raster scale. Each visible 6×6 terrain chunk caches only its projected mesh against the existing memory budget. One reusable source-texture canvas serves every chunk, avoiding redundant Retina bitmaps and eviction churn without reducing texture resolution. The geometry halo participates in chunk fingerprints, so nearby height edits refresh every affected slope. Large-map minimaps retain bounded sampling.

Camera focus, panning and anchored zoom use the raised projection. Ground grids and construction previews follow the mesh. Buildings sit on foundations at the highest center or corner in their complete footprint, with retaining faces where necessary. Bridge decks resolve a constant span height from their displayed bank levels; network-only shore textures ramp to that deck at the shared edge, and vehicle positions follow the same approach. Lighting receives separate building, ground and transport projection callbacks. None of these view transforms alter saved elevation, networks or routes.

## Terrain construction controls

`app.js` groups earthworks and explicit crossings in the expandable Network → Terrain & crossings panel. Raise/lower gestures use the same deduplicated construction plan, prices, notifications, revision handling and autosave path as other tools. Terrain tools snap to visible grid vertices and mark their connecting edges. Each raise/lower drag captures every selected point’s target before mutation, verifies the final limited surface, and commits the complete stroke atomically. A point already moved by a neighboring edit is not lowered twice. Quotes and previews use the same plan. Level area uses a rectangle anchored at its first point’s displayed integer height. `planTerraformLevel`, `quoteTerraformLevel` and `buildTerraformLevel` preflight the complete area and funds before charging per changed height step. A point already displayed at the requested height is a free no-op, even when its legacy source is fractional. Raises and leveling boundaries reject heights the limiter cannot display; edited sources save as level/7 through the existing codec. Adjoining water and occupied cells protect their shared corners. A bounded counterfactual also rejects edits whose slope influence would move more distant occupied corners. Bridge/tunnel gestures snap to one horizontal or vertical axis; the shared plan quote provides level, total price and validation feedback. Road/rail selection changes the explicit crossing mode without adding four permanent toolbar buttons.

Span validation and atomic construction belong to the model and construction planner, so previews and committed spans share the same geometry and constraints. New crossings require flat endpoint cells at matching displayed heights. Interior bridge faces stay at or below the deck with clearance, and tunnel faces stay at or above the bore with cover. Legacy raw-height validation remains available for saved crossings; new source-clipped banks use the geometric envelope. The renderer uses the existing saved elevation for terrain and span metadata for level crossings. `tests/earthworks-browser-check.mjs` exercises the controls through browser pointer events and isolated local storage.

`terrain-engineering.js` centralizes earthwork protection, span geometry and network edge validation. New ordinary networks use the rendered four-corner surface: near-flat ground accepts junctions, while monotonic straight inclines permit only their uphill axis. Side slopes, corner slopes, crowns and turning/joining a ramp sideways reject the complete stroke before payment. Existing saved networks remain traversable. Interior span tiles store `structureLevel` and `structureAxis`; approaches remain ordinary network tiles. Pathfinding permits entry along the span axis at its deck or bore level, while legacy untagged networks retain their original connection rules. Construction invalidates route caches once, demolition removes the metadata, and the existing sparse save codec preserves both elevation edits and span fields without a format migration. `structure-visibility.js` shares underground vehicle visibility between the renderer and night lighting. Model tests cover atomic failures, routing, repairs and saved-world restoration; the engineering renderer check verifies portals, underground vehicles, previews and cache limits at all three zooms.
